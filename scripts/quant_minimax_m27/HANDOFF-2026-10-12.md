## Open question, decide before rewriting run_unsloth_compatible.ps1

The r2 pipeline exists only because the installed Unsloth Studio server was a
stock llama.cpp build whose GGML type range ends at 66, so it rejected r1 files
carrying fork-local types (139, 156). `prepare_unsloth_compatible.py` therefore
downgrades `IQ3_KS -> IQ3_S` and `IQ5_K -> Q5_K`.

Since 2026-10-04 Studio runs **our** ik_llama build from `W:`, which supports
those types by construction. So the downgrade is probably unnecessary now and
`run_recipe.ps1` with the original recipes may be the better path. This is
**assumed, not established**: the r1 GGUF files were deleted, so nothing was
loaded to prove it. A cheap check is to quantize one small-footprint recipe with
fork types and load it in Studio.

## Two traps that cost time

**Context, not model size, is what breaks a load.** Studio reads the context from
GGUF metadata, and M2.7 declares `context_length=196608`. Loading `ram_safe`
(79.4 GiB) at that context needs, by llama-server's own accounting,
`81321 MiB model + 47899 MiB KV = 130392 MiB` against 95.1 GiB RAM and a
111.1 GiB commit limit. The load never finishes, Studio's watchdog kills the
backend after three failed health checks, and the UI says "Server stopped
unexpectedly". KV here costs about 0.244 GiB per 1k tokens:

| Context | KV f16 | KV with `-ctk q8_0 -ctv q8_0` |
|---|---|---|
| 196608 | 46.8 GiB | 23.4 GiB |
| 65536 | 15.6 | 7.8 |
| 32768 | 8.0 | 4.0 |

Cap the context per model in Studio before loading anything above `compact`.

**`Permission denied` over SSH means the account is locked, not a broken key.**
`AndrewM` locks after 10 bad passwords in 10 minutes, and each Playwright
`chrome.exe` launch with a fresh profile writes one. Wait 10 minutes without
retrying. Details: `~/docs/connect-desktop-hens8k7.md` on the Linux host.
