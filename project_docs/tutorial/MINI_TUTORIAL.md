# Mini Tutorial: How To Think About The Dashboard

Этот документ не про кнопки интерфейса. Он про логику.

Если вы поймете логику ниже, вы сможете осмысленно настраивать не только готовые примеры из документации, но и новые случаи.

## 1. Сначала надо понять, что именно вы оптимизируете

Новички часто говорят: "хочу быстрее".

Этого недостаточно. Есть как минимум три разных "быстрее":

1. Быстрее обработать prompt.
- это `PP` (prompt processing)
- важно для длинных запросов и длинной истории диалога

2. Быстрее генерировать токены.
- это `TG` (token generation)
- это скорость "печати" ответа

3. Быстрее пройти реальный цикл "прочитал prompt -> начал отвечать -> закончил ответ".
- это `PG` или mixed path
- для реального пользователя обычно это главный режим

Именно поэтому дашборд спрашивает workload.

## 2. Dense и MoE — это не одно и то же

### Dense

Dense модель использует все свои веса на каждый токен.

Следствие:
- важны CPU bandwidth и обычная locality
- настройки относительно предсказуемы
- если модель помещается в RAM, поведение чаще стабильнее

### MoE

MoE модель состоит из большого числа экспертов, но на каждом токене реально работает только часть из них.

Следствие:
- важно не только "как быстро считать", но и "какие именно части модели нужно держать горячими"
- huge MoE легко становится `swap-bound`
- плохая настройка памяти может убить пользу от любой локальной оптимизации kernel'ов

Практический вывод:
- одну и ту же оптимизацию нельзя механически переносить с Dense на MoE
- одну и ту же оптимизацию нельзя механически переносить с `Qwen3MoE` на `MiniMax`

## 3. Как реально работает MoE-модель во время inference

Здесь у новичков часто возникает опасная ошибка.

Кажется, что если модель огромная, но "active params" всего `10B`, то она должна работать как обычная dense-модель на `10B`.

Для huge MoE это неверно.

### Что люди обычно представляют неправильно

Неправильная картина выглядит так:

1. пользователь отправил prompt
2. роутер один раз выбрал нужные `10B`
3. runtime загрузил этот кусок в RAM
4. дальше модель работает только на нем

На практике так обычно **не происходит**.

### Мысленный эксперимент: dense `10B` против MoE `230B / 10B active`

Это полезно представить как две разные мастерские.

#### Dense `10B`

У вас есть одна мастерская и один постоянный набор инструментов.

На каждом заказе:
- вы подходите к тому же самому столу
- берете те же инструменты
- выполняете работу

Что это значит для runtime:
- путь исполнения предсказуем
- рабочий набор более стабилен
- данные проще держать в RAM и кешах

#### MoE `230B / 10B active`

У вас не одна мастерская, а огромный склад с множеством наборов инструментов.

На каждом шаге нужно:
1. понять, какие инструменты понадобятся сейчас
2. найти их
3. принести их к рабочему месту
4. использовать
5. на следующем шаге, возможно, снова брать уже другой набор

Что это значит для runtime:
- активная часть маленькая только в каждый конкретный момент
- но путь к этой активной части динамический и дорогой
- часть цены сидит не в math, а в логистике доступа к данным

Именно поэтому:
- `10B active` не равно "ведет себя как dense `10B`"

### Что происходит на самом деле

Во время prompt и decode inference выглядит примерно так:

1. Сначала работает общая часть модели.
- attention
- norms
- router
- другие shared operations

2. В каждом MoE-слое роутер выбирает экспертов.
- не один раз на всю сессию
- а по слоям
- и по токенам

3. Runtime пытается добраться до нужных expert weights.
- если они уже в RAM, это хорошо
- если нет, включается page-in и подкачка

4. Prompt действительно может прогреть часть памяти.
- часть нужных experts уже была использована
- часть страниц уже попала в RAM

5. Fork может запомнить "горячих" экспертов.
- это и есть логика `hot experts`
- но это только небольшой прогноз на ближайший decode

6. Во время decode все повторяется снова.
- shared path
- router
- expert choice
- memory access
- compute

Главный вывод:

- `active 10B` не означает, что существует один фиксированный компактный `10B` кусок модели, который мы один раз загрузили и дальше считаем как dense `10B`

### Пошагово: что происходит с одним токеном

Если упростить до одного токена, картина примерно такая:

1. Токен входит в слой.
2. Сначала отрабатывает общая часть:
- attention
- norms
- shared projections
- router

3. Роутер для этого слоя решает, какие эксперты нужны именно сейчас.
4. Runtime проверяет, где лежат нужные expert weights.
5. Если страницы уже в RAM, токен идет дальше почти сразу.
6. Если нет, начинаются:
- page faults
- подкачка
- ожидание данных

7. После этого выполняется compute по выбранным экспертам.
8. Дальше токен переходит к следующему слою, где история снова повторяется.

Ключевая мысль:

- в MoE цена токена складывается не только из "сколько считаем", но и из "насколько дорого добраться до того, что нужно считать"

### Почему prompt не "фиксирует будущую submodel"

Prompt действительно полезен, но его полезность часто понимают слишком сильно.

Prompt **может**:
- прогреть часть страниц
- показать, какие эксперты были особенно активны
- дать эвристику для `hot experts`

Prompt обычно **не может**:
- один раз навсегда определить весь будущий expert set
- гарантировать, что decode будет ходить только по тем же экспертам
- превратить huge MoE в стабильную dense-подмодель

Почему:

1. выбор экспертов зависит от текущего токена
2. выбор экспертов меняется по слоям
3. decode после prompt может пойти по другому содержательному пути, чем сам prompt

Практический вывод:

- prompt — это хороший сигнал для ближайшего будущего
- но не точный долгосрочный oracle

### Что реально может оставаться "горячим" после prompt

После prompt в выгодном случае остаются горячими:

1. shared части модели
- attention
- router
- norms
- другие часто используемые тензоры

2. часть expert pages, которые уже были недавно затронуты

3. небольшой `hot`-набор экспертов, если runtime специально его удерживает

Но не:

- весь будущий рабочий путь модели целиком

Поэтому huge MoE приходится думать не как "про одну загрузку нужного куска", а как про:

- постоянное управление рабочим набором под memory pressure

### Почему это замедляет huge MoE

Потому что bottleneck тут не только в математике.

Есть еще:

1. shared часть модели, которая работает всегда
2. router, который добавляет динамику
3. experts, которые могут быть не в RAM
4. page faults и подкачка
5. слабая locality по сравнению с обычной dense-моделью

Поэтому huge MoE вроде `MiniMax` часто упирается не в "мало FLOPS", а в:

- память
- working set
- paging
- expert locality

### Где именно обычно теряется время у huge MoE

Упрощенно время теряется в четырех местах:

#### 1. Shared path

Это цена, которую вы платите почти всегда:
- attention
- router
- общие слои

Даже если экспертов активно мало, shared path никуда не исчезает.

#### 2. Router + dynamic dispatch

Нужно не только считать, но и решить:
- какие эксперты брать
- как распределить токены
- как потом собрать результат

#### 3. Memory access

Это часто главный практический bottleneck huge MoE:
- нужные страницы могут быть не в RAM
- SSD намного медленнее RAM
- случайный доступ и page churn быстро убивают throughput

#### 4. Непредсказуемость рабочего набора

Чем менее стабилен набор нужных экспертов:
- тем хуже локальность
- тем труднее ОС и runtime держать полезные данные горячими

### Что из этого уже пытается делать fork

Именно поэтому в форке появляются идеи не только про kernels, но и про:

1. `mmap`
- чтобы huge-модель вообще можно было использовать в demand-paged режиме

2. `rtr`
- потому что layout может либо помочь, либо разрушить полезное memory behavior

3. `hot experts`
- чтобы хоть частично угадать ближайший decode working set

4. prefetch
- чтобы уменьшить цену page-in в критический момент

5. удержание shared tensors в RAM
- чтобы swap не трогал то, что нужно на каждом токене

### Что это значит practically

Именно поэтому для huge MoE важны:

- `mmap`
- `rtr`
- `hot experts`
- prefetch
- policy по памяти

А не только "включить побольше ускоряющих флагов".

Если упростить:

- dense `10B` часто ограничена арифметикой и обычной locality
- MoE `230B / 10B active` часто ограничена логистикой доступа к нужным данным

Именно это нужно понимать перед настройкой `MiniMax`.

### Какие параметры дашборда влияют на какие части этой схемы

Это полезная карта:

#### `Flash Attention`

Влияет прежде всего на:
- shared attention path

То есть:
- не решает проблему paging экспертов
- но может сильно ускорить ту часть, которая работает всегда

#### `Runtime Repack`

Влияет прежде всего на:
- layout весов
- working set
- startup/load behavior
- совместимость с выгодным `mmap`-поведением

То есть:
- может помочь in-RAM модели
- но может навредить huge swap-bound модели

#### `Hot Expert Budget`

Влияет прежде всего на:
- попытку удержать полезный небольшой expert subset горячим после prompt

То есть:
- это не "ускоритель вообще"
- это попытка улучшить ближайший decode working set

#### `mmap`

Влияет прежде всего на:
- стратегию доступа к huge модели
- возможность demand-paged работы

Для huge MoE это один из фундаментальных параметров, а не второстепенная галочка.

#### Threads

Влияют прежде всего на:
- compute-side scaling
- contention
- memory bandwidth pressure

То есть:
- "больше потоков" не всегда означает "быстрее", особенно когда bottleneck уже в памяти

### Интуиция, которую важно сохранить

Если вы запомните только одну вещь, пусть это будет она:

- huge MoE оптимизируется не только как математика, а как система доступа к данным под memory pressure

Именно поэтому:
- один и тот же "ускоряющий" флаг может быть полезен на `Qwen3MoE`
- и вреден на `MiniMax`

## 4. Что значит in-RAM и swap-bound

### in-RAM

Модель целиком помещается в RAM.

Что это значит practically:
- главная борьба идет за CPU locality, cache behavior и throughput
- здесь чаще полезны те настройки, которые улучшают арифметику и layout

### swap-bound

Модель не помещается в RAM целиком.

Что это значит practically:
- часть данных неизбежно приезжает с SSD
- система живет на page faults и подкачке
- настройки, которые расширяют working set, могут быть вреднее, чем кажутся

Для huge MoE это особенно важно.

Простое правило:
- если модель больше примерно `90%` доступной RAM, относитесь к ней как к `swap-bound`

## 5. Почему неверные параметры могут сильно вредить

### Слишком много потоков

Интуитивная ошибка новичка:
- "чем больше потоков, тем быстрее"

Почему это неверно:
- при MoE и bandwidth-sensitive workload потоки начинают мешать друг другу
- рост числа потоков может увеличить контенцию, а не скорость

Что вы увидите:
- токены/сек не растут
- иногда даже падают
- система шумит сильнее, а пользы нет

### Неправильный `rtr`

`Runtime Repack` меняет layout весов.

Когда это может помочь:
- модель помещается в RAM
- bottleneck ближе к CPU locality

Когда это может навредить:
- модель huge и `swap-bound`
- repack увеличивает working set или ломает выгодное mmap-поведение

Что вы увидите:
- вырос startup/load time
- throughput не вырос, а иногда просел
- система стала менее предсказуемой

### Неправильный `muge`

`Merge Up+Gate` кажется красивой идеей: объединить связанные экспертные тензоры.

Но на huge swap-bound MoE это может:
- увеличить pressure на память
- ухудшить page behavior
- дать хуже, чем базовый путь

Практический вывод:
- это не дефолтная "ускорялка"
- без отдельного A/B лучше держать `off`

**Важно:** на gpt-oss MXFP4 флаг `-muge` вызывает краш (exit 127). Для этого семейства `-muge` нельзя включать ни при каких условиях.

### Выключение `Flash Attention`

На текущем validated Zen4 профиле `Flash Attention` — это одна из самых надежных вещей.

Что вы увидите при неудачном отключении:
- mixed path замедлится
- prompt-side attention path разрастется
- выигрыш не появится, если вы не делаете специальную диагностику

### Агрессивная KV-квантизация без понимания задачи

KV cache влияет на память контекста.

Если вы выберете слишком тяжелый вариант:
- потратите больше RAM, чем нужно
- уменьшите пространство под веса и runtime

Если выберете слишком агрессивный вариант без проверки:
- можете получить деградацию качества или нестабильность на длинном контексте

Текущий safest baseline:
- `q8_0` для K и V

**Обновление (2026-03-06):** бенчмарки подтвердили, что `q8_0` для K и V нейтрален по скорости на Zen4. Это безопасный validated baseline, экономящий ~50% KV-cache памяти.

## 6. Почему `MiniMax` особый случай

`MiniMax M2.5` для этого форка важен не как экзотика, а как один из центральных targets.

Причина:
- это huge MoE, который на целевом хосте больше RAM
- именно на таких моделях проверяется реальная идея форка: можно ли заставить очень большую MoE-модель работать practically useful на CPU-only машине

Следствие:
- для `MiniMax` важны memory policy, expert locality, hot experts, runtime policy
- а не только обычные CPU optimizations

Поэтому правильный вопрос для `MiniMax` такой:
- не "что включить для максимального количества оптимизаций"
- а "какой набор дает лучшую end-to-end работу under memory pressure"

## 7. Как думать о validated и experimental

### Validated

Это то, что уже имеет измеримую опору.

Примеры:
- `-fa on` как надежный baseline
- `rtr auto` для текущих `Qwen3MoE` / `gpt-oss` линий
- `rtr off` как safest baseline для `MiniMax`

### Experimental

Это то, что выглядит разумно, но еще не должно подаваться как дефолт.

Примеры:
- `SER`
- `Merge QKV`
- `Hot Expert Budget`

Правильное поведение новичка:
- сначала получить рабочий validated baseline
- только потом включать 1 experimental knob за раз

## 8. Как рассуждать самому на новом кейсе

Если перед вами новая модель, идите по такой схеме:

1. Определить family.
- Dense или MoE
- если MoE, то насколько это похоже на `Qwen3MoE`, `gpt-oss` или `MiniMax`

2. Определить memory regime.
- in-RAM или swap-bound

3. Определить workload.
- `PP`, `TG`, `PG`

4. Взять validated baseline.
- не экспериментальный набор
- а безопасный старт

5. Менять только один существенный параметр за раз.

6. Сравнивать не только "стало быстрее или медленнее", но и:
- startup/load time
- общую предсказуемость
- не развалился ли другой workload path

Это и есть правильная интуиция.

## 9. Что должен уметь пользователь после этого документа

После этого документа пользователь должен уметь:
- понять, почему одна и та же настройка полезна для одной модели и вредна для другой
- не путать `TG-only` выводы с `PG`
- понимать, зачем нужен `mmap`, `rtr`, `KV cache`, `SER`, `Hot Expert Budget`
- отличать validated baseline от исследовательской опции

Если это уже понятно, переходите к `PARAMETER_REFERENCE.md`.
