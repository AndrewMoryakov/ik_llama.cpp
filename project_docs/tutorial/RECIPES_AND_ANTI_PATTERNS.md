# Recipes And Anti-Patterns

Этот документ нужен для двух вещей:
- быстро стартовать с рабочим профилем
- не повторять типовые ошибки

## 1. Рецепты

### Рецепт A: Qwen3MoE, обычный реальный запуск на Zen4

Когда использовать:
- `Qwen3MoE`
- модель помещается в RAM
- основной сценарий это чат, то есть `Mixed (PG)`

Старт:
- `Workload = Mixed (PG)`
- `Threads = 16`
- `Flash Attention = ON`
- `Runtime Repack = AUTO`
- `Merge Up+Gate = OFF`
- `KV Cache K = q8_0`
- `KV Cache V = q8_0`
- `SER = OFF`
- `Hot Expert Budget = 0`

Почему так:
- это текущий validated baseline
- он не переусложнен
- он не подменяет реальные verified выводы экспериментальными флагами

### Рецепт B: gpt-oss-20b, compute-oriented baseline

Когда использовать:
- `gpt-oss-20b`
- цель — хороший mixed throughput на текущем Zen4 host

Старт:
- `Workload = Mixed (PG)`
- `Threads = 16`
- `Flash Attention = ON`
- `Runtime Repack = AUTO`
- `Merge Up+Gate = OFF` ← **критическое: на gpt-oss MXFP4 `-muge` вызывает краш (exit 127), никогда не включать**
- `KV Cache K = q8_0`
- `KV Cache V = q8_0`
- `SER = OFF`

Почему так:
- `gpt-oss-20b` сейчас ближе к compute-oriented линии
- главный стартовый вопрос здесь не huge-model survival, а корректный throughput-first baseline
- `ctk/ctv q8_0` подтверждён нейтральным по скорости, экономит ~50% KV-cache памяти

### Рецепт C: gpt-oss-120b, huge model throughput-first

Когда использовать:
- модель очень большая
- throughput важнее, чем startup/load latency

Старт:
- `Workload = Mixed (PG)`
- `Threads = 16`
- `Flash Attention = ON`
- `Runtime Repack = AUTO`
- `Merge Up+Gate = OFF` ← **на gpt-oss MXFP4 `-muge` вызывает краш (exit 127)**
- `KV Cache K = q8_0`
- `KV Cache V = q8_0`

Что помнить:
- `AUTO` здесь не означает "бесплатно"
- load/startup penalty может быть заметным
- если cold start критичен, обязательно отдельно сравнить с `OFF`
- если baseline уже подтвержден, следующий осмысленный experimental A/B для `120b` — `Prompt Packed QKV back-half`

### Рецепт D: MiniMax M2.5, safe baseline

Когда использовать:
- huge swap-bound `MiniMax`
- нужен стабильный честный старт без лишней изобретательности

Старт:
- `Workload = Mixed (PG)` или `TG-only`, смотря что вы реально проверяете
- `Threads = 16`
- `Flash Attention = ON`
- `Runtime Repack = OFF`
- `Merge Up+Gate = OFF`
- `KV Cache K = q8_0`
- `KV Cache V = q8_0`
- `SER = OFF`
- `Hot Expert Budget = 0`
- `mmap = ON`

Почему так:
- это safest baseline
- он не путает huge-model policy с in-RAM tuning
- при этом на текущем дереве mixed path уже имеет рабочую `auto` branch; просто это не самый консервативный первый старт

### Рецепт E: MiniMax M2.5, controlled experiment

Когда использовать:
- baseline уже получен
- вы хотите адресно проверить hot experts

Менять только одно:
- оставить safe baseline
- сначала оставить `Hot Expert Budget = 0`
- только если вы сознательно воспроизводите MiniMax-исследование, сравнить с одним большим бюджетом отдельно

Что нельзя делать:
- одновременно включить `SER`, изменить `rtr`, поменять потоки и hot budget

Иначе результат будет неинтерпретируемым.

Что важно:
- первый более длинный controlled `rtr=off` run не подтвердил новый default выше legacy `16`
- поэтому большие бюджеты сейчас остаются research-only, а не новым рецептом по умолчанию

## 2. Анти-паттерны

### Анти-паттерн 1: "Я включу все, что похоже на оптимизацию"

Симптом:
- `rtr on`
- `muge on`
- `ser on`
- `mqkv on`
- еще и `hot budget` руками выставлен

Почему это плохо:
- вы смешали validated и experimental knobs
- вы не узнаете, что реально помогло
- для huge моделей такая смесь особенно опасна

Правильнее:
- baseline
- затем один изменяемый параметр за раз

### Анти-паттерн 2: "Настроил TG-only, значит чат тоже ускорился"

Почему это плохо:
- `TG` и `PG` уже показали разное поведение
- реальные пользовательские сессии редко совпадают с чистым decode-only benchmark

Правильнее:
- если целевой сценарий это чат, используйте `Mixed (PG)` как основной workload

### Анти-паттерн 3: "MiniMax тоже MoE, значит возьму профиль от Qwen3MoE"

Почему это плохо:
- `MiniMax` — huge swap-bound special case
- у него другая practical problem: memory pressure, paging, hot experts, runtime policy

Правильнее:
- для `MiniMax` начинать с собственного safe baseline

### Анти-паттерн 4: "У меня 32 потока, значит надо ставить 32"

Почему это плохо:
- физическое количество потоков CPU не равно оптимальному числу inference threads
- у MoE узким местом часто становится bandwidth и contention

Правильнее:
- начинать с `16` на текущем Zen4 dual-CCD baseline
- потом осознанно делать A/B

### Анти-паттерн 5: "AUTO всегда умнее меня"

Почему это плохо:
- `auto` это runtime policy, а не магия
- он может быть очень хорошим стартом
- но он не снимает обязанность понимать family и memory regime

Правильнее:
- считать `auto` хорошим стартом там, где он validated
- и отдельно проверять исключения, прежде всего `MiniMax`

### Анти-паттерн 6: "Если prompt ускорился, то и вся сессия ускорилась"

Почему это плохо:
- некоторые experimental knobs, например `Prompt Packed QKV`, могут заметно ускорять `PP`
- но end-to-end mixed path при этом может почти не измениться

Правильнее:
- смотреть не только на `pp512`, но и на `pg512,128`
- не путать prompt-side gain с общим practical win

### Анти-паттерн 7: "muge — это просто оптимизация, которая не помогла"

Почему это плохо:
- на `gpt-oss MXFP4` флаг `-muge` вызывает **краш** (exit 127), а не просто деградацию
- это не "слабый результат", это fatal failure

Правильнее:
- для `gpt-oss` никогда не включать `-muge`
- не путать "не помогло" с "ломает процесс"

## 3. Как строить свой собственный рецепт

Если у вас новая модель, которой нет в документации, используйте такую схему:

1. Определите family.
2. Определите, помещается ли модель в RAM.
3. Выберите workload.
4. Возьмите conservative baseline.
5. Меняйте только один сильный параметр за раз.
6. Смотрите не только на скорость, но и на startup/load behavior и общую предсказуемость.

## 4. Минимальный набор сравнений

Для нового случая обычно достаточно таких сравнений:

1. `rtr off` vs `auto`
2. `fa off` vs `on` только если вы реально проверяете attention path
3. `TG-only` vs `Mixed (PG)`
4. для `MiniMax`: сначала `Hot Expert Budget = 0`, и только потом один отдельный research-only A/B с большим бюджетом

Если этого еще не сделано, переходить к более экзотическим ручкам рано.

## 5. Что считать хорошим результатом

Хороший результат это не просто "число в одном бенче выросло".

Хороший результат — это когда:
- ускорение воспроизводимо
- понятен workload, на котором оно получено
- нет скрытого обмена вида "стало на 2% быстрее, но запуск вдвое дольше"
- профиль остается объяснимым и переносимым

Это и есть правильная инженерная дисциплина работы с дашбордом.
