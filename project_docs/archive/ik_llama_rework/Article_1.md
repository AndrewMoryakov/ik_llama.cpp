\## Где реально есть потенциал



\### 1. Zen 4 SIMD-оптимизации (самое вкусное для тебя)



7950X поддерживает AVX-512 (а точнее, AVX-512 через VNNI на Zen 4). ik\_llama.cpp имеет оптимизированные ядра деквантизации, но они написаны достаточно обобщённо — под «хороший AVX-512», а не конкретно под Zen 4.



Что можно сделать:

\- \*\*Тюнинг размеров тайлов\*\* в матричных умножениях под L1/L2 кэш Zen 4 (32K L1D, 1M L2 per core). Текущие ядра оптимизированы скорее под Intel-размеры кэшей.

\- \*\*VNNI (Vector Neural Network Instructions)\*\* — Zen 4 поддерживает VPDPBUSD/VPDPWSSD для int8 dot product. Если текущие ядра деквантизации не используют эти инструкции явно (а многие не используют — они делают unpack → FP32 → FMA), то переписав ключевые циклы под VNNI, можно получить заметный прирост на низкобитных квантах.

\- \*\*Prefetch-паттерны\*\* — Zen 4 имеет специфическую модель предсказания prefetch, и правильно расставленные `\_mm\_prefetch` под его stride-паттерн могут дать 5-15% на memory-bound операциях.



\### 2. NUMA / CCD-aware scheduling



7950X имеет два CCD (chiplet core die), каждый с 8 ядрами и своим L3 кэшем (32 МБ). Между CCD идёт Infinity Fabric, и доступ к памяти не полностью uniform — есть небольшая NUMA-подобная асимметрия.



Сейчас ik\_llama.cpp просто распределяет потоки через `--threads N`. Что можно улучшить:

\- \*\*Pinning экспертов по CCD\*\* — при MoE инференсе можно держать определённых экспертов «ближе» к конкретному CCD, минимизируя cross-CCD трафик через IF.

\- \*\*Dual-buffer prefetch\*\* — один CCD начинает prefetch следующего эксперта, пока второй считает текущего.



Реалистичная оценка прироста: \*\*5-10%\*\* на token generation, потенциально больше на prompt processing.



\### 3. MoE-специфичные оптимизации



\*\*Для Qwen3-Next 80B\*\* — модель имеет нестандартную архитектуру с Gated DeltaNet. Это относительно новый тип attention, и его реализация в llama.cpp/ik\_llama.cpp наверняка ещё не полностью оптимизирована:

\- DeltaNet по своей природе рекурентный — его можно оптимизировать через параллельный scan (как в Mamba), что на CPU с AVX-512 может быть значительно быстрее наивной реализации.

\- Гибридный layout 3:1 (три DeltaNet-блока на один attention-блок) означает, что 75% вычислений — линейный attention, который принципиально дешевле в compute и memory. Правильная оптимизация этих блоков даст непропорционально большой эффект.



\*\*Для GPT-OSS 120B\*\* — модель использует alternating dense + banded sparse attention с окном 128 токенов. Banded attention на CPU можно оптимизировать через blocked sparse layout, избегая полных матричных умножений.



\*\*Для обеих моделей\*\* — fused expert execution. Сейчас при top-K routing каждый эксперт обрабатывается последовательно. На CPU с 16 ядрами можно параллелить экспертов по ядрам (4 эксперта для GPT-OSS → 4 ядра на expert, 10 для Qwen3-Next → распределить по ядрам). ik\_llama.cpp частично это делает через fused MoE, но специализация под конкретное количество экспертов может дать прирост.



\### 4. Memory bandwidth оптимизации



Твоё главное узкое место — ~100 ГБ/с dual-channel DDR5-6800. Здесь:

\- \*\*Speculative decoding\*\* без draft-модели — Qwen3-Next нативно поддерживает Multi-Token Prediction (MTP). Если ik\_llama.cpp правильно реализует MTP, можно генерировать 2-4 токена за один forward pass, что при тех же затратах bandwidth даёт кратный прирост effective t/s. Это потенциально \*\*самый большой выигрыш\*\* — удвоение или больше.

\- \*\*Expert caching / prediction\*\* — при MoE не все эксперты нужны на каждом токене. Можно предсказывать, какие эксперты будут вызваны следующими, и делать prefetch заранее, чтобы данные уже были в L3.

\- \*\*Compression в памяти\*\* — некоторые реализации хранят веса в более сжатой форме в RAM и распаковывают в L2/L3 «на лету». При ограниченном bandwidth это выгодно — compute у тебя в избытке (16 ядер × AVX-512), а bandwidth в дефиците.



\## Что вряд ли имеет смысл трогать



\- \*\*Базовую архитектуру GGML\*\* — слишком много кода, слишком мало выхлопа

\- \*\*GPU offload\*\* — у тебя Radeon 780M iGPU, его bandwidth делится с основной DDR5, толку не будет

\- \*\*Тип квантизации\*\* — IQK/Trellis кванты от ikawrakow и так SOTA, улучшать их алгоритмически крайне сложно



\## Реалистичная оценка



| Оптимизация | Сложность | Потенциальный прирост |

|---|---|---|

| MTP/speculative для Qwen3-Next | Высокая | \*\*+50-100%\*\* effective t/s |

| Zen 4 VNNI ядра для IQK квантов | Средняя | \*\*+10-20%\*\* |

| CCD-aware expert pinning | Средняя | \*\*+5-10%\*\* |

| Fused parallel expert execution | Средняя | \*\*+5-15%\*\* |

| Gated DeltaNet parallel scan | Высокая | \*\*+10-20%\*\* (для Qwen3-Next) |

| Prefetch + tiling для Zen 4 | Низкая-средняя | \*\*+5-15%\*\* |



Суммарно, при серьёзной работе, можно реалистично получить \*\*+30-50%\*\* к baseline ik\_llama.cpp, а с работающим MTP для Qwen3-Next — потенциально \*\*удвоение\*\* effective throughput.
