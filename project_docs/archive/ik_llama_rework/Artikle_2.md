Отличный вопрос. Давай разберёмся, что реально можно выжать сверх стандартной сборки с AVX-512.



\## Что уже работает в твоей сборке



С AVX-512 на Zen 4 ты уже получаешь основные SIMD-оптимизации для деквантизации и matmul. Но есть нюансы.



\## Реальные возможности оптимизации



\### 1. NUMA-aware memory access (средний эффект, ~10-20%)



7950X имеет два CCD (chiplet complex dies), каждый со своим L3 cache. Это де-факто NUMA-топология, хоть и на одном сокете. По умолчанию ik\_llama.cpp не знает о расположении данных по CCD.



Что можно сделать:

\- Привязка потоков к конкретным CCD через `numactl` или `taskset` — это не доработка кода, а конфигурация, но эффект заметный

\- Более глубоко: модифицировать аллокатор памяти в ggml, чтобы тензоры эксперта распределялись с учётом NUMA-аффинности потоков. Когда MoE-роутер выбирает экспертов, идеально читать веса из "своего" CCD. Это нетривиальная модификация ggml\_backend\_cpu, но потенциально даёт 10-15% на MoE-моделях.



\### 2. Оптимизация MoE dispatching (средний-высокий эффект)



Это самое перспективное направление для твоего кейса. При CPU-only инференсе MoE-моделей bottleneck — это не compute, а \*\*memory bandwidth\*\*. Каждый токен требует чтения весов выбранных экспертов из RAM.



Что можно попробовать:

\- \*\*Expert prefetching\*\* — когда роутер определил, какие эксперты нужны, начать software prefetch (`\_mm\_prefetch`) весов следующего эксперта, пока текущий обрабатывается. В ik\_llama.cpp fused MoE уже оптимизирован, но prefetch-хинты можно добавить или улучшить

\- \*\*Expert weight reordering\*\* — перераспределить layout экспертов в памяти так, чтобы наиболее часто вызываемые эксперты (shared expert + top-N популярных) лежали в "горячих" страницах и попадали в L3 cache. Для Qwen3-Next с 512 экспертами, где активируется только 10+1, горячий набор может быть относительно стабильным

\- \*\*Batched expert execution\*\* — если несколько токенов в prompt processing идут к одному эксперту, обработать их за один проход, избежав повторного чтения весов. Для PP это может дать ощутимый прирост



\### 3. Специфичные Zen 4 micro-optimizations (низкий-средний эффект, ~5-10%)



AVX-512 на Zen 4 имеет свои особенности:

\- \*\*VNNI (Vector Neural Network Instructions)\*\* — Zen 4 поддерживает AVX512-VNNI, что ускоряет integer dot product. Для IQK квантов с integer-based trellis это может быть критично. Стоит проверить, использует ли ik\_llama.cpp VNNI-инструкции (`\_mm512\_dpbusd\_epi32`) в ядрах деквантизации, и если нет — добавить

\- \*\*Cache line optimization\*\* — Zen 4 имеет 64-byte cache lines. Убедиться, что quant block layout выравнен по ним. Row-interleaved R4 кванты уже частично это делают

\- Zen 4 имеет throughput 2×256-bit на AVX-512 (реализует 512-bit через два 256-bit pipe). Это значит, что иногда 2×AVX2 операции могут быть не медленнее одной AVX-512. Можно попробовать профилирование с `perf stat` чтобы понять, где реально выигрыш от 512-bit



\### 4. Gated DeltaNet kernel для Qwen3-Next (высокий эффект, специфично)



Это самый интересный и самый сложный пункт. Gated DeltaNet — относительно новая архитектура, и CPU-реализация в llama.cpp/ik\_llama.cpp может быть далека от оптимальной.



Linear attention в DeltaNet не требует KV cache в традиционном смысле — вместо этого поддерживается рекуррентное состояние. На CPU это потенциально \*\*быстрее\*\*, чем стандартный attention, но только если реализация эффективна. Стоит посмотреть:

\- Как реализован recurrent state update — можно ли векторизовать через AVX-512

\- Gate-sigmoid можно вычислять через polynomial approximation вместо точного `exp()` — быстрее и достаточно точно для inference



\### 5. DDR5 bandwidth maximization (средний эффект)



На уровне кода:

\- \*\*Huge pages\*\* (`madvise(MADV\_HUGEPAGE)` или transparent huge pages) — снижают TLB misses при работе с большими тензорами. Для моделей 40-60 ГБ в RAM это может дать 5-10%

\- \*\*Memory interleaving\*\* — если у тебя dual channel, убедиться что данные распределены по обоим каналам (`numactl --interleave=all`)

\- Компилировать с `-march=znver4` вместо generic x86-64 — это включит все Zen 4 специфичные оптимизации



\## Что НЕ стоит делать



\- Писать кастомные CUDA/ROCm ядра — у тебя нет дискретного GPU, iGPU (RDNA 2 в 7950X) слишком слаб и с маленьким shared memory

\- Переписывать весь matmul — слишком много работы, лучше точечно оптимизировать горячие пути

\- Пытаться использовать ROCm для iGPU — overhead превысит выигрыш



\## Практический план действий



\*\*Быстрые победы (день работы):\*\*

1\. `numactl --interleave=all` + правильная привязка потоков

2\. Transparent Huge Pages: `echo always > /proc/sys/vm/transparent\_hugepage/enabled`

3\. Пересобрать с `-march=znver4 -O3 -flto`

4\. Профилирование с `perf record` / `perf stat` чтобы найти реальные bottlenecks



\*\*Средняя сложность (неделя):\*\*

5\. Software prefetch для expert weights в fused MoE

6\. Проверить/добавить VNNI-пути в IQK деквантизацию

7\. Expert frequency profiling + hot expert pinning



\*\*Хардкор (месяц+):\*\*

8\. NUMA-aware expert allocation для dual-CCD

9\. Оптимизированный Gated DeltaNet kernel для Zen 4

10\. Custom batched MoE dispatcher с учётом cache hierarchy



Реалистичный суммарный эффект от всего этого — \*\*20-40% поверх стандартной сборки\*\*. Не революция, но для разницы между 12 t/s и 16 t/s это ощутимо в интерактивном использовании.
