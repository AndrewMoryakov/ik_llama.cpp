Хороший вопрос. Давай разберу трезво — что реалистично оптимизировать, что даст ощутимый выигрыш, а что будет потерей времени.



\## Сначала — где ты сейчас упираешься



На CPU-only инференсе с MoE-моделями есть два фундаментальных bottleneck:



\*\*1. Memory bandwidth\*\* — при генерации токенов нужно читать веса активных экспертов из RAM. Твоя DDR5-6200 с tight timings даёт ~90-95 ГБ/с реальной пропускной способности (dual channel). Это физический потолок, софтом не обойти.



\*\*2. Compute\*\* — деквантизация + матричные умножения на CPU. Zen 4 с AVX-512 тут достаточно быстр, и обычно это \*не\* bottleneck при генерации (bandwidth-bound), но может быть bottleneck при prompt processing (compute-bound).



\## Что реалистично оптимизировать



\### Высокий потенциал (5-30% прирост)



\*\*MoE expert prefetching / sparse loading.\*\* Это, пожалуй, самое перспективное направление. Сейчас ik\_llama.cpp при обработке MoE-слоя должен прочитать веса выбранных экспертов из RAM. Но роутер уже знает, какие эксперты будут нужны, \*до\* того как начнётся вычисление. Идея: пока текущий слой считается, начинать prefetch весов экспертов следующего слоя в L3 cache (у тебя 64 МБ на 7950X — это много). Для Qwen3-Next с 3B активных параметров и 48 слоями, каждый слой ~60 МБ активных весов в Q4 — это как раз вписывается в L3.



Сложность реализации: средняя. Нужно вставить `\_\_builtin\_prefetch` или `\_mm\_prefetch` в правильные места в MoE dispatch loop. AI-агент справится с шаблонным кодом, но нужно понимать layout данных в памяти.



\*\*NUMA / CCD-aware memory allocation.\*\* У 7950X два CCD, каждый со своим L3 (32 МБ). По дефолту ik\_llama.cpp может раскидать потоки по обоим CCD неоптимально. Тут два направления:



\- Привязать конкретные слои модели к конкретному CCD через `mbind()` / `numa\_alloc\_onnode()`

\- Чередовать вычисления так, чтобы каждый CCD работал с данными в "своей" части RAM



Это может дать 5-15% на prompt processing. На token generation эффект меньше (bandwidth-bound).



\*\*Оптимизация deквантизации под Zen 4 VNNI.\*\* Zen 4 поддерживает AVX-512 VNNI (Vector Neural Network Instructions) — `VPDPBUSD`, `VPDPWSSD` для быстрых int8/int4 dot products. ik\_llama.cpp использует AVX-512, но не факт что максимально использует VNNI-инструкции для всех типов квантов. Проверь через `objdump` или `perf stat` — если VNNI-инструкции не используются в hot path деквантизации, тут может быть 10-20% на compute-bound фазах.



\### Средний потенциал (5-10%)



\*\*Gated DeltaNet kernels для Qwen3-Next.\*\* Это новая архитектура, и её поддержка в llama.cpp/ik\_llama.cpp свежая. Linear attention в Gated DeltaNet теоретически быстрее стандартного attention, но реализация может быть не оптимизирована под CPU. Если ты найдёшь что CPU kernel для DeltaNet написан наивно — можно выиграть на prompt processing. Но это нишевая оптимизация для одной модели.



\*\*Batched expert computation.\*\* Вместо последовательного вычисления 4 (GPT-OSS) или 10+1 (Qwen3-Next) экспертов, можно организовать батчевую деквантизацию и GEMV. Это лучше утилизирует SIMD-юниты и может снизить overhead на каждого эксперта.



\### Низкий потенциал (или уже сделано)



\*\*AVX-512 сам по себе\*\* — ты уже собрал с ним, основной выигрыш получен.



\*\*Тюнинг thread count\*\* — это делается параметрами, не кодом. Попробуй `--threads 16` (один поток на ядро, без SMT) vs `--threads 8` (один CCD) — результат может удивить.



\*\*Общие compiler flags\*\* — `-march=znver4 -O3 -flto` уже должны быть включены. Если нет — это бесплатные 3-5%.



\## Честная оценка: стоит ли?



Вот главное, о чём нужно подумать:



\*\*Потолок оптимизации ограничен физикой.\*\* При генерации ты bandwidth-bound. Для Qwen3-Next Q5\_K с 3B активных параметров (~6 ГБ на токен) при 95 ГБ/с ты теоретически можешь получить ~15-16 t/s. Если сейчас ты получаешь 12-13, то выжать ещё 2-3 t/s оптимизацией — реалистично. Если уже 14+ — ты близко к потолку.



\*\*AI-агенты для C/C++ SIMD-оптимизаций — непросто.\*\* Claude Opus или Codex хорошо пишут высокоуровневый код, но низкоуровневые AVX-512 intrinsics с учётом Zen 4 microarchitecture — это область где AI-агенты часто ошибаются. Потребуется:

\- Много итераций с benchmarking

\- Понимание того, как устроен memory layout GGML-тензоров в ik\_llama.cpp

\- Умение читать `perf stat` и `perf record` чтобы находить реальные bottleneck'и



\*\*Мой совет:\*\*



1\. \*\*Сначала профилируй.\*\* `perf record -g ./llama-cli ...` + `perf report` покажет, где реально тратится время. Без этого оптимизация — гадание.



2\. \*\*Начни с prefetch для MoE.\*\* Это самая "чистая" оптимизация — не трогаешь core math, только добавляешь hints процессору. Агент может написать прототип, ты проверяешь на бенчмарке.



3\. \*\*Попробуй NUMA-привязку без кода\*\* — через `numactl --cpunodebind=0 --membind=0` проверь, даёт ли привязка к одному CCD прирост. Если да — стоит копать глубже.



4\. \*\*Не трогай core GEMM/GEMV kernels\*\* если ты не готов потратить недели. ikawrakow — опытный оптимизатор, его kernels уже хороши.



По соотношению время/результат, разгон DDR5 с 6200 до стабильных 6400-6600 с tight timings может дать столько же прироста (3-5%), сколько неделя кодинга оптимизаций. Но если тебе интересно как проект и для портфолио — MoE prefetching и NUMA-оптимизация для Zen 4 — это отличная тема, которая может быть полезна и другим пользователям ik\_llama.cpp.
