Хороший вопрос, давайте разложу по полочкам.

  Что произошло

  Первый тест SMT (в bench-cpu-topology.ps1):

  Мы хотели измерить эффект SMT (HyperThreading) — сравнить:
  - 8 потоков, 1 на ядро (без SMT) — маска 0x5555
  - 16 потоков, 2 на ядро (с SMT) — маска 0xFFFF

  Обе маски привязывают к CCD0 (8 ядер). Результат nosmt: gpt-oss PP 78.8 t/s. Но в baseline (тест без привязки) те же 8
   потоков давали 173.7 t/s — в 2.2 раза больше! Мы подумали, что маска сломана.

  Что выяснили

  1. Маска 0x5555 правильная. Проверили через Windows API — топология: ядро N = логические процессоры [2N, 2N+1]. Маска
  корректно выбирает по одному потоку с каждого из 8 ядер CCD0.
  2. Проблема в другом. Когда мы запускаем t=8 без привязки, Windows сам раскидывает потоки по обоим CCD:

  Без привязки (t=8):          С привязкой к CCD0 (t=8):
    CCD0: ~4 потока (32 MB L3)    CCD0: все 8 потоков (32 MB L3)
    CCD1: ~4 потока (32 MB L3)    CCD1: пусто
    Итого L3: 64 MB               Итого L3: 32 MB
    Результат: 170.9 t/s          Результат: 110.9 t/s

  Все 8 ядер работали в обоих случаях. Но без привязки каждый CCD обслуживает только ~4 потока и L3 кеш не переполнен. С
   привязкой к одному CCD — все 8 потоков толкутся в одном L3 на 32 MB, и данные вытесняются.

  Главный вывод

  Дело не в количестве ядер и не в SMT, а в L3 кеше:

  ┌───────────────────┬──────────┬─────────┐
  │      Ресурс       │ Один CCD │ Оба CCD │
  ├───────────────────┼──────────┼─────────┤
  │ Ядра              │ 8        │ 16      │
  ├───────────────────┼──────────┼─────────┤
  │ L3 кеш            │ 32 MB    │ 64 MB   │
  ├───────────────────┼──────────┼─────────┤
  │ PP (gpt-oss, t=8) │ 110.9    │ 170.9   │
  └───────────────────┴──────────┴─────────┘

  Разница в 1.5x — это ровно разница в доступном L3. Модели при inference активно используют кеш для весов и
  промежуточных данных. Половина L3 = половина throughput.

  Бонус: SMT всё-таки измерили корректно

  Сравнив конфиги на одном CCD (одинаковый L3):

  ┌───────────────────────────────────────┬──────────────┬──────────────┐
  │               Сравнение               │      PP      │      TG      │
  ├───────────────────────────────────────┼──────────────┼──────────────┤
  │ 8 ядер × 1 поток vs 4 ядра × 2 потока │ -18% to +12% │ +16% to +90% │
  └───────────────────────────────────────┴──────────────┴──────────────┘

  SMT критически важен для TG — второй поток на ядре занимает pipeline пока первый ждёт данные из RAM. Для PP важнее
  количество ядер, чем SMT.

  Практический итог

  - Не привязывать потоки — OS scheduler оптимален
  - Не отключать SMT — катастрофическое падение производительности
  - PR06 (NUMA pinning) из бэклога можно деприоритизировать — не поможет на этом железе


 Что выяснили

  1. Маска 0x5555 была правильной — топология подтверждена: ядро N = логические [2N, 2N+1]. Маска выбирает по одному
  потоку на ядро.
  2. Причина деградации — не маска, а L3 кеш. Без привязки Windows раскидывает 8 потоков по обоим CCD, давая доступ к 64
   MB L3. С привязкой к CCD0 — только 32 MB.
  3. SMT критически важен:
    - TG: +16-90% (скрывает latency чтения весов из RAM)
    - Без SMT при 16 потоках на 2 CCD: -79% (катастрофа)
  4. Вывод для проекта: PR06 (NUMA pinning) можно деприоритизировать — одна NUMA нода, CCD pinning вредит, OS scheduler
  справляется оптимально. Лучше сосредоточиться на PR03 (expert prefetch) и PR09 (IQK audit).
