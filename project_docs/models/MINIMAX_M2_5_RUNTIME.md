# MiniMax M2.5 В Этом Форке

Дата: 2026-02-28

## Зачем этот документ

`MiniMax M2.5` важен для проекта не как экзотическая модель, а как один из главных примеров huge MoE-модели, которая не помещается в RAM целиком.

Этот документ объясняет простыми словами:

- почему `MiniMax` для нас важен
- чем он сложен
- что уже было сделано в коде именно под него
- что реально дало эффект
- что не сработало
- как сейчас разумно его запускать

## Почему MiniMax важен

На целевом железе проекта:

- CPU-only
- Ryzen 9 7950X
- 96 GB RAM

`MiniMax M2.5` в целевой квантизации существенно больше доступной RAM.

Это делает его полезным тестом для главной идеи форка:

- можно ли заставить очень большую MoE-модель работать не только "формально", но и практически полезно
- если на каждом токене реально активна только малая часть экспертов

Именно поэтому `MiniMax` нельзя считать просто еще одной поддерживаемой архитектурой.

## Почему MiniMax сложнее обычной модели

У `MiniMax` одновременно несколько сложных свойств:

1. Это большая MoE-модель.
- активируются не все веса, а только часть экспертов на токен

2. Она swap-bound на целевом хосте.
- то есть часть модели неизбежно живет не в RAM, а подкачивается

3. У нее есть архитектурные особенности attention path.
- в коде у `MiniMax` есть отдельный build path
- это значит, что не все оптимизации от `Qwen3MoE` или `gpt-oss` можно переносить на нее напрямую

Практический смысл:

- для `MiniMax` важны не только быстрые вычисления
- для `MiniMax` очень важны память, локальность и порядок доступа к данным

## Что уже сделано в коде под MiniMax

Ниже перечислено не "что можно было бы сделать", а то, что уже реально есть в коде форка.

### 1. Batch VM prefetch для активных экспертов

Идея:

- до вычисления экспертов подсказать операционной системе, какие страницы скоро понадобятся
- делать это батчем, а не отдельным системным вызовом на каждого эксперта

Зачем:

- чтобы OS начинала подкачку заранее
- чтобы потоки меньше ждали page fault прямо в момент вычисления

Почему это важно:

- у huge MoE-моделей page fault и подкачка могут убивать throughput сильнее, чем сами вычисления

### 2. Блокировка shared/attention/router тензоров в RAM

Идея:

- удерживать в RAM те тензоры, которые нужны постоянно:
  - attention
  - output
  - norm
  - router
  - другие shared части

Зачем:

- чтобы OS не вытесняла самые часто используемые данные
- чтобы swap в первую очередь касался именно экспертных весов

Практический смысл:

- если attention-веса уйдут в swap, модель начнет тормозить практически везде
- если в swap уходят в основном неактивные эксперты, это для MoE логичнее

### 3. Hot expert tracking после prompt

Идея:

- во время prompt processing собрать статистику, какие эксперты вызываются чаще всего
- после этого статически залочить небольшое количество самых "горячих" экспертов

Зачем:

- часть экспертов активируется заметно чаще других
- если именно их держать в RAM, можно уменьшить количество дорогих page-in во время generation

Это одна из самых содержательных специфичных идей для huge MoE в этом форке.

### 4. Отдельная поддержка архитектуры MiniMax

В коде у `MiniMax` не просто "включена совместимость".

Есть отдельные архитектурные ветки:

- `ik_llama.cpp/src/llama-build-context.cpp`
- `ik_llama.cpp/src/llama-load-tensors.cpp`
- `ik_llama.cpp/src/llama-hparams.cpp`

Это важно, потому что `MiniMax` не идет по той же логике, что некоторые другие модели.

## Что реально дало эффект

Исторически самый понятный и полезный результат на `MiniMax` в проекте был от:

- `hot expert tracking + static lock`

Смысл эффекта:

- после prompt мы получаем грубую карту того, какие эксперты вероятнее будут нужны дальше
- фиксируем небольшой top-N
- не пытаемся динамически "дергать" lock/unlock во время generation

Почему это важно:

- именно static strategy оказалась намного практичнее dynamic strategy

Также полезной идеей оказался:

- batch VM prefetch

Но его важно не путать с per-expert prefetch.

## Что было проверено и отвергнуто

Это не менее важно, чем список успехов.

Ниже то, что уже пробовали и что не оправдало себя:

### 1. Per-expert prefetch

Почему плохо:

- слишком много системных вызовов
- syscall overhead съедает потенциальную пользу

### 2. Dynamic lock/unlock экспертов во время generation

Почему плохо:

- получается lock storm
- слишком много дорогих операций
- generation начинает ждать не вычислений, а работы с памятью и OS

### 3. Deferred commit по TG-статистике

Почему плохо:

- блокировка/подкачка начинается уже во время generation
- это превращается в блокирующий I/O в самом чувствительном участке

### 4. Слепой перенос `rtr`-логики с других MoE

Почему плохо:

- `MiniMax` ведет себя не так же, как `Qwen3MoE` или `gpt-oss`
- для него нельзя просто копировать чужую runtime-policy

## Что сейчас известно по runtime-политике

По текущим локальным данным:

### TG-only

- `rtr=off` сейчас лучший чисто подтвержденный baseline
- `rtr=on` не выглядит катастрофическим и может быть близок к `off`
- старый плохой результат `rtr=auto` оказался связан с policy/reporting problem
- эта проблема уже исправлена, и свежий closeout показал: `off` по-прежнему лучше на `TG-only`

Это важное уточнение, потому что старое грубое утверждение:

- "`rtr` полностью убивает MiniMax"

сейчас уже слишком сильное и неточное.

Правильнее говорить так:

- `off` пока safer baseline
- `on` нужно проверять измерением
- `auto` для `MiniMax` нельзя оценивать по старому сломанному результату
- на свежем fixed-tree closeout `auto` проиграл `off` на `TG-only`, но это уже не означает, что `auto` бесполезен вообще

### Mixed path

Для mixed path картина теперь уже не такая, как раньше.

Свежий closeout `off vs auto` на fixed tree показал:

- `pp32+tg4`
  - `off`: `1.277317`
  - `auto`: `1.316512`

Практический смысл:

- `off` остается safest baseline
- но `auto` уже стал реальным mixed-path кандидатом
- старую формулу "`MiniMax = только off`" теперь нужно считать слишком грубой

Правильнее так:

- если нужен самый консервативный старт, начинайте с `off`
- если вас интересует реальный mixed prompt+generation path, `auto` теперь обязательно стоит сравнивать

Почему это важно:

- у huge swap-bound модели `TG-only` и mixed path действительно могут оптимизироваться по-разному

## Что важно понимать новичку

Если очень упростить:

- обычная оптимизация пытается сделать один токен быстрее
- оптимизация для `MiniMax` пытается сделать так, чтобы huge-модель вообще работала без постоянного развала из-за нехватки RAM

То есть мы оптимизируем не только арифметику, но и:

- поведение памяти
- подкачку
- выбор того, что держать в RAM
- порядок доступа к экспертам

## Что сейчас разумно считать текущим статусом

`MiniMax M2.5` в этом форке сейчас:

- поддерживается в коде
- является важной целевой моделью
- уже имеет несколько специально сделанных под нее optimizations
- но все еще остается research-heavy и сложной runtime-line

То есть это уже не "сырая неподдерживаемая модель", но и не полностью закрытая стабильная история.

## Что делать дальше

Следующие практические шаги для `MiniMax`:

1. Не возвращаться к старому сломанному выводу про `auto`; policy closeout уже закрыт.
2. Следующим шагом идти в:
- expert locality
- paging behavior
- качество hot-expert selection
3. Отдельно перепроверить и при необходимости доработать:
- hot expert policy
- budget hot experts
- swap-bound memory behavior

## Что уточнилось дополнительно

После исправления `rtr auto` был сделан сначала быстрый exploratory check, а затем первый более длинный controlled run по `hot experts`.

Что важно:

1. короткий quick check действительно дал сигнал в сторону `24/32`
2. но первый более длинный controlled `rtr=off` run этот сигнал не подтвердил
3. временная попытка поднять MiniMax default выше legacy `16` была после этого откатана

Практический смысл сейчас такой:

- knob живой и влияет на поведение
- но current safe answer снова такой: оставить runtime default
- более крупные бюджеты пока research-only, а не пользовательская рекомендация
