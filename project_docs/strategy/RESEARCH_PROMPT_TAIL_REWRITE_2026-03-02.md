# Research Line: Prompt-Tail Rewrite - 2026-03-02

## Что это такое

Это отдельная исследовательская линия, не входящая в основной runtime-plan на текущем этапе.

Идея:

- использовать небольшую вспомогательную модель
- не для генерации основного ответа
- а для контролируемой переработки конца prompt
- чтобы prompt tail лучше отражал ближайшую задачу и потенциально давал более полезный сигнал для:
  - `Hot Expert Selection`
  - `Tail Window`
  - раннего `decode`

То есть речь не про "ускорить основную модель маленькой моделью",
а про:

- semantic shaping конца prompt
- ради лучшего `expert locality` и более полезного `prompt -> decode` прогноза

---

## Почему эта идея вообще появилась

Текущая locality-логика для `MiniMax` уже показала:

1. конец prompt может быть полезнее всего prompt целиком для раннего decode
2. `tail-window` уже дал живой signal на `MiniMax mixed-path`

Из этого возникает более сильная спекулятивная идея:

- если не только выбирать экспертов по хвосту prompt,
- но и сделать этот хвост более "semantic-friendly" для раннего decode,
- то можно потенциально улучшить:
  - locality
  - early decode behavior
  - mixed-path stability

---

## Почему это не основной путь

Эта идея **не должна становиться основным направлением раньше runtime/locality work**.

Причины:

1. она меняет не только runtime, но и сам prompt
2. добавляет вторую модель и orchestration
3. может улучшить routing/locality, но ухудшить качество ответа
4. усложняет benchmarking и воспроизводимость

Поэтому это:

- не `Phase 2`
- не baseline work
- а отдельная `research/*` линия

---

## Главная гипотеза

Если последняя часть prompt будет:

1. более короткой
2. более task-focused
3. ближе к ближайшему decode intent

то:

1. `Tail Window` может выбирать более полезный hot set
2. первые decode токены могут лучше попадать в этот hot set
3. mixed-path huge-MoE может стать стабильнее и/или чуть быстрее

---

## Почему это может не сработать

Нужно понимать сильные риски:

### 1. Router не работает по словам напрямую

Router большой модели выбирает экспертов по внутренним представлениям.

Значит:

- маленькая модель может "красиво" переписать хвост prompt,
- но это не гарантирует более полезного expert path в большой модели.

### 2. Потеря смысла prompt

Если маленькая модель начнет:

- сокращать
- перефразировать
- менять структуру

то она может:

- упростить prompt для locality
- но ухудшить ответ

### 3. Дополнительная стоимость

Нужно:

1. держать вторую модель
2. запускать еще один inference
3. добавлять orchestration layer

На практике выигрыш может исчезнуть в этой дополнительной цене.

### 4. Снижение воспроизводимости

Если rewrite не строгий и не детерминированный:

- benchmark becomes noisy
- становится трудно сравнивать baseline и rewrite path

---

## Правильная форма этой идеи

Если вообще ее исследовать, то только в **контролируемом** виде.

Не так:

- "пусть маленькая модель свободно переписывает весь prompt"

А так:

- "пусть маленькая модель строит короткий routing-oriented tail summary"

То есть безопаснее не заменять исходный prompt, а:

1. сохранить исходный prompt как есть
2. добавить в конец короткий structured tail block
3. использовать именно его как локальный predictor для раннего decode

---

## Предпочтительная форма rewrite

Самая безопасная форма сейчас:

### `Prompt Tail Summary`

Короткий добавочный блок в конец prompt, который фиксирует:

1. текущую задачу
2. ближайшее ожидаемое действие модели
3. последние ограничения пользователя
4. актуальный запрос "что делать прямо сейчас"

Примерно:

- не пересказ всего prompt
- а короткая "оперативная сводка" для начала ответа

---

## Ограничения для маленькой модели

Если использовать вспомогательную модель `1B-4B`, для нее должны быть жесткие правила.

### Она не должна

1. менять факты
2. менять инструкции системы
3. выбрасывать критичный контекст
4. вносить новые допущения
5. заменять исходный prompt как единственный источник истины

### Она может

1. сжать последний пользовательский запрос
2. явно сформулировать текущую задачу
3. свернуть хвост диалога в короткий operational summary
4. оставить итог в компактной и предсказуемой форме

---

## Как эту идею правильно валидировать

### Этап 1. Pure research

Проверять только:

1. меняется ли `prompt -> decode` overlap
2. меняется ли `hot expert usefulness`
3. меняется ли `PG` на коротком workload

Без claims о качестве.

### Этап 2. Quality sanity

Если есть runtime signal, проверить:

1. не теряется ли смысл ответа
2. не ломаются ли инструкции
3. не деградирует ли task-following

### Этап 3. Cost accounting

Считать честно:

1. latency маленькой модели
2. общий wall-clock
3. полученный выигрыш большой модели

Если маленькая модель съедает весь выигрыш — идея не проходит.

---

## Что считать успехом

Минимальный успех:

1. ранний decode лучше попадает в hot set
2. `PG` дает небольшой, но честный signal
3. качество не ухудшается очевидно

Хороший успех:

1. итоговый wall-clock mixed-path реально улучшается
2. huge-MoE behavior становится стабильнее
3. rewrite path остается достаточно контролируемым и воспроизводимым

---

## Что считать провалом

Идея должна считаться неудачной, если:

1. rewrite заметно меняет смысл prompt
2. выигрыш только в внутренних counters, но не в wall-clock
3. маленькая модель съедает весь practical benefit
4. результат нестабилен и плохо воспроизводится

---

## Рекомендуемая позиция в roadmap

Эта линия должна жить как:

- `secondary research branch`
- `not mainline`
- `not Phase 2 blocker`

То есть:

1. сначала `Phase 2`: runtime generalization
2. затем `Phase 3`: targeted validation
3. и только параллельно или позже — `prompt-tail rewrite research`

---

## Branch and workflow

Рекомендуемая рабочая ветка:

- `research/prompt-tail-rewrite`

Это сознательно `research/*`, а не `feature/*`, потому что:

1. гипотеза высокая по риску
2. затрагивает semantics prompt, а не только runtime
3. может вообще оказаться тупиковой

---

## Короткий вывод

Это хорошая исследовательская идея.

Но правильно ее понимать так:

- не "следующая главная optimization line"
- а "возможный более дальний semantic/locality experiment"

Ее правильное место:

- рядом с roadmap
- отдельно от mainline runtime work
- с жесткими safety rules для rewrite
