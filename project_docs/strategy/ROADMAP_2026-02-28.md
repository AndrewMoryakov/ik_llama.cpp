# Roadmap

## Что это за документ

Этот документ фиксирует roadmap по развитию `ik_llama` в текущем состоянии проекта.

Он нужен для того, чтобы было понятно:

1. Что можно получить быстро.
2. Что потребует нескольких недель.
3. Что является уже долгим направлением развития.
4. Какие результаты ожидаются на каждом этапе.

Документ специально написан простым языком, чтобы его мог понять не только инженер, давно работающий с `llama.cpp`-подобными проектами, но и человек, который только входит в тему.

---

## Общая идея roadmap

Сейчас проект уже прошел важную часть пути:

- benchmark infrastructure создана
- mixed-path уже исследован
- часть ложных направлений уже отброшена
- появилось понимание, что нужна architecture-specific optimization

Это важно, потому что теперь работа идет не "вслепую", а по уже суженному кругу гипотез.

Но нужно понимать:

- быстрые и дешевые оптимизации почти выбраны
- следующие improvements будут сложнее
- зато они уже имеют больше шансов дать реальный practical effect

---

## Текущий фундаментальный этап: Phase 1

## Что это такое

Это не optimization phase в узком смысле и не новый benchmark-cycle.

`Phase 1` — это фундаментальный semantic layer для experimental knobs и class-based runtime work.

Ее задача:

1. перестать смешивать:
   - где параметр **подходит по механике**
   - где он **реально поддержан текущим runtime**
   - где он **уже validated benchmark-ами**
2. перестать привязывать knobs только к одной модели, если по смыслу они относятся к **классу моделей**
3. сделать так, чтобы следующие фазы:
   - runtime generalization
   - community testing
   - dashboard guidance
   - experimental presets
   опирались на один и тот же vocabulary и source of truth

Иначе проект начинает дрейфовать:

- UI говорит одно
- docs другое
- runtime code третье

---

## Почему Phase 1 нельзя перепрыгивать

Если идти дальше без полного закрытия `Phase 1`, возникает типичная ошибка:

1. knob показывается шире, чем его реально понимает runtime
2. пользователь видит параметр как "подходящий", но не понимает:
   - это уже supported path
   - или только class-compatible idea
3. benchmarking и community A/B начинают собираться поверх разной семантики

Практически это особенно важно для:

- `Hot Expert Selection`
- `Tail Window`
- `Hot Expert Budget`
- `Prompt Packed QKV`
- `Merge QKV`
- `SER`

Это именно те knobs, которые по смыслу часто шире одной family, но по текущему коду могут быть уже.

---

## Что входит в Phase 1

Для каждого experimental knob нужно зафиксировать:

1. `Applicability`
- для какого класса моделей knob вообще имеет смысл по механике

2. `Runtime support today`
- где текущий код реально включает этот path, а не просто принимает параметр

3. `Validation`
- где уже есть benchmark-backed signal

4. `Risk`
- насколько knob безопасен как user-facing experiment

5. `Failure mode`
- что будет, если включить его вне правильного класса/архитектуры

## Статус закрытия Phase 1

`Phase 1` теперь закрыта как semantic/product layer.

Это означает:

1. в dashboard уже есть три независимые оси:
   - applicability
   - runtime support
   - validation
2. это зафиксировано не только в UI-коде, но и в отдельном canonical docs-layer
3. presets и warnings уже опираются на эту модель
4. handoff и roadmap синхронизированы и больше не должны путать:
   - applicability
   - runtime support today
   - validation

Что это не означает:

- runtime generalization уже не сделана автоматически
- knobs пока не стали одинаково supported на всем классе моделей
- Phase 2 не отменяется

---

## Что идет сразу после Phase 1

После полного закрытия `Phase 1` правильный следующий шаг:

### 1. Runtime generalization line

Сначала:

- `Hot Expert Selection`
- `Tail Window`

Цель:

- расширить поддержку от `MiniMax-first` path к классу `MoE / huge-MoE`, где это оправдано

### 2. Затем prompt-packed line

- `Prompt Packed QKV`

Цель:

- двигаться от family-first runtime support к class-based `Split-QKV` support

То есть `Phase 1` не конкурирует с engine work.
Она делает следующий engine work **намного чище**.

---

## Последовательность фаз до цели

Ниже зафиксирована рабочая цепочка фаз, которая сейчас наиболее логично ведет проект к целевому состоянию:

- сильный huge-MoE runtime story
- class-based experimental layer
- воспроизводимые architecture-specific wins
- аккуратный release-facing narrative

Эти фазы не означают "сначала всё документируем, потом только код".
Они нужны, чтобы не ломать семантику проекта и не переоткрывать одни и те же вопросы в каждой новой сессии.

---

## Phase 2. Runtime Generalization

### Смысл

Вынести experimental knobs из узкого `family-first` runtime path туда, где они действительно относятся к классу моделей.

### Текущий статус

`Phase 2` теперь закрыта как bounded runtime-generalization milestone.

Canonical backlog for this phase:

- `project_docs/strategy/PHASE2_KNOB_BACKLOG_2026-03-03.md`

Текущая рабочая ветка:

- `feature/runtime-generalization`

Первый bounded runtime-slice уже реализован:

- commit `b60461556`
- `Runtime: add hot-expert selection capability logging`

Этот шаг:

1. вводит явное различие selection modes:
   - `default`
   - `full-prompt`
   - `tail-window`
2. убирает ложное впечатление, что `Tail Window` одинаково активен для всех compatible-looking families
3. добавляет honest logging for:
   - active path
   - fallback
   - current runtime limitation

Это не завершение `Phase 2`, а ее правильный первый срез.

Второй bounded runtime-slice уже реализован:

- commit `29e4fa3ff`
- `Runtime: generalize hot-expert tail-window to MoE path`

Этот шаг:

1. переносит `Tail Window` от family-only gating к compatible `MoE / huge-MoE` runtime path
2. отделяет:
   - class applicability
   - runtime support
   - validation
3. оставляет validation консервативной:
   - `MiniMax` остается первой подтвержденной линией

Третий bounded runtime-slice уже реализован:

- manual `Prompt Packed QKV` generalized to capability-based `Split-QKV` runtime path

Этот шаг:

1. больше не держит manual prompt-packed path только на `Qwen3MoE / gpt-oss`
2. оставляет `auto` policy family-tuned
3. уже имеет smoke validation на:
   - `Qwen3-1.7B`
   - `Mistral-7B`

Практический смысл:

- `Phase 2` дала три реальные generalized runtime slices:
  - `Hot Expert Selection` capability logging / fallback
  - `Tail Window` on generic `MoE / huge-MoE` hot-expert path
  - `Prompt Packed QKV` manual path on capability-based `Split-QKV`
- `Hot Expert Budget Mult` теперь тоже выведен из env-only слоя в first-class experimental runtime control
- этого достаточно, чтобы считать `Phase 2` practically complete и переходить в `Phase 3` targeted validation

### Первые кандидаты

1. `Hot Expert Selection`
2. `Tail Window`
3. `Prompt Packed QKV`
4. затем следующий decision point по оставшимся class-sensitive knobs

### Цель

Сделать так, чтобы:

- knob был не только показан как class-applicable
- но и реально имел содержательный runtime path для всего целевого класса, где это оправдано

### Правило по defaults

Generalized support не отменяет family-specific defaults.

Если в оригинальном `ik_llama` или в уже подтвержденной линии форка для конкретной family есть рабочий default, его нужно сохранять:

1. family-specific default остается default для этой family
2. class-level manual/experimental support открывается шире для совместимого класса моделей
3. `auto`-policy и family-tuned presets могут оставаться узкими, даже если underlying runtime path уже generalized

Практический смысл:

- расширяем доступность knobs по классу моделей
- не ломаем уже существующие tuned defaults
- не выдаем class-level availability за universal default behavior

### Результат фазы

1. меньше hardcoded family gating
2. больше class-based runtime support
3. меньше silent no-op поведения

## Phase 3. Targeted Validation

### Смысл

Каждый новый generalized knob нельзя сразу считать удачным.
Его надо подтверждать короткими и затем длинными A/B.

### Цель

1. не продвигать ложные defaults
2. отделять:
   - полезную идею
   - neutral/no-op path
   - harmful path

### Приоритетные validation lines

Canonical plan for this phase:

- `project_docs/strategy/PHASE3_VALIDATION_PLAN_2026-03-03.md`

1. `MiniMax`
- locality / paging / hot experts

2. `Qwen3MoE`
- split-QKV / prompt-path experiments

3. `gpt-oss-20b`
- prompt/decode attention-side experiments

### Результат фазы

- benchmark-backed matrix для новых class-based knobs

## Phase 4. Architecture-Specific Optimization

### Смысл

После того как semantic layer и class-based experimental support уже собраны, можно делать новые engine changes без путаницы в том, где knob вообще имеет смысл.

### Основные линии

1. `MiniMax locality / paging`
2. `gpt-oss-20b decode-side path`
3. `Prompt Packed` / attention-side work на split-QKV families

### Цель

Получить уже не только policy win, а реальный code-level performance win.

### Результат фазы

1. один или несколько measurable change-set'ов
2. не только better guidance, но и better runtime

## Параллельная secondary research line

Помимо mainline фаз есть одна отдельная гипотеза, которую не надо путать с текущим основным направлением:

- `prompt-tail rewrite`

Смысл:

- использовать небольшую вспомогательную модель
- не для основного ответа
- а для контролируемой переработки конца prompt
- чтобы улучшить `prompt -> decode` signal для locality-логики huge MoE

Почему это не mainline:

1. это уже не только runtime engineering, но и semantic pre-processing
2. здесь высокий риск ухудшить качество prompt
3. здесь легко потерять воспроизводимость и честность benchmark-ов

Поэтому этот вектор должен жить как:

- `research/*`
- secondary line
- не blocker для `Phase 2-4`

Research docs:

- `project_docs/research/expert-selection/HOT_EXPERTS_RUNTIME_FOUNDATION_2026-03-02.md`
- `project_docs/research/expert-selection/PROMPT_TAIL_REWRITE_2026-03-02.md`
- `project_docs/research/expert-selection/AUX_EXPERT_PREDICTOR_2026-03-02.md`

## Short-Term Roadmap

## Срок

Примерно:

- несколько рабочих итераций
- или несколько дней плотной работы

---

## Цель

Получить следующий содержательный и доказуемый результат.

Это еще не "зрелая система оптимизаций", а следующий реальный шаг, который:

- подтвержден benchmark'ами
- понятен технически
- может лечь в основу следующего engine patch

---

## Основные задачи

### 0. Closeout по huge MiniMax policy

Сейчас лучший short-term benchmark по ROI:

- `MiniMax tg32`: `rtr=off` vs `rtr=auto`
- `MiniMax pg32,4`: `rtr=off` vs `rtr=auto`

Это нужно, чтобы закрыть вопрос:

- стал ли fixed `rtr=auto` реально жизнеспособной веткой для huge `MiniMax`

### 1. Завершить execution maps

Для трех основных линий:

- `Qwen3MoE`
- `gpt-oss-20b`
- `gpt-oss-120b`

Нужно зафиксировать:

- prompt path
- decode path
- mixed path
- attention branch
- MoE/runtime branch
- memory behavior

### 2. Определить первый architecture-specific bottleneck

Выбрать первый реальный target для следующего серьезного patch.

На текущий момент strongest candidate выглядит так:

- `gpt-oss-20b decode-side mixed path`

Отдельно для huge-model линии сохраняется следующий кандидат:

- `MiniMax` expert locality / paging behavior

### 3. Сделать первую decode-side instrumentation phase

Нужно перейти от prompt-side исследований к decode-side mixed-path profiling.

Цель:

- понять, где реально лежит bottleneck в decode tail

### 4. Сделать первый architecture-specific change-set

Это должен быть уже не просто tracing, а первый patch, направленный на:

- `gpt-oss-20b`
- или другой подтвержденный decode-side hot path

### 5. Подтвердить результат benchmark'ами

Минимум:

- `Qwen3MoE`
- `gpt-oss-20b`
- subset для `gpt-oss-120b`

---

## Ожидаемые результаты short-term этапа

К концу short-term этапа хотелось бы получить:

1. Полные execution maps по главным архитектурам.
2. Первый уверенный architecture-specific bottleneck.
3. Первый decode-side optimization patch.
4. Либо подтвержденный win, либо честно зафиксированный отрицательный результат.

---

## Что будет считаться успехом

Успех short-term этапа:

1. Не "еще один документ", а реальный кодовый результат.
2. Появление хотя бы одного нового improvement, который:
   - воспроизводим
   - измерим
   - полезен пользователю

Даже если improvement будет не огромным, но устойчивым, это уже хороший результат.

## Mid-Term Roadmap

## Срок

Примерно:

- несколько недель плотной инженерной работы

---

## Цель

Перейти от отдельных экспериментов к рабочему набору architecture-specific решений.

Это уже этап, на котором форк начинает выглядеть как система, а не как набор отдельных патчей и исследований.

---

## Основные задачи

### 1. Получить отдельные runtime profiles

Сделать понятные и проверенные profiles для:

- `Qwen3MoE`
- `gpt-oss-20b`
- `gpt-oss-120b`

То есть получить не просто benchmark results, а практические режимы использования.

### 2. Сделать несколько подтвержденных optimization change-sets

Нужно уже не один patch, а несколько, например:

- decode-side mixed-path improvement
- memory-policy improvement for huge MoE
- architecture-specific fast path for a validated family

### 3. Закрепить rules по runtime-policy

Например:

- когда нужен `rtr auto`
- когда полезен `on`
- когда нужно быть осторожным с теми или иными optimization paths

### 4. Отдельно стабилизировать huge-model path

Это про:

- `gpt-oss-120b`
- memory pressure
- startup/load cost
- behavior under low-RAM conditions

### 5. Обновить и нормализовать документацию

На этом этапе документация уже должна не просто описывать исследования, а стать:

- runbook
- source of truth
- practical guide for users

### 6. Расширить family-specific presets для dashboard и user-facing runbooks

Это отдельная mid-term задача.

Сейчас дашборд уже различает несколько ключевых линий:

- `Qwen3MoE`
- `gpt-oss`
- `MiniMax M2.5`

Но дальше knowledge layer должна стать шире, не превращаясь в набор случайных эвристик.

Кандидаты на следующие family-specific presets:

1. `DeepSeek MLA family`
- отдельный preset path для моделей с `MLA`
- причина: у них другой attention/KV path, и им нельзя механически наследовать generic MoE guidance

2. `Qwen dense / Qwen3 dense`
- полезный массовый beginner-safe baseline
- нужен, чтобы не смешивать dense Qwen и `Qwen3MoE`

3. `Qwen3-Next / qwen3next`
- уже фигурирует в кодовой базе и планах проекта
- требует отдельной knowledge layer из-за гибридной архитектуры

4. `Mixtral / Mistral-family MoE`
- отдельный "классический" MoE кейс
- полезен как отдельная линия по сравнению с `MiniMax` и `gpt-oss`

5. `GLM4-MoE`
- отдельная архитектурная ветка, которую нельзя автоматически сводить к `Qwen3MoE`

6. `Granite MoE`
- кандидат на отдельный enterprise-oriented preset path

7. `Kimi / Kimi 2.5 / Kimi-K2 family`
- пока не validated line
- но это явный кандидат для будущего huge-model preset layer, если будет практическая работа с квантованными Kimi-моделями

8. `Dense baseline families`
- `Llama`
- `Gemma`
- `Phi`
- `Mistral`
- нужны не ради глубокой architecture-specific optimization, а ради хороших beginner-safe presets

Принцип добавления:

- новый family preset появляется не потому, что архитектура поддерживается в коде
- он появляется только после того, как по нему есть хотя бы safe baseline и понятная runtime-policy

---

## Ожидаемые результаты mid-term этапа

1. Несколько подтвержденных improvements.
2. Отдельные architecture-specific runtime profiles.
3. Более понятные практические пресеты.
4. Более устойчивое поведение больших MoE under memory pressure.
5. Документация, которой реально можно пользоваться без погружения во все исследования с нуля.
6. Более широкий, но все еще контролируемый набор family-specific presets в dashboard.

---

## Что будет считаться успехом

Mid-term этап успешен, если к его завершению можно сказать:

1. У форка есть не только идеи, но и рабочие architecture-specific решения.
2. Есть хотя бы несколько improvements, которые можно честно показать пользователю.
3. Есть понятная линия поддержки:
   - `Qwen3MoE`
   - `gpt-oss-20b`
   - `gpt-oss-120b`

## Long-Term Roadmap

## Срок

Это уже долгий этап.

Речь идет скорее о месяцах, а не о днях или одной-двух неделях.

---

## Цель

Довести `ik_llama` до состояния, где он:

- имеет устойчивые architecture-specific fast paths
- имеет зрелую runtime-policy
- имеет реальные преимущества на целевых MoE under RAM pressure
- остается совместимым с широким набором моделей и квантов

---

## Основные задачи

### 1. Развить architecture-specific execution paths

Не только profiles, но и полноценные fast paths там, где это оправдано.

### 2. Развить новую собственную квантование

Это один из стратегически важных векторов проекта.

Нужно пройти путь от идеи до полного цикла:

- формат
- loader
- kernels/runtime path
- benchmark
- quality validation

### 3. Развить memory-efficiency как отдельную сильную сторону форка

Например:

- лучшее поведение huge MoE в плохих RAM-условиях
- более разумные runtime defaults
- более эффективные layouts и runtime decisions

### 4. Создать устойчивый regression contour

То есть систему, которая позволяет быстро проверять:

- speed regressions
- memory regressions
- behavior regressions

### 5. Поддерживать несколько model families без потери качества

Это особенно важно, потому что форк не должен превращаться в оптимизацию только под одну модель.

## Ожидаемые результаты long-term этапа

1. Зрелая architecture-specific optimization system.
2. Реальные преимущества по performance и efficiency.
3. Поддержка целевых model families без постоянного ручного хаоса.
4. Более сильная собственная техническая идентичность форка.

3. Они сохраняются не только в in-RAM benchmark'ах, но и в stress / low-RAM режимах.
4. Пользователь может этим пользоваться без того, чтобы вручную разбираться во всех внутренних исследованиях проекта.
