# Architecture-Specific Optimization Plan

## Что это за документ

Этот документ описывает следующую большую фазу развития `ik_llama`.

Ее идея простая:

- перестать искать одну "волшебную" оптимизацию для всех моделей сразу
- начать оптимизировать движок под конкретные семейства моделей
- учитывать не только архитектуру модели, но и реальный режим работы

Документ написан так, чтобы его мог понять не только инженер, давно работающий с `llama.cpp`-подобными движками, но и человек, который только входит в тему.

---

## Почему вообще нужен новый подход

На предыдущих шагах уже было подтверждено несколько важных вещей:

1. Разные модели ведут себя по-разному.
2. Один и тот же benchmark не объясняет всю картину.
3. Mixed path (`prompt + generation`, то есть `pg`) нельзя оптимизировать только по результатам `tg` (`generation only`).
4. Оптимизация, которая чуть улучшает prompt-side, не обязательно двигает общий `pg`.

Это значит, что дальше уже недостаточно:

- просто тюнить флаги
- просто менять layout тензоров
- просто искать "универсальный" быстрый путь

Нужно перейти на следующий уровень:

- смотреть, как реально устроена конкретная модель
- смотреть, какой код реально исполняется для этой модели
- оптимизировать именно этот путь

Именно это и называется здесь `architecture-specific optimization`.

---

## Что такое "architecture-specific optimization"

Это подход, при котором мы оптимизируем не "LLM вообще", а конкретное семейство моделей.

Например:

- `Qwen3MoE`
- `gpt-oss`

На практике это означает:

1. Понять, какие ветки кода реально исполняются у этой модели.
2. Понять, где именно находится bottleneck.
3. Делать оптимизации под этот bottleneck, а не под абстрактную среднюю модель.

Это особенно важно для MoE-моделей, потому что у них есть:

- attention path
- routing path
- expert execution
- часто очень разное memory behavior

То есть две MoE-модели могут быть похожи "по названию класса", но на деле вести себя по-разному в runtime.

---

## Почему мы делим работу именно на три линии

На текущем этапе правильнее всего разделить работу на три линии:

1. `Qwen3MoE`
2. `gpt-oss-20b`
3. `gpt-oss-120b`

Это не случайное деление.

Оно основано на уже проведенных измерениях.

### Почему отдельно `Qwen3MoE`

`Qwen3MoE` уже показал себя как хороший representative для:

- in-RAM работы
- prompt-heavy и mixed-path нагрузок
- CPU execution path на Zen4

На нем удобно изучать:

- attention
- prompt path
- `pg`

И на нем уже видно, что некоторые оптимизации работают не так, как на `gpt-oss`.

### Почему отдельно `gpt-oss-20b`

`gpt-oss-20b` тоже является целевой моделью, но ведет себя не так, как `Qwen3MoE`.

Это уже подтверждено.

Он важен как:

- compute-oriented кейс
- in-RAM / near-in-RAM MoE
- представитель семейства `gpt-oss`

На нем хорошо видно:

- decode-side behavior
- mixed-path behavior
- особенности attention/decode для `gpt-oss`

### Почему отдельно `gpt-oss-120b`

`gpt-oss-120b` нужен не потому, что он просто "больше", а потому что это уже другой режим работы.

Это не просто большая версия `20b`.

Это другой performance regime:

- memory pressure
- paging
- startup/load overhead
- swap-bound or near-swap-bound behavior

То есть:

- `20b` показывает compute-path эффективность
- `120b` показывает, выживает ли оптимизация в условиях дефицита RAM

Если оптимизация помогает `20b`, но ломает `120b`, она не может считаться хорошим решением для форка, цель которого как раз и связана с дефицитом RAM и software-side efficiency.

---

## Что именно мы хотим получить в этой фазе

Наша цель не просто "сделать что-нибудь быстрее".

Нам нужно получить:

1. Понимание реального hot path для каждой целевой линии.
2. Отдельные runtime profiles для разных архитектур и режимов.
3. Минимум один реальный engine-level improvement, подтвержденный benchmark'ами.

То есть успех фазы выглядит так:

- не только новые заметки в документации
- не только новые benchmark'и
- а конкретное изменение в коде, которое дает измеримый эффект

---

## Что такое execution map и зачем он нужен

Перед тем как что-то оптимизировать, нужно понять, как модель реально исполняется.

Для этого будет собираться `execution map`.

### Простыми словами

`execution map` это карта реального пути выполнения модели.

Она отвечает на вопросы:

1. Какой путь идет при prompt?
2. Какой путь идет при generation?
3. Чем `pg` отличается от `tg`?
4. Где attention?
5. Где routing?
6. Где experts?
7. Где появляются rebuild / alloc / input prep / compute costs?

### Зачем это нужно

Если не делать execution map, то очень легко начать оптимизировать не тот участок.

Именно это уже частично произошло раньше:

- сначала казалось, что проблема в graph transition
- потом измерения показали, что основная проблема не там

То есть execution map нужен не для красоты, а чтобы не тратить время на ложные гипотезы.

---

## Линия 1: `Qwen3MoE`

## Что это за линия

Это семейство моделей `Qwen3MoE`, которое уже использовалось как один из основных benchmark targets.

### Что она дает нам

Она помогает изучать:

- prompt path
- mixed path
- attention-heavy CPU execution

### Что в ней важно понять

1. Где у `Qwen3MoE` главный bottleneck в `pg`.
2. Насколько сильно упираемся в attention, а насколько в MoE side.
3. Какие оптимизации работают именно для `Qwen3MoE`, а не "вообще".

### Что потенциально можно получить

1. Более быстрый prompt path.
2. Более быстрый mixed path.
3. Отдельный `Qwen3MoE` runtime profile для Zen4.

### Ограничения

Нельзя делать так, чтобы qwen-specific решение ломало:

- `gpt-oss`
- другие модели
- общий fallback path

То есть любые qwen-specific fast paths должны быть additive.

---

## Линия 2: `gpt-oss-20b`

## Что это за линия

Это основной `gpt-oss` compute-oriented case.

Он важен не только как поддерживаемая модель, но и как отдельный объект оптимизации.

### Что она дает нам

Она помогает изучать:

- decode-side hot path
- `pg` behavior
- особенности `gpt-oss` attention/runtime

### Что в ней важно понять

1. Почему `gpt-oss-20b` реагирует на optimization path не так, как `Qwen3MoE`.
2. Где в `gpt-oss` реально находится bottleneck:
   - attention
   - decode tail
   - routing
   - sliding-window path
3. Где выгоднее делать следующий реальный patch.

### Что потенциально можно получить

1. Отдельный `gpt-oss` fast profile для `pg`.
2. Более точный decode-side optimization target.
3. Понимание, какие prompt-side optimizations там уже малополезны.

### Ограничения

Нельзя автоматически переносить выводы с `gpt-oss-20b` на `gpt-oss-120b`.

Это одна family, но не один performance regime.

---

## Линия 3: `gpt-oss-120b`

## Что это за линия

Это memory-pressure / swap-bound representative.

Это критически важно для самого смысла форка, потому что форк как раз и ориентирован на максимальную эффективность в условиях дорогой и дефицитной RAM.

### Что она дает нам

Она помогает понять:

- какие optimizations переживают memory pressure
- какие optimizations хороши только на in-RAM кейсах
- какие runtime policy нужны для реально больших моделей

### Что в ней важно понять

1. Как ведут себя `rtr off/on/auto`.
2. Где реальная цена у startup/load.
3. Какие access patterns к expert tensors вредят при нехватке RAM.
4. Где locality реально влияет на throughput, а где нет.

### Что потенциально можно получить

1. Реальные runtime rules для больших MoE.
2. Более безопасные defaults для memory-stressed кейсов.
3. Отбраковку optimizations, которые красиво смотрятся на `20b`, но не годятся для `120b`.

### Ограничения

1. Такие benchmark'и дорогие по времени.
2. Полную матрицу гонять каждый раз не получится.
3. Нужно держать сокращенный, но содержательный benchmark subset.

---

## Как будет идти работа

Фаза будет идти в несколько последовательных шагов.

## Шаг 1. Построить execution maps

Для каждой линии надо собрать карту:

1. prompt path
2. decode path
3. mixed path
4. attention branch
5. MoE branch
6. memory behavior

### Что это дает

После этого мы будем знать не "примерно где проблема", а конкретно:

- какие ветки кода реально используются
- где реально hot path
- какие изменения вообще имеют смысл

## Шаг 2. Выделить bottleneck для каждой линии

Для каждой линии выбирается:

1. главный bottleneck
2. запасной bottleneck

Не больше.

### Почему это важно

Если пытаться оптимизировать сразу 5 вещей, очень трудно понять:

- что сработало
- что не сработало
- что вызвало регрессию

## Шаг 3. Делать отдельные change-sets

Не один патч "для всех", а отдельные оптимизационные шаги:

1. `Qwen3MoE` change-set
2. `gpt-oss-20b` change-set
3. `gpt-oss-120b` policy/memory-oriented change-set

### Почему это лучше

Так проще:

- атрибутировать эффект
- держать совместимость
- откатывать неудачные идеи

## Шаг 4. Проверять cross-regime regressions

Любой серьезный патч должен проверяться хотя бы на:

1. `Qwen3MoE`
2. `gpt-oss-20b`
3. `gpt-oss-120b` subset

### Почему это обязательно

Потому что иначе легко получить:

- improvement на одном кейсе
- regression на другом

А такой результат для форка неприемлем.

---

## Что именно считается успехом

Фаза считается успешной, если в итоге будут получены:

1. Понятные architecture-specific profiles.
2. Понятные правила, где какой path использовать.
3. Хотя бы один engine-level optimization patch с подтвержденным benchmark effect.

Уточнение:

Нужен именно кодовый результат, а не только хорошие документы.

---

## Что это дает пользователю и проекту

Если фаза будет сделана правильно, она даст:

1. Более понятные пресеты для запуска моделей.
2. Лучшее соответствие между моделью и runtime-параметрами.
3. Более высокую производительность на целевом железе.
4. Меньше ложных универсальных настроек.
5. Более устойчивое поведение больших MoE в условиях дефицита RAM.

---

## Важные ограничения и требования

## 1. Нельзя ломать обратную совместимость

Поддержка должна сохраняться для:

- `Q`
- `IQ`
- `UD-Q`
- существующих CLI режимов

Новые optimization paths должны быть additive.

## 2. Нельзя терять `gpt-oss`

Поддерживаться должны:

- `gpt-oss-20b`
- `gpt-oss-120b`

Причем не формально, а реально, с проверкой на benchmark'ах.

## 3. Нельзя делать выводы по одному benchmark'у

Особенно опасно:

- смотреть только на `tg128`
- делать выводы только по одному smoke run
- переносить выводы с одной модели на все остальные

## 4. Нельзя путать compute-bound и memory-bound cases

Это одна из главных инженерных ошибок, которых нужно избежать.

`20b` и `120b` нужно рассматривать отдельно.

---

## Почему этот план реалистичен

Этот план не начинается "с нуля".

Уже есть:

1. benchmark infrastructure
2. mixed-path traces
3. prompt/decode separation
4. первые architecture-specific observations
5. уже подтвержденные различия между `Qwen3MoE` и `gpt-oss`

То есть следующий шаг не теоретический.

Он естественно вытекает из уже проведенной работы.

---

## Какой практический порядок действий сейчас самый правильный

На текущем этапе правильный порядок такой:

1. Зафиксировать этот план.
2. Построить execution maps для:
   - `Qwen3MoE`
   - `gpt-oss-20b`
   - `gpt-oss-120b`
3. После этого выбрать первый architecture-specific bottleneck.
4. Затем сделать первый targeted patch.
5. Потом снова benchmark + проверка regressions.

---

## Какой первый target выглядит самым сильным сейчас

На основе уже проведенных измерений самым сильным кандидатом сейчас выглядит:

1. `gpt-oss-20b decode-side mixed-path`

Почему:

- prompt-side микровыигрыши уже почти выбраны
- `pg` все больше выглядит decode-dominated
- именно здесь сейчас есть наибольшая вероятность реального end-to-end эффекта

После этого логично идти в:

2. `gpt-oss-120b memory-policy / memory-behavior`
3. затем следующий `Qwen3MoE` fast path

---

## Итог

Главная идея этой фазы:

- не пытаться оптимизировать "все модели сразу одинаково"
- а строить точечные оптимизации по реальной архитектуре модели и реальному режиму исполнения

Это более сложный путь, но именно он дает шанс на настоящий прирост производительности, а не на случайные микровыигрыши.

Для `ik_llama` это особенно важно, потому что цель форка не просто "быть немного быстрее", а:

- выдерживать дефицит RAM
- сохранять поддержку разных форматов
- выжимать максимум из CPU execution, в том числе на Zen4

Именно поэтому architecture-specific optimization является не побочной идеей, а логическим следующим этапом развития проекта.
