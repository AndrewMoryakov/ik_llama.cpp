# Цель И Область Работы Форка

Дата: 2026-02-28

## Коротко

Главная цель этого форка не просто "ускорить ik_llama вообще".

Главная цель:

- сделать CPU-only инференс больших MoE-моделей более практичным на реальном домашнем или рабочем железе
- в том числе в самом важном для проекта режиме: когда модель целиком не помещается в RAM
- получить не абстрактные "оптимизации ради оптимизаций", а измеримые улучшения:
  - выше скорость генерации
  - лучшее поведение в mixed path
  - меньше деградация при нехватке RAM
  - понятные и воспроизводимые runtime-профили

Целевое железо в текущем цикле работ:

- AMD Ryzen 9 7950X
- 96 GB RAM
- CPU-only
- Zen4 как основная точка оптимизации

## Почему фокус именно такой

Для больших MoE-моделей проблема не сводится к обычному "ускорить matmul".

Основная практическая проблема такая:

- модель может быть заметно больше доступной RAM
- но на каждом токене реально используется только часть экспертов
- значит задача уже не только вычислительная, но и memory/runtime-ориентированная

Проще говоря:

- модель огромная
- активная часть модели на токене намного меньше
- если правильно организовать доступ к данным, можно получить полезный inference даже там, где "по размеру модель не влезает"

Именно поэтому для этого форка важны:

- swap-bound сценарии
- MoE routing
- locality
- подкачка страниц
- порядок доступа к экспертам
- runtime-policy для моделей больше RAM

## Что это значит на практике

Форк оптимизируется не только под:

- `Qwen3MoE`
- `gpt-oss`

но и под тяжелые huge-model сценарии, где модель не помещается в RAM, например:

- `MiniMax M2.5`

Это важное уточнение.

`MiniMax` не является "случайной поддерживаемой моделью".

Наоборот:

- это один из ключевых stress-case кейсов проекта
- именно такие модели проверяют, есть ли у форка реальная ценность в условиях дефицита RAM

## Что считается успехом

Хороший результат в рамках этого форка это не только "выше токенов в секунду на маленькой модели".

Хороший результат это:

1. Модель, которая больше объема RAM, работает предсказуемо и не разваливается по throughput.
2. Есть понятные режимы `off/on/auto` и другие runtime-параметры для разных классов моделей.
3. Улучшения подтверждены benchmark-ами, а не интуицией.
4. Есть понятное разделение:
- что уже stable
- что пока experimental

## Что не является целью

Не является основной целью:

- полировать все архитектуры одинаково
- делать оптимизации "потому что можем"
- ориентироваться только на in-RAM кейсы
- делать выводы только по одному benchmark-режиму вроде `tg128`

## Что сейчас в активной области работы

1. Большие MoE-модели, включая режимы больше RAM.
2. Runtime-policy для swap-bound сценариев.
3. `MiniMax M2.5` как отдельная performance line.
4. `Qwen3MoE` и `gpt-oss` как отдельные architecture-specific линии.
5. Новые собственные квантизации, но без отказа от поддержки `UD-Q / IQ / Q`.

## Как это читать новичку

Если коротко:

- обычный inference думает: "модель должна влезть в RAM"
- этот форк пытается сделать practical inference и тогда, когда модель целиком в RAM не помещается
- для этого приходится оптимизировать не только вычисления, но и память, подкачку, локальность и порядок доступа к экспертам

Именно это и есть центральная идея текущего этапа форка.
