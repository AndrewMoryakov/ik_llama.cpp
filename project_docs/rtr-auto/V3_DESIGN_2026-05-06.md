# V3 design for `-rtr auto` policy

Date: 2026-05-06
Status: Design frozen, awaiting maintainer answer on mmap-coupling
question before implementation.

This doc captures the refined v3 design after two review passes and
maintainer feedback on PR #1738. It supersedes the path-A patch on
`pr/rtr-auto-mode-v2` (which was insufficient per maintainer's
2026-05-06 comment about repackable bytes vs full GGUF size).

## Background

PR #1738 currently submitted at commit `0115ace21` with v1 logic
(total RAM, `n_gpu_layers > 0` skip, bool return).

dmaivel's feedback (2026-05-05 post and edit):
- `-rtr auto` did not fire on his real `-ngl 99 -ot exps=CPU` setup
  with a 120 GiB MoE on 64 GiB RAM.
- Total RAM is the wrong metric; available memory is the right one.
- Uncertainty should default to disable, not to keep.

Maintainer's reply (2026-05-06 05:57 UTC):
- Available RAM, yes.
- Take into account tensor overrides and quantization types.
- Use only the tensors that will get repacked when computing
  required memory.
- Mentioned the offline `llama-quantize --repack` workflow as an
  alternative for users with low-RAM systems.

Our reply posted 2026-05-06 11:45 UTC:
- Confirmed direction.
- Flagged loader's `use_mmap=false` coupling: KEEP based on
  repackable bytes alone can still cause swap when total
  CPU-resident bytes exceed available memory.
- Proposed AND-check total CPU-resident bytes as a secondary gate.
- Disclosed CPU-only environment, cannot runtime-validate the
  GPU+override case.

Awaiting maintainer's answer on the mmap-coupling question before
writing code.

## Two review passes ran 2026-05-06

The design below is what passed both passes. Each numbered point
below traces back to a specific finding from the second pass.

## Decision enum (final)

```cpp
enum class llama_rtr_auto_decision {
    KEEP,    // repackable bytes > 0 AND fits AND total fits
    DISABLE, // doesn't fit OR zero repackable on CPU
    UNKNOWN, // probe failure, OS query failure, or complex mode
             // (merge_qkv, merge_up_gate_exps, --fit, ncmoe > 0,
             // n_gpu_layers > 0 without matching override on this
             // tensor)
};
```

`NOT_APPLICABLE` from earlier drafts is removed. The case "no
repackable tensors on CPU" collapses into DISABLE: keeping
`repack_tensors=true` in that case is strictly worse than disabling
it (forces `use_mmap=false` for no actual repack work).

## Caller dispatch

```cpp
switch (decision) {
    case KEEP:
        // Auto kept repack on; force mmap=false for the repack pass
        params.use_mmap = false;
        LLAMA_LOG_INFO("--run-time-repack auto: keeping repack enabled");
        break;
    case DISABLE:
        params.repack_tensors = false;
        // Leave mmap as user/default (true unless --no-mmap)
        LLAMA_LOG_INFO("--run-time-repack auto: disabled (%s)", reason);
        break;
    case UNKNOWN:
        params.repack_tensors = false;
        // Leave mmap as user/default
        LLAMA_LOG_WARN("--run-time-repack auto: disabled (uncertainty: %s)", reason);
        break;
}
```

UNKNOWN is safety-first: disable repack, keep mmap, WARN log so the
user notices.

## Placement resolver

```cpp
enum class Placement { CPU, GPU, UNKNOWN };

Placement resolve_placement(const ggml_tensor * t,
                            const llama_model_params & params) {
    // 1. Complex modes the probe cannot accurately simulate.
    if (params.fit)                  return Placement::UNKNOWN;
    if (params.merge_qkv)            return Placement::UNKNOWN;
    if (params.merge_up_gate_exps)   return Placement::UNKNOWN;

    // 2. Check tensor_buft_overrides. First match wins,
    //    std::regex_search (substring), host buft normalizes to CPU.
    if (params.tensor_buft_overrides) {
        for (const auto * o = params.tensor_buft_overrides;
             o->pattern != nullptr; ++o) {
            std::regex re(o->pattern);
            if (std::regex_search(t->name, re)) {
                return ggml_backend_buft_is_host(o->buft)
                    ? Placement::CPU
                    : Placement::GPU;
            }
        }
    }

    // 3. ncmoe distribution depends on per-layer device assignment
    //    we do not have at probe time. Conservative.
    if (params.ncmoe > 0) return Placement::UNKNOWN;

    // 4. No override matched. Default by n_gpu_layers.
    if (params.n_gpu_layers == 0) return Placement::CPU;

    // 5. n_gpu_layers > 0 without an override on this specific tensor.
    //    Some tensors (token embedding, output) stay on CPU regardless,
    //    others go to GPU; exact mapping depends on split_mode and
    //    device list which we do not have. Conservative.
    return Placement::UNKNOWN;
}
```

Notes:

- The `regex_search` choice mirrors `src/llama-load-tensors.cpp:418`
  exactly. Using `regex_match` would miss substring matches the
  loader does pick up.
- `ggml_backend_buft_is_host` normalization mirrors line 228 of the
  same file, where the loader normalizes any host buft to the
  default CPU buft.
- The first-match-wins behavior mirrors the early `break` in the
  loader's match loop.
- ncmoe split-layer mode (load-tensors.cpp:242-310) walks layers
  from `n_layer-1` to 0 with per-device counts and iterative
  refinement. Reproducing this at probe time without
  `model.default_layer_device` is impractical.
- `model.devices` is populated inside `llama_model_load` itself, not
  at probe time. We have only `params.devices` (string),
  `params.split_mode`, and `params.n_gpu_layers` available. Without
  the resolved device list, exact split placement of layers cannot
  be simulated. The UNKNOWN cascade on `n_gpu_layers > 0` without
  matching override is the conservative response to this gap.

## Policy walk

```cpp
uint64_t cpu_repackable_bytes = 0;
uint64_t cpu_total_bytes = 0;
bool any_unknown = false;

const uint64_t avail_ram = llama_get_available_ram_bytes();
if (avail_ram == 0) {
    reason = "could not query available memory";
    return UNKNOWN;
}

try {
    llama_model_loader probe(...); // metadata-only
    llama_model probe_model;
    probe_model.hparams.vocab_only = params.vocab_only;
    llm_load_arch(probe, probe_model);
    llm_load_hparams(probe, probe_model);

    for (const auto & w : probe.weights) {
        const ggml_tensor * t = w.tensor;
        Placement p = resolve_placement(t, params);

        if (p == Placement::UNKNOWN) {
            any_unknown = true;
            continue;
        }
        if (p == Placement::GPU) continue;

        // CPU
        cpu_total_bytes += ggml_nbytes(t);

        // Forbidden tensors (token_embd.weight) do not get repacked
        if (std::string(t->name) == "token_embd.weight") continue;

        // Type filter via canonical iqk API
        if (iqk_repacked_type(t) == (int)t->type) continue;

        cpu_repackable_bytes += ggml_nbytes(t);
    }
} catch (const std::exception & e) {
    reason = format("probe failed (%s)", e.what());
    return UNKNOWN;
}

// Final decision
const uint64_t threshold = avail_ram - avail_ram / 10; // 90%

if (any_unknown) {
    reason = "complex mode or partial GPU offload not simulated";
    return UNKNOWN;
}

if (cpu_repackable_bytes == 0) {
    reason = "no repackable tensors on CPU";
    return DISABLE;
}

if (cpu_repackable_bytes > threshold) {
    reason = format("repackable bytes %.1f GiB > 90%% of available memory %.1f GiB",
                    cpu_repackable_bytes / 1073741824.0,
                    avail_ram / 1073741824.0);
    return DISABLE;
}

if (cpu_total_bytes > threshold) {
    reason = format("CPU-resident bytes %.1f GiB > 90%% of available memory %.1f GiB (mmap forced off when repack on)",
                    cpu_total_bytes / 1073741824.0,
                    avail_ram / 1073741824.0);
    return DISABLE;
}

return KEEP;
```

## Why the secondary gate exists (sharp rationale)

The secondary `cpu_total_bytes > threshold` gate is **not about
"repack work cost"**. It is about the loader's existing global
coupling: when `repack_tensors=true`, the loader sets
`use_mmap=false` for the entire load, not just for the repackable
tensors. This means every tensor (repackable or not) ends up in
anonymous memory. If total CPU-resident bytes exceed available
memory, the load swaps regardless of how cheap the repack pass
itself would have been.

Primary gate (repackable bytes) answers the maintainer's question:
"is the repack work cost manageable?" Secondary gate answers a
different but unavoidable question given the existing loader:
"will the load itself fit when mmap is forced off?"

Both gates use the same 90% threshold and either trip leads to
DISABLE. The secondary gate goes away cleanly if and when the
loader is changed to load only repackable tensors into anonymous
memory while keeping non-repackable tensors mmap'd (see "Approach
D phase 2" below).

## Walk-through of representative cases

| Case                                                  | Decision  | Why |
|-------------------------------------------------------|-----------|-----|
| Qwen3-30B Q4_K_M in-RAM                               | KEEP      | All Q4_K (repackable), fits in available |
| gpt-oss-20b/120b MXFP4 in-RAM                         | KEEP      | MXFP4 not repackable, but attention layers (BF16/F16/Q8_0) are repackable on AVX512BF16 build; small repackable, large total, both fit |
| MiniMax UD-Q5_K_XL 151 GiB on 96 GiB                  | DISABLE   | Repackable bytes > available; primary gate |
| Qwen3.5-397B-A17B 6 shards 219 GiB on 96 GiB          | DISABLE   | Repackable bytes > available; multi-shard accumulation works |
| Qwen3.5-27B Q8_0 dense, fits                          | KEEP      | Q8_0 has Q8_0_R8 repack, fits; dense is no longer NOT_APPLICABLE |
| Hypothetical 70B F16 dense on 50 GiB, no AVX512BF16   | DISABLE   | F16 not repackable in this build → repackable_bytes=0 → DISABLE (avoids forced mmap=off on swap) |
| dmaivel `-ngl 99 -ot exps=CPU` Qwen3.5-397B 64 GiB    | DISABLE   | UNKNOWN cascade (non-expert tensors hit n_gpu_layers > 0 default) → safety-first DISABLE |
| Any model with `--fit`                                | UNKNOWN   | fit-generated overrides materialize after our policy point |
| Any model with `-mqkv` or `-muge`                     | UNKNOWN   | merge creates synthetic tensors not in probe.weights |
| Any model with `-ncmoe N`                             | UNKNOWN   | ncmoe split-layer requires per-layer device assignment |

UNKNOWN cascade defaults to DISABLE per the safety-first rule.

## Critical caveat: mmap can still be forced off independently

**Discovered in third review pass 2026-05-06.**

Even when v3 returns DISABLE and the policy block leaves
`use_mmap` alone, the loader has multiple independent code paths
that force `use_mmap_buffer = false` later in `create_tensors()`.
This means our promise "DISABLE preserves mmap" is conditional, not
absolute.

The non-RTR mmap killers in `src/llama-load-tensors.cpp`:

1. **Line 4113-4115**: when any `-ot pattern=CPU` override matches
   (`has_buft_overrides=true`), and the env var
   `GGML_CUDA_NO_PINNED` is not set, the loader forces
   `use_mmap_buffer = false`. This bypasses our policy entirely.
   - dmaivel's reproducer has `GGML_CUDA_NO_PINNED=1` set, which
     skips this branch, so his case is unaffected.
   - Other users running CUDA builds with `-ot exps=CPU` and
     without `GGML_CUDA_NO_PINNED` will hit this and lose mmap
     even after our DISABLE.

2. **`merge_qkv` macro** (lines 521, 651, 1185): when merging
   creates a new synthetic tensor, mmap is forced off. Affected by
   `--merge-qkv` flag.

3. **`create_std_ffn_exps`** (lines 664, 769): similar synthetic
   tensor creation. Affected by `--merge-up-gate-experts`.

4. **Old MoE format** (line 549): when GGUF stores experts as
   separate per-expert tensors instead of unified expert blocks,
   loader merges them and forces mmap off. Mostly historical, but
   some older quants may still have this layout.

5. **Per-arch conditions** (line 717 and similar): some
   architectures have specific tensors that disable mmap.

What v3 can and cannot do:

- v3 closes the **repack-induced** mmap-off path: `repack_tensors`
  no longer forces mmap off when our policy says DISABLE. Good.
- v3 cannot single-handedly close paths 1-5 above. They are
  pre-existing loader behavior independent of repack.
- v3 can detect path 1 at probe time (`has_buft_overrides` plus
  env var check) and emit a more specific log so the user sees the
  real cause if their load still swaps.

Implementation plan for path 1 detection:

```cpp
// At probe time, after resolving placement
bool has_cpu_override = false;
if (params.tensor_buft_overrides) {
    for (const auto * o = params.tensor_buft_overrides;
         o->pattern != nullptr; ++o) {
        if (ggml_backend_buft_is_host(o->buft)) {
            has_cpu_override = true;
            break;
        }
    }
}
const bool no_pinned_env = std::getenv("GGML_CUDA_NO_PINNED") != nullptr;
const bool loader_will_force_mmap_off =
    has_cpu_override && !no_pinned_env;
```

When `loader_will_force_mmap_off` is true, log additionally on
DISABLE:

```
--run-time-repack auto: disabled (...).
note: tensor_buft_overrides will also force mmap off in the loader
(GGML_CUDA_NO_PINNED is not set). To preserve mmap streaming on
this load, set GGML_CUDA_NO_PINNED=1.
```

Paths 2-4 are detected via params (`merge_qkv`, `merge_up_gate_exps`)
or by examining tensor name patterns at probe time. v3 already
treats `merge_qkv` and `merge_up_gate_exps` as UNKNOWN (path D), so
those paths are handled by the safety-first cascade.

Path 5 (per-arch) is too varied to enumerate at probe time. Accept
as known limitation, document.

## View-tensor accounting clarification

probe.weights iterates GGUF base tensors. Runtime
`model.tensors_by_name` includes view tensors created by
`create_tensor_as_view()` (e.g., individual experts viewed into a
merged block tensor in old MoE format). These views share data with
the underlying base tensor; their bytes are not separate.

Our byte accounting via `ggml_nbytes(probe.weights[i].tensor)` over
GGUF base tensors gives the correct total CPU-resident memory
without double-counting through views.

The merge case (line 549) creates a NEW base tensor that is not in
GGUF and forces mmap off. Our v3 cannot account for this synthetic
tensor, but the loader has already decided to force mmap off in
that case anyway, so memory pressure is high regardless of our
policy. Marking these arch families as UNKNOWN at the placement
resolver level is the correct response (already in design via the
merge_* flags).

## Side effects vs v2 (current dev)

1. Dense models with repackable types now go through full policy
   instead of the `is_moe || is_minimax_m2` shortcut. Q8_0 dense
   that fits gets KEEP (correct, dense Q8_0 benefits from Q8_0_R8).
   Dense that doesn't fit gets DISABLE (correct, prevents the
   silent swap-thrash that v2 has on huge dense models).
2. Multi-shard accumulation already works via `probe.weights`
   collecting all shard tensors. No change needed.
3. Probe overhead is the same as v1/v2 (same metadata-only load).
4. Logs gain a third type: WARN on UNKNOWN. INFO on KEEP and DISABLE
   stays.
5. The `LLM_ARCH_MINIMAX_M2` special-case in our local fork is
   dropped in the upstream PR (was never in upstream tree). For
   the local v2-gated experimental version on `feature/rtr-auto-v2`
   we may keep it; for the upstream port we will not.

## Caveats to surface in PR description

1. CPU-only validation environment. The `-ngl 99 -ot exps=CPU`
   case dmaivel reported is logic-reasoned in the placement
   resolver but not runtime-validated locally. Maintainer or other
   GPU reviewers needed.
2. UNKNOWN cascade is conservative by design. Users with
   `--merge-qkv`, `--merge-up-gate-experts`, `--fit`, `--n-cpu-moe`,
   or partial GPU offload without explicit `-ot` overrides will see
   the auto policy disable repack with a WARN. They can opt back in
   via `-rtr 1` if they know their setup fits.
3. `iqk_repacked_type()` returns build-specific results. F16/BF16
   only repackable when `__AVX512BF16__` is defined. Same model on
   different binaries can get different decisions.
4. Threshold is 90% of available memory. For workloads with large
   KV cache or large batch, this margin may be insufficient.
   Consistent with v1/v2.
5. **DISABLE does not always preserve mmap.** Five independent
   loader paths can force `use_mmap=false` regardless of our
   decision: has_buft_overrides without `GGML_CUDA_NO_PINNED`,
   merge_qkv, merge_up_gate_exps, old MoE expert layout,
   per-arch conditions. v3 detects has_buft_overrides at probe
   time and adds an actionable note in the log. Other paths are
   handled by the UNKNOWN cascade (merge_qkv / merge_up_gate_exps
   already trigger UNKNOWN).

## Open question for the maintainer

The mmap-coupling question from our 2026-05-06 reply:

The loader forces `use_mmap=false` whenever `repack_tensors=true`
(`src/llama-model-loader.cpp:585`). This means a KEEP decision
based on repackable bytes alone can still trigger swap when total
CPU-resident bytes exceed available memory. The secondary
total-bytes gate above addresses this defensively. Three possible
maintainer answers:

1. **Keep both gates as designed** — accept the conservative
   secondary check. Implementation as above.
2. **Drop the secondary gate, repackable-bytes only** — strictly
   matches maintainer's wording. Caveat: huge dense models in
   `-rtr auto` mode can still silently swap. We document this and
   leave it to the user to know their setup.
3. **Decouple repack from mmap=off in a follow-up** — bigger
   change to the loader. We then do not need a secondary gate
   because mmap streaming handles non-repackable bytes regardless.

We lean to (1). If maintainer says (2), drop the second
`if (cpu_total_bytes > threshold)` check and expand the PR
description with the documented caveat. If (3), wait for that
loader refactor or do it ourselves as a separate prep PR.

## Fourth-pass investigation 2026-05-06

After the third pass surfaced the mmap-independence issue, ran a
fresh independent investigation looking at the whole problem rather
than incremental fixes. The findings did not invalidate the design
above, but they reframed the strategy and surfaced one concrete
refinement.

### Reframing: what does v3 actually achieve?

Our design rests on the chain
`DISABLE repack → mmap preserved → swap thrash prevented`. Pass 3
showed this chain breaks in five places (the loader has five
independent code paths that force `use_mmap=false` regardless of
our policy). The most impactful is path 1 (`has_buft_overrides`
without `GGML_CUDA_NO_PINNED`), which fires on the same dmaivel-
class workload our auto policy targets, and dmaivel only avoided it
because his reproducer happened to set the env var.

This means v3 is a safety net **with holes**. Not a reason to drop
the work, but a reason to scope it honestly: v3 closes one of the
five mmap-off paths and detects another with actionable advice.
The other three are pre-existing loader behavior outside this PR's
scope.

### Why path 1 exists (semantics check)

Verified the rationale for path 1's `mmap=false` forcing. This is
not a loader bug, it is a CUDA performance trade-off:

- CUDA pinned (page-locked) memory speeds up CPU to GPU transfers.
- mmap'd pages cannot be pinned (they are already mapped, not
  anonymous).
- To use pinned memory, CPU-side tensors must be in anonymous
  memory, so `use_mmap=false`.
- `GGML_CUDA_NO_PINNED=1` opts out of pinned memory, so mmap can
  stay.

For a swap-bound user the right trade is obvious: set
`GGML_CUDA_NO_PINNED=1`, accept slower transfers, get a working
load. v3's actionable note in the DISABLE log delivers exactly
this advice. Not a fix, but useful diagnosis.

### Strategic options considered

| Approach | Pros | Cons |
|---|---|---|
| A. Status quo v3 (closes only repack-induced path) | Targeted, minimal | Does not guarantee mmap |
| B. Fix the loader directly (decouple paths 1-2 too) | Real fix, root cause | Bigger surface, maintainer did not ask for this |
| C. Document and warn only, no auto-policy | Simplest | Silent failure not prevented |
| D. Two-phase: ship v3 now, propose mmap decoupling later | Incremental, easier reviews, builds maintainer trust | dmaivel-class users still vulnerable until phase 2 ships |

Recommended: **D**. Approach A was already implicit in the v3 plan,
but D names the second phase explicitly so it is not lost.

### Approach D phase 2: selective per-tensor buffer allocation

The right long-term fix for the root coupling is not a
boolean `if (repack_tensors) use_mmap=false`. It is per-tensor
buffer allocation:

- For each CPU-resident tensor whose type is in the repack map
  (per `iqk_repacked_type`), allocate **anonymous/writable**
  memory and load the bytes from the file into it. The repack
  pass then operates in place on this anonymous memory, exactly
  as it does today.
- For each CPU-resident tensor whose type is **not** in the
  repack map, keep the current mmap'd path. Read-only streaming
  through page cache, no working-set inflation.

Effect: the global `use_mmap=false` coupling on `repack_tensors=true`
disappears. Only the bytes that actually need to be modified live
in anonymous memory. Non-repackable tensors do not pay the swap
cost.

This is a loader-side change, not a policy change. It belongs in a
separate PR after #1738 lands. When it does:

- The secondary `cpu_total_bytes > threshold` gate in v3 becomes
  redundant (only `cpu_repackable_bytes` matters, matching the
  maintainer's original framing).
- Path 1 (`has_buft_overrides` plus missing `GGML_CUDA_NO_PINNED`)
  remains independent. It is still worth addressing separately,
  but it is a different code path with a different rationale
  (CUDA pinned memory, not repack).

Scope estimate for phase 2: medium. Touches `llama-load-tensors.cpp`
and possibly the buffer-type dispatch. Needs careful smoke on at
least one Linux build.

We do not propose phase 2 in #1738. We surface it in the PR
description as a planned follow-up so the maintainer sees the
direction we are aiming at long-term.

### Algorithmic refinements

R1. **Order UNKNOWN exits before the probe**, not after. The probe
is the expensive step; if `--fit`, `--merge-qkv`,
`--merge-up-gate-experts`, or `--ncmoe > 0` is set, our
placement-aware accounting is unreliable, so skip the probe and
return UNKNOWN immediately.

R2. **Pre-compile regexes once.** `std::regex(o->pattern)` per
tensor is slow on probe.weights with hundreds of tensors. Build
the compiled regex list once before the walk, iterate over the
compiled set per tensor.

R3. **Catch `std::regex_error` explicitly.** A user-supplied bad
regex pattern in `-ot pattern=...` should produce a clear UNKNOWN
reason rather than a generic "probe failed". The general
`std::exception` catch already covers it, but a dedicated catch
gives a clearer diagnostic.

R4. **Detect path 1 and append advice.** Compute
`has_cpu_override && !no_pinned_env` once during regex
pre-compile. If true, append `"; note: tensor_buft_overrides will
also force mmap=false unless GGML_CUDA_NO_PINNED=1"` to the
reason string at decision time. Decision itself is not changed.

R5. **KV cache and compute-graph budget.** Punted in v3. Could
subtract estimated KV bytes from available before the threshold
check. Useful for users with large `-c` or batch. Defer to v4 if
maintainer asks.

R6. **90% threshold.** Consistent with v1/v2. Comfortable for
`-c 4096`, possibly tight for `-c 32768`. Document caveat.

R7. **Tensor with `n_gpu_layers > 0` and no override match.** Two
options: assume GPU (optimistic, may underestimate CPU bytes and
KEEP when DISABLE is right) or UNKNOWN (conservative, may DISABLE
when KEEP would have been fine). Going with UNKNOWN. The
optimistic alternative would silently misallocate the budget and
leak mmap=false.

### Risk re-assessment after fourth pass

| Risk class | Exposure | Mitigation |
|---|---|---|
| Critical bug (crash, wrong output) | Low. The policy block reads probe state and writes only `params.repack_tensors` and `params.use_mmap`, both already mutable. | None needed. |
| False DISABLE (loses up to 15% PP from v2 KEEP) | Medium. UNKNOWN cascade is intentionally aggressive. | User can opt back via `-rtr 1` if they know their setup fits. |
| False KEEP (swap thrash) | Low. Secondary total-bytes gate catches huge totals. Path 1 silent failure remains the residual risk. | NO_PINNED hint in the DISABLE log lets the user diagnose if it still happens. |
| Behavior change for dense Q8_0 with `-rtr auto` | Strictly better than v2's NOT_APPLICABLE. | Document in PR description. |
| Multi-shard correctness | Verified across three review passes plus real probe data on Qwen3.5-397B 6-shard. | None additional. |
| Cross-platform compile (Linux/macOS) | Code compiles on Windows; Linux cgroup walker and macOS host_statistics64 paths are not runtime-tested locally. | Disclosed in PR description; rely on maintainer or community to runtime-test. |
| GPU plus override edge cases | Cannot runtime-validate locally; CPU-only environment. | Disclosed in our 2026-05-06 reply to maintainer. |

Net assessment: v3 plan is **sound but bounded**. Solving one
mmap-off path properly and detecting another with actionable
advice is honest scope.
