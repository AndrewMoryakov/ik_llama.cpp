# Dashboard Roadmap

Дата: 2026-02-28

## Зачем нужен этот документ

Этот документ фиксирует отдельный roadmap именно по dashboard.

Он нужен, чтобы не потерять важную идею:

- dashboard должен быть не только launcher'ом
- dashboard должен оставаться понятным учебным интерфейсом
- при этом knowledge layer должна расти не хаотично, а только на основе измерений и validated runtime-policy

## Текущее состояние

На текущем этапе dashboard уже умеет:

- определять базовые model families
- различать `in-RAM` и `swap-bound`
- учитывать workload: `PP`, `TG`, `PG`
- различать `validated` и `experimental`
- давать практические стартовые рекомендации для:
  - `Qwen3MoE`
  - `gpt-oss`
  - `MiniMax M2.5`

Это уже хороший фундамент.

Но knowledge layer пока покрывает не все семьи моделей, которые могут быть важны для проекта и пользователей.

## Главный принцип развития dashboard

Новый preset или новая family-specific recommendation добавляется только если есть:

1. понятный safe baseline
2. понятная runtime-policy
3. хотя бы минимальная benchmark-опора
4. понятное объяснение для новичка

Если хотя бы одного из этих пунктов нет, family можно поддерживать в коде, но не нужно делать вид, что dashboard уже знает, как ее правильно запускать.

## Ближайший backlog по family-specific presets

### 1. DeepSeek MLA family

Почему важно:
- это отдельный attention/KV path
- для таких моделей обычные generic MoE правила могут быть неполными или неверными

Что нужно для добавления:
- safe baseline
- отдельная формулировка по `MLA`
- базовые warnings для `PP/TG/PG`

### 2. Qwen dense / Qwen3 dense

Почему важно:
- это популярные и понятные пользователю модели
- нужно разводить dense Qwen и `Qwen3MoE`

Что даст:
- хороший beginner-safe baseline
- меньше ложных рекомендаций MoE-only параметров

### 3. Qwen3-Next / qwen3next

Почему важно:
- уже фигурирует в кодовой и проектной базе
- архитектура гибридная, значит generic profile здесь особенно опасен

Что нужно:
- отдельный bring-up и хотя бы базовая runtime-policy

### 4. Mixtral / Mistral-family MoE

Почему важно:
- это отдельный тип "классического" MoE
- полезно как отдельная линия по сравнению с `MiniMax` и `gpt-oss`

### 5. GLM4-MoE

Почему важно:
- отдельная архитектурная ветка в коде
- нельзя автоматически сводить к `Qwen3MoE`

### 6. Granite MoE

Почему важно:
- кандидат на отдельный enterprise-oriented preset path

### 7. Kimi / Kimi 2.5 / Kimi-K2 family

Почему важно:
- это вероятный future huge-model target
- если по нему начнется практическая работа, dashboard должен получить отдельную knowledge layer

Важно:
- пока это не validated family для dashboard recommendations
- сейчас это backlog, а не текущая публичная рекомендация

### 8. Dense baseline families

Кандидаты:
- `Llama`
- `Gemma`
- `Phi`
- `Mistral`

Почему важно:
- не ради глубокой architecture-specific optimization
- а ради безопасных и понятных presets для новичков

## Что не надо делать

Не надо:

1. добавлять family preset просто потому, что архитектура поддерживается в коде
2. делать вид, что одна recommendation подходит всем MoE
3. переносить huge-model guidance на in-RAM dense модели
4. перегружать dashboard редкими knobs без user-facing explanation

## Что будет считаться хорошим развитием dashboard

Хорошее развитие dashboard — это не больше кнопок.

Хорошее развитие dashboard — это когда:
- больше реальных model families получают safe baseline
- рекомендации остаются объяснимыми
- новичок меньше ошибается
- experimental knobs не маскируются под validated defaults

## Следующий правильный порядок

1. закрепить текущие линии:
- `Qwen3MoE`
- `gpt-oss`
- `MiniMax`

2. расширять presets только после benchmark-backed policy

3. приоритетными кандидатами считать:
- `DeepSeek MLA family`
- `Qwen dense / Qwen3 dense`
- `Qwen3-Next`
- `Mixtral / Mistral-family MoE`
- `Kimi family` как future huge-model line
