# Hybrid Source Research — подмена тензоров из safetensors в GGUF

Дата: 2026-03-22

---

## Идея

Вместо скачивания полного BF16 (~450 GiB), скачать **отдельные safetensor-файлы** с наиболее чувствительными тензорами (edge-эксперты, attention) и подставить их как источник при квантизации. Это даст BF16-качество для критичных слоёв без скачивания всей модели.

---

## Исследование: структура оригинала на HuggingFace

### Формат хранения

Оригинал MiniMax M2.5 на HuggingFace (`MiniMaxAI/MiniMax-M2.5`) хранится в **FP8 (F8_E4M3)**, не BF16:
- Каждый тензор `*.weight` сопровождается `*.weight_scale_inv` (блочный scale-фактор)
- Это значит: даже "оригинал" уже квантован до 8 бит
- BF16 можно получить путём деквантизации FP8 × scale, но это не lossless BF16

### Структура файлов

- 126 safetensor-шардов, ~2.5 GiB каждый
- Маппинг тензоров → файлов в `model.safetensors.index.json`
- Каждый эксперт хранится **отдельно**: `model.layers.{L}.block_sparse_moe.experts.{E}.w1.weight`
- При конвертации в GGUF 256 экспертов **сливаются** в один тензор: `blk.{L}.ffn_gate_exps` (через `torch.stack`)

### Имена тензоров: safetensors → GGUF

| Safetensors | GGUF |
|-------------|------|
| `model.layers.{L}.self_attn.q_proj.weight` | `blk.{L}.attn_q.weight` |
| `model.layers.{L}.self_attn.k_proj.weight` | `blk.{L}.attn_k.weight` |
| `model.layers.{L}.self_attn.v_proj.weight` | `blk.{L}.attn_v.weight` |
| `model.layers.{L}.self_attn.o_proj.weight` | `blk.{L}.attn_output.weight` |
| `model.layers.{L}.block_sparse_moe.experts.{E}.w1.weight` | `blk.{L}.ffn_gate_exps.weight` (stacked) |
| `model.layers.{L}.block_sparse_moe.experts.{E}.w2.weight` | `blk.{L}.ffn_down_exps.weight` (stacked) |
| `model.layers.{L}.block_sparse_moe.experts.{E}.w3.weight` | `blk.{L}.ffn_up_exps.weight` (stacked) |
| `model.embed_tokens.weight` | `token_embd.weight` |
| `model.norm.weight` | `output_norm.weight` |

### Размер edge-слоёв в safetensors

Один слой MoE (256 экспертов, 3 тензора) в FP8:
- w1 (gate): 256 × 3072 × 1536 × 1 byte ≈ 1.2 GiB
- w2 (down): 256 × 1536 × 3072 × 1 byte ≈ 1.2 GiB
- w3 (up): 256 × 3072 × 1536 × 1 byte ≈ 1.2 GiB
- Всего на слой: ~3.6 GiB

Edge (4 слоя): ~14.4 GiB
Bridge (6 слоёв): ~21.6 GiB
Attention (все 62 слоя): ~2.4 GiB (маленькие)

## Анализ осуществимости

### Вариант A: Скачать edge safetensors → конвертировать → квантовать отдельно

**Процесс:**
1. Скачать `model.safetensors.index.json` (~10 МБ)
2. Определить, в каких шардах лежат edge-слои (0-3, 58-61)
3. Скачать только эти шарды (~14–20 GiB)
4. Деквантизовать FP8 → BF16 (через scale_inv)
5. Конвертировать edge-тензоры в GGUF формат
6. Квантовать edge из BF16, core из Q8_0

**Проблема:** `llama-quantize` принимает один входной файл, не умеет брать часть тензоров из одного источника и часть из другого.

**Решение:** Нужен кастомный скрипт, который:
- Читает Q8_0 GGUF как базу
- Для указанных тензоров читает BF16 из safetensors
- Квантует каждый тензор из правильного источника
- Записывает итоговый GGUF

### Вариант B: Создать гибридный GGUF-источник

**Процесс:**
1. Скачать edge-шарды из safetensors
2. Деквантизовать FP8 → BF16
3. Подменить edge-тензоры в Q8_0 GGUF на BF16 версии
4. Квантовать из этого гибрида обычным `llama-quantize`

**Проблема:** Нужен инструмент для подмены тензоров в GGUF. `gguf-py` умеет читать и писать GGUF, но подмена in-place не тривиальна для 90+ GiB файлов.

### Вариант C: Двухпроходная квантизация

**Процесс:**
1. Квантовать core (слои 5-56) из Q8_0 как сейчас
2. Квантовать edge (слои 0-4, 57-61) из BF16 (полученного из safetensors)
3. Слить два результата в один GGUF

**Проблема:** `llama-quantize` не поддерживает частичную квантизацию по слоям. Нужна доработка или скрипт.

## Критическое ограничение

**Оригинал на HuggingFace — FP8, не BF16.**

Это значит:
- Скачивая safetensors, мы получаем FP8 + scale_inv
- Деквантизация FP8 → BF16 даёт **приблизительный** BF16, не оригинальный
- Цепочка: оригинал BF16 → FP8 (потеря) → деквант BF16 (не восстановлено) → наш квант
- Это **лучше**, чем Q8_0 → наш квант, но **не равно** оригинальному BF16

### Есть ли чистый BF16?

Нужно проверить, публиковал ли кто-то BF16 версию MiniMax M2.5:
- Unsloth Q8_0 — уже квантован
- MiniMaxAI оригинал — FP8
- Возможно есть BF16 конвертация от сообщества

## Инструменты в проекте

### Что есть
- `convert_hf_to_gguf.py` — конвертер safetensors → GGUF (полная конвертация)
- `gguf-py` (gguf_reader.py, gguf_writer.py) — чтение/запись GGUF из Python
- `llama-gguf-split` — split/merge GGUF файлов
- `llama-quantize` — квантизация с `--custom-q`

### Что нужно создать

**Скрипт `hybrid_quantize.py`:**
1. Принимает: base GGUF (Q8_0), список safetensor-файлов, маппинг "какие тензоры брать откуда"
2. Для edge-тензоров: читает safetensors → деквантует FP8→BF16 → квантует в целевой тип (iq5_k, iq4_xs)
3. Для остальных тензоров: читает из Q8_0 GGUF → квантует как обычно
4. Записывает итоговый GGUF

Ориентировочная сложность: средняя (1-2 дня разработки). Основная часть — правильная деквантизация FP8 и маппинг имён тензоров.

## Оценка выигрыша

### Сколько скачивать

| Что | Шардов | Размер | Покрывает |
|-----|--------|--------|-----------|
| Edge (0-3, 58-61) | ~8-12 | ~20-30 GiB | 4+4 слоя, самые чувствительные |
| Edge + Bridge | ~16-20 | ~40-50 GiB | 4+6+6+4 слоя |
| Вся модель (BF16) | 126 | ~320 GiB | Всё |

### Ожидаемый эффект на PPL

- Edge-слои это 8 из 62 слоёв (~13%)
- Но они квантуются в iq5_k/iq4_xs, не iq3_ks — ошибка на них и так меньше
- Основной bottleneck — core в iq3_ks (52 слоя)
- **Ожидаемый эффект: малый** (edge и так квантуются точнее)

Гибридный подход был бы **значительно полезнее**, если бы мы подменяли core-тензоры (iq3_ks из BF16 вместо iq3_ks из Q8_0). Но core — это 52 слоя × 3.6 GiB = ~187 GiB, что сравнимо с полной загрузкой.

## Вывод

### Стоит ли делать?

**Для edge-слоёв — малый эффект, не оправдывает сложность.** Edge и так в iq5_k/iq4_xs, разница FP8→iq5_k vs Q8_0→iq5_k минимальна.

**Для core-слоёв — нужно скачивать почти всё**, что сводит преимущество на нет.

### Когда это имеет смысл

1. Если появится **чистый BF16** MiniMax M2.5 (не FP8) — тогда разница FP8→iq3_ks vs BF16→iq3_ks может быть существенной
2. Если нужен **per-layer AB-тест** — квантовать один слой из BF16, другой из Q8_0, замерить PPL-дельту на этом слое
3. Для **исследования double quantization loss** — измерить, сколько именно теряется при Q8_0→iq3_ks vs BF16→iq3_ks

### Рекомендация (первоначальная)

Приоритетнее:
1. Перераспределить бюджет (attention↓ experts↑) — бесплатно, быстро
2. Свой imatrix из Q8_0 — средняя сложность, потенциально полезно
3. Гибридный подход — высокая сложность, неясный выигрыш

Гибрид стоит реализовать **только после** того, как исчерпаны более простые направления, или если появится BF16 оригинал.

## Обновление: найден BF16 источник (2026-03-22)

### Полный BF16 MiniMax M2.5

**Репозиторий:** `PrimeIntellect/MiniMax-M2.5-bf16` (huggingface.co)

- 125 safetensor-шардов
- **~619 GiB** суммарно
- 1,880 скачиваний, активный репозиторий
- Полная деквантизация FP8 → BF16

### Происхождение весов

```
Обучение (BF16) → MiniMaxAI публикация (FP8) → PrimeIntellect конвертация (BF16)
```

BF16 от PrimeIntellect — это **деквантизованный FP8**, не оригинальные обучающие веса. Потеря при FP8 → BF16 уже произошла и не восстановлена. Но для квантизации это **значительно лучший** источник, чем Q8_0:

- FP8 (8 бит, floating point) → BF16 деквант — потеря минимальная, FP8 спроектирован для обратимости
- Q8_0 (8 бит, integer, блочный) → уже внёс свою блочную ошибку квантизации

### Сравнение цепочек квантизации

| Цепочка | Шагов квантизации | Ожидаемое качество |
|---------|-------------------|-------------------|
| BF16(train) → iq3_ks | 1 (идеал, недоступен) | Лучшее |
| BF16(train) → FP8 → BF16(deq) → iq3_ks | 1 реальный (FP8↔BF16 почти lossless) | Очень хорошее |
| BF16(train) → FP8 → BF16(deq) → Q8_0 → iq3_ks | 2 (текущий путь) | Хуже |

### Размеры шардов

| Файлы | Размер | Содержимое |
|-------|--------|-----------|
| model-00000 — model-00019 | ~2.4 GiB каждый | Ранние слои (смешанные тензоры) |
| model-00020 — model-00123 | ~4.9 GiB каждый | Основная масса (expert FFN) |
| model-00124 | ~1.2 GiB | Финальный шард |
| **Итого** | **~619 GiB** | Полная модель |

### Варианты использования BF16

#### Вариант 1: Полная загрузка и конвертация (максимальное качество)

```
Скачать все 619 GiB → convert_hf_to_gguf.py → BF16 GGUF → llama-quantize → наш квант
```

**Плюсы:** Лучшее возможное качество.
**Минусы:** Нужно ~619 GiB для safetensors + ~450 GiB для BF16 GGUF + ~92 GiB для кванта = ~1.1 TB свободного места.

#### Вариант 2: Потоковая конвертация (средне)

`convert_hf_to_gguf.py` может работать с HuggingFace напрямую, скачивая шарды по мере необходимости и не держа все в памяти одновременно. Но на выходе всё равно нужен полный GGUF.

```
huggingface-cli download (по шардам) → convert_hf_to_gguf.py → GGUF → quantize
```

**Плюсы:** Не нужно хранить все 619 GiB одновременно.
**Минусы:** Нужно место для промежуточного GGUF (~450 GiB).

#### Вариант 3: Гибридная подмена (выборочно)

Скачать только шарды с edge-слоями (~20–30 GiB), подменить edge-тензоры в Q8_0 GGUF на BF16 версии, квантовать.

**Плюсы:** Минимум трафика.
**Минусы:** Нужен кастомный скрипт, и основной bottleneck (core iq3_ks) не затронут.

#### Вариант 4: Прямая квантизация из HuggingFace (оптимальный)

Если `convert_hf_to_gguf.py` может записывать промежуточный результат по частям и сразу квантовать — можно обойтись минимумом места:

```
HF safetensors (потоково) → convert + quantize в один проход → 92 GiB квант
```

**Плюсы:** Нужно только ~92 GiB для результата.
**Минусы:** Нестандартный pipeline, нужна доработка. `convert_hf_to_gguf.py` и `llama-quantize` — отдельные инструменты, их нужно объединить.

### Оценка дискового пространства

Текущее свободное место:
- Z: ~40 GiB
- D: ~112 GiB (после удаления v2)

Ни на одном диске не хватает для полного BF16 (619 GiB) или промежуточного GGUF (450 GiB).

Возможные решения:
- **Внешний диск / NAS** — если есть
- **Потоковая конвертация** — скачивать шарды по одному, конвертировать, удалять
- **Только edge-шарды** (~20–30 GiB) — влезет на D:

### Обновлённая рекомендация

С учётом найденного BF16 приоритеты меняются:

| # | Действие | Эффект | Требования |
|---|----------|--------|-----------|
| 1 | Перераспределить бюджет (attn↓ experts↑) | Средний | 0 GiB, 1 час |
| 2 | Квантовать из BF16 (PrimeIntellect) | **Высокий** | ~500+ GiB места или потоковый pipeline |
| 3 | Свой imatrix из Q8_0 | Средний | Время (часы-сутки) |
| 4 | Гибрид: edge из BF16, core из Q8_0 | Малый | ~30 GiB + кастомный скрипт |

**Ключевой вопрос:** есть ли возможность временно получить ~500+ GiB дискового пространства? Если да — вариант 2 (полная конвертация из BF16) даст максимальный эффект на PPL. Если нет — вариант 1 (перераспределение бюджета) остаётся приоритетным как бесплатный и быстрый.
