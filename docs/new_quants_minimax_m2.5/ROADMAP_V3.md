# Roadmap v3 — развитие кастомной квантизации MiniMax M2.5

Дата: 2026-03-21

## Текущее состояние

### Поколение 1 (v1): Варианты A–F
Грубая геометрия зон, симметричная квантизация down и gate/up.
- 5 рецептов (A, C, D, E, F), 87–110 GiB
- Описаны в `project_docs/strategy/TASK.md`

### Поколение 2 (v2): Tapered-RAM, Deep-Taper 115
Ступенчатый taper + асимметрия down vs gate/up в каждой зоне.
- 2 рецепта, 91–115 GiB
- Описаны в `minimax_quant_recipes.md`
- Tapered-RAM собран и протестирован (работает, ~3.5–4.1 t/s на TG)

### Известный баг в v2
Базовый тип IQ3_KS применяется к attention-тензорам: `attn_q` → iq3_ks, `attn_output` → q5_K. Рецепт подразумевает attention в Q8_0, но custom-q правила покрывают только expert FFN. Качество attention деградировано сильнее, чем задумано.

## Поколение 3 (v3): планируемые улучшения

### v3.1 — Исправление attention [приоритет: критический]

**Проблема:** custom-q правила не покрывают attention-тензоры, и базовый ftype IQ3_KS квантует их агрессивнее, чем задумано.

**Решение:** добавить явные правила для attention:
```
blk\..*\.attn_q=q8_0
blk\..*\.attn_k=q8_0
blk\..*\.attn_v=q8_0
blk\..*\.attn_output=q8_0
```

**Ожидаемый эффект:** заметное улучшение качества при минимальном росте размера (~1–2 GiB). Attention маленький относительно expert FFN, но критичен для качества.

**Сложность:** низкая — только добавить правила в скрипты и переквантовать.

---

### v3.2 — Imatrix-guided зоны [приоритет: высокий]

**Проблема:** границы зон (edge=4 слоя, bridge=6 и т.д.) выбраны по интуиции, а не по данным.

**Решение:** сгенерировать imatrix для MiniMax M2.5 и использовать данные о чувствительности каждого слоя для оптимального размещения границ зон.

**Что нужно:**
1. Сгенерировать imatrix: `llama-imatrix -m model.gguf -f calibration_text.txt -o imatrix.dat`
2. Проанализировать per-layer sensitivity
3. Скорректировать границы зон по данным
4. Использовать imatrix при квантизации для лучшего распределения точности внутри каждого тензора

**Ожидаемый эффект:** высокий — и лучшие зоны, и лучшее внутритензорное распределение точности.

**Сложность:** средняя — генерация imatrix для huge-модели долгая, нужен калибровочный текст.

**Блокер:** скачанный imatrix от Unsloth (470 МБ, `imatrix_unsloth.gguf_file`) оказался в несовместимом формате. Нужен либо конвертер, либо собственная генерация.

---

### v3.3 — Per-layer taper (непрерывный) [приоритет: средний]

**Проблема:** даже 5 зон — это ступеньки. Реальная чувствительность слоёв скорее плавная кривая.

**Решение:** индивидуальный тип для каждого из 62 слоёв. Плавная кривая от iq5_k на краях до iq3_ks в центре, с промежуточными iq4_k, iq4_xs на конкретных слоях.

**Как реализовать:** `--custom-q` поддерживает regex по номеру слоя — нужно 62×3 = 186 правил. Можно автогенерировать скриптом.

**Ожидаемый эффект:** средний — улучшение поверх ступенчатого taper, но не революция.

**Сложность:** низкая (автогенерация правил), но нужны данные из v3.2 для выбора типов.

---

### v3.4 — Асимметричные края [приоритет: средний]

**Проблема:** ранние edge (0–3) и поздние edge (58–61) квантуются одинаково, хотя выполняют разные функции.

**Решение:** попробовать:
- Вариант A: поздние edge точнее (финализация вывода критичнее)
- Вариант B: ранние edge точнее (ошибка на входе накапливается через 60 блоков)

**Как проверить:** квантовать два варианта, сравнить PPL и живое качество.

**Ожидаемый эффект:** малый–средний.

**Сложность:** низкая.

---

### v3.5 — Дифференциация attention-тензоров [приоритет: низкий]

**Проблема:** все attention-тензоры одним типом (q8_0), но они разного размера и важности.

**Решение:** варьировать тип по тензорам:
- `attn_q` (6144 dim, самый большой) → можно попробовать iq5_k (экономия ~1 GiB)
- `attn_k`, `attn_v` (1024 dim, маленькие) → оставить q8_0
- `attn_output` (6144×3072) → варьировать

**Ожидаемый эффект:** малый. Освободившиеся байты можно перенаправить на эксперты.

**Сложность:** низкая.

---

### v3.6 — Per-expert квантизация [приоритет: исследование]

**Проблема:** все 256 экспертов в блоке квантуются одинаково, но не все одинаково важны. Часто используемые эксперты влияют на качество сильнее.

**Решение:** собрать статистику использования экспертов (из imatrix или runtime hot-expert trace), квантовать часто используемых точнее, редких — агрессивнее.

**Блокер:** текущий `--custom-q` не поддерживает per-expert гранулярность (только per-tensor по имени, а все 256 экспертов хранятся в одном тензоре `ffn_down_exps`). Нужна доработка инструмента или другой подход.

**Ожидаемый эффект:** потенциально высокий, но требует исследования.

**Сложность:** высокая.

---

### v3.7 — Ко-дизайн с runtime [приоритет: исследование]

**Идея:** оптимизировать квантизацию не изолированно, а вместе с runtime-флагами:
- Если SER обрезает слабых экспертов (<5% вес) → этих экспертов можно квантовать грубее, т.к. их вклад мал
- Если hot experts залочены → часто используемых экспертов стоит квантовать точнее, они будут в RAM постоянно
- Если модель in-RAM (Tapered-RAM с c=4096) → можно позволить чуть больший размер за счёт лучшего качества

**Ожидаемый эффект:** зависит от связки. Потенциально это "следующий уровень" после per-layer taper.

**Сложность:** высокая — нужна обратная связь между runtime-статистикой и квантизацией.

## Статус v4 — Deep-Taper (2026-03-22)

v4 реализован и протестирован:
- 5-зонная лестница, бюджет перераспределён от attention к экспертам
- Файл: `D:\MiniMax-M2.5-DeepTaper-v4.gguf` (114 GiB, BPW 4.26)
- **PPL = 9.42 ± 0.23** (64 чанка)
- **Скорость:** ~4 t/s (dashboard, после прогрева), swap ~19 GiB

Рецепт v4:
```
Edge      [0-3, 58-61]   (8):  down=iq5_k,  gate/up=iq5_k
Bridge    [4-7, 54-57]   (8):  down=iq5_k,  gate/up=iq4_xs
Mid-sens  [8-13, 48-53]  (12): down=iq5_k,  gate/up=iq4_xs
Mid-high  [14-17, 44-47] (8):  down=iq5_k,  gate/up=iq3_ks
Core      [18-43]        (26): down=iq4_xs,  gate/up=iq3_ks
Attention: attn_q=iq5_k, attn_k/v=q8_0, attn_output=q5_K
Embeddings/Output: q8_0, Router: f32
```

Вывод: +0.8 BPW (3.46→4.26) при +22 GiB дал лишь -0.28 PPL (9.70→9.42). Потолок PPL ~9.4 определяется **двойной квантизацией** (Q8_0 источник), а не BPW.

## Поколение 5 (v5): пробить потолок PPL

### Главный рычаг: устранить двойную квантизацию

Текущий путь: BF16(train) → FP8(MiniMax) → **Q8_0(Unsloth)** → наш квант
Целевой путь: BF16(train) → FP8(MiniMax) → наш квант

Ожидаемое улучшение: **PPL -0.3 — -0.5** (с 9.42 до ~8.9–9.2)

Два варианта источника:

| Путь | Скачать | Качество |
|------|---------|----------|
| FP8 оригинал (`MiniMaxAI/MiniMax-M2.5`) | ~320 GiB | FP8→квант (лучше Q8_0→квант) |
| BF16 деквант (`PrimeIntellect/MiniMax-M2.5-bf16`) | ~619 GiB | deq(FP8)→квант (≈ FP8 путь) |

FP8 оригинал **вдвое компактнее** и даст тот же результат.
Нужно проверить, что `convert_hf_to_gguf.py` корректно читает FP8+scale_inv.

### Дополнительные оптимизации v5

#### v5.1 — Асимметрия gate vs up [ожидание: -0.0 — -0.1 PPL]

Сейчас gate_exps и up_exps квантуются одинаково. Gate — фильтр, up — расширение. Попробовать:
- Вариант A: gate точнее (он решает, что пропустить)
- Вариант B: up точнее (он формирует представление)

Бесплатно по размеру — перераспределение внутри зоны.

#### v5.2 — Альтернативные IQ-типы [ожидание: -0.0 — -0.3 PPL]

Вместо iq3_ks (3.19 bpw) для core gate/up:
- `iq4_kss` (4.0 bpw) — промежуточный между iq3_ks и iq4_xs
- `iq4_kt` (4.0 bpw, trellis) — другой алгоритм оптимизации
- `iq3_k` (3.0 bpw) — другая внутренняя структура

#### v5.3 — Свой imatrix на рус+код [ожидание: -0.0 — -0.2 PPL]

Текущий imatrix от ubergarm — английский калибровочный текст. Генерация своего из:
- Русский текст (Wikipedia RU, Habr, юридические тексты)
- Код (Python, JavaScript, SQL)
- Английский текст

Для мультиязычной модели это может дать лучшее распределение точности.

#### v5.4 — KV cache q4_0 [ожидание: косвенное, -0.0 — -0.1 PPL]

V-cache в q4_0 вместо f16 экономит ~0.3 GiB, которые можно вложить в пару слоёв экспертов.

#### v5.5 — Per-expert frequency analysis [ожидание: прорывной, но долгосрочный]

Собрать статистику использования экспертов через hot-expert-trace. Если 20% экспертов обрабатывают 80% токенов — квантовать частых точнее, редких агрессивнее. Требует доработки llama-quantize для per-expert гранулярности.

#### v5.6 — Eval Suite [ожидание: понимание, не PPL]

Прогнать 13 тестов (130 баллов) на v4 и сравнить с v3.1. Покажет, транслируется ли -0.28 PPL в реальное улучшение.

#### v5.7 — Применить к другим моделям

Зонный taper + down>gate/up + budget redistribution — универсальный подход для MoE. Кандидаты:
- Qwen3.5-397B-A17B
- DeepSeek-V3
- Другие huge MoE

## Поколение 6 (v6): гибридные подходы

### Сравнение с существующими методами

Наш подход (zone taper + down>gate/up + budget redistribution) занимает нишу между стандартными:

| Подход | Гранулярность | MoE-aware | Автоматизация |
|--------|--------------|-----------|--------------|
| Standard IQ | По типу тензора | Нет | Полная (1 команда) |
| UD-Q (Unsloth) | По каждому тензору | Косвенно (imatrix) | Полная |
| **Наш** | По зонам + тип тензора | **Да** (эксперты = 95% бюджета) | Ручные рецепты |

### v6.1 — UD-Q importance scores для определения зон [высокий приоритет]

**Суть:** Вместо ручного выбора границ зон (edge=4 слоя, bridge=6) — использовать UD-Q или imatrix importance scores для определения, какие слои реально чувствительнее.

**Как реализовать:**
1. Получить per-layer importance из imatrix (или сгенерировать через llama-imatrix)
2. Ранжировать слои по importance
3. Автоматически назначить зоны: top-N = edge (iq5_k), middle = bridge (iq4_xs), bottom = core (iq3_ks)

**Ожидаемый эффект:** Зоны будут data-driven, а не ручные. Возможно edge не на краях, а в неожиданных позициях.

### v6.2 — Per-expert importance [исследование]

**Суть:** Не все 256 экспертов в слое одинаково важны. Используя hot expert dispatch stats + imatrix, определить importance каждого эксперта.

**Как реализовать:**
1. Собрать dispatch stats через `IK_LLAMA_EXPORT_EXPERT_STATS`
2. Скрестить с imatrix: эксперты с высокой частотой И высокой importance → точнее
3. Требует доработки llama-quantize для per-expert гранулярности (сейчас все 256 экспертов в одном тензоре)

**Блокер:** `--custom-q` не поддерживает per-expert (только per-tensor). Нужна новая опция или доработка кода.

### v6.3 — Гибрид IQ + budget redistribution как стандартная опция [средний приоритет]

**Суть:** Простое улучшение стандартного IQ, не требующее ручных рецептов:
```
llama-quantize --attn-q-type iq5_k --attn-output-type q5_K model.gguf output.gguf IQ3_KS
```
Это одна команда, но с budget redistribution (attention↓, experts получают базовый IQ3_KS).

**Ожидаемый эффект:** Улучшение стандартного IQ за счёт architectural knowledge, без ручных зон.

### v6.4 — Автоматический recipe generator [долгосрочное]

**Суть:** Скрипт, который принимает модель + целевой размер + imatrix и автоматически генерирует оптимальный `--custom-q` рецепт.

**Алгоритм:**
1. Прочитать imatrix → per-layer importance
2. Прочитать hparams → n_layer, n_expert, expert FFN размеры
3. Задать целевой размер (например 92 GiB)
4. Оптимизировать: распределить бюджет по слоям и типам тензоров, максимизируя weighted importance
5. Выдать `--custom-q` строку

**Ожидаемый эффект:** Масштабирование нашего подхода на любую MoE модель без ручного проектирования рецептов.

### v6.5 — Применение к другим моделям [масштабирование]

Протестировать methodology на:
- **Qwen3.5-397B-A17B** — другая MoE архитектура (128 экспертов, 17B active)
- **DeepSeek-V3** — MLA attention + MoE
- **Llama-4 Scout/Maverick** — Meta MoE models

Каждая модель потребует адаптации зон, но принципы (down>gate/up, edge>core, budget redistribution) универсальны.
