# Evidence 6 — инструментация `--moe-trace` проверена на живой MoE-модели

Дата: 2026-09-09
Машина: DESKTOP-HENS8K7, Ryzen 9 7950X, 95.1 ГБ (свободно ~40 ГБ, `llama-server` держал 38.1 ГБ)
Сборка: `D:\build-zen4` (`HAVE_FANCY_SIMD is defined`, см. evidence-5)
Модель: `Qwen3-30B-A3B-Instruct-2507-Q4_K_M`, 17.3 ГБ, `Z:` (HDD)

## 1. Зачем этот прогон

Step0 опирается на `--moe-trace`. При слиянии с upstream вызовы
`moe_trace->begin_batch` / `end_batch` в `examples/main/main.cpp` расставлялись
**вручную**: upstream изменил построение `llama_batch`, и автослияние там не
сработало. За инструментом стоял только `tests/test-moe-trace-writer.cpp`,
который проверяет писателя, а не срабатывание в реальном цикле декодирования.

То есть у Step0 была незакрытая зависимость, не связанная с памятью. Проверять
её следовало первой: нехватка памяти - задержка, сломанный инструмент - отмена.

Выбор модели: MoE, Q4_K (то, на что нацелены Zen4-ядра IQK), 17.3 ГБ - влезает
в свободную память, цена ошибки в 7 раз ниже, чем на MiniMax 123.6 ГБ.

## 2. Прогон

```
llama-cli.exe -m Qwen3-30B-A3B-Instruct-2507-Q4_K_M.gguf
  -p "<20 токенов>" -n 32 -t 16 -c 2048 --no-warmup
  --moe-trace D:\trace_qwen3.ndjson
```

`RUN_EXIT=0`. Полное время 118 с, из них генерация 2.2 с; остальное - чтение
17.3 ГБ с HDD.

## 3. Проверка трассы

Файл забран на linux-хост и разобран построчно парсером JSON.

| Проверка | Результат |
|---|---|
| размер / строк | 1 090 147 байт, 1491 строка |
| невалидных строк JSON | **0** |
| состав записей | `meta` 1, `model` 1, `route` 1488, `end` 1 |
| схема | `ik_llama.moe_routing_trace` v1 |
| модель по трассе | `qwen3moe`, `n_layer` 48, MoE-слоёв 48 |
| батчей | 31, все с полными 48 слоями; неполных **0** |
| арифметика | 31 × 48 = 1488 = `end.routes` |
| выборов экспертов | 11 904 = 1488 × 8 |
| запись `end` | `complete: true` |

Три счёта получены независимо друг от друга - число строк, поле `end.routes`,
и произведение батчей на слои - и сходятся. Значит писатель не терял и не
дублировал записи.

## 4. Сигнал в данных

Задействованы все 128 экспертов, отбор top-8 на токен. Распределение
неравномерное: эксперт 115 выбран 222 раза при равномерном ожидании ~93
(8 из 128 на пару токен-слой) - перекос в 2.4 раза. Топ-5:
115 (222), 103 (203), 0 (192), 43 (176), 19 (161).

То есть инструмент не просто пишет корректный формат, а показывает то явление,
ради наблюдения которого Step0 и затевается.

## 5. Ограничение: prefill не трассируется

`pos` в трассе идёт с 20 по 50, ровно 1 токен на батч. Двадцать токенов промпта
(позиции 0-19) не дали ни одной записи.

Причина - гейт в `dev:examples/main/main.cpp:975`:

```c
if (moe_trace && embd_is_generated) {
    moe_trace->begin_batch(&embd[i], n_eval, n_past, 0);
}
```

**Это замысел, а не регрессия слияния.** Проверено: тот же гейт присутствует до
слияния - `1e190293:examples/main/main.cpp:830`, автор `Andrew_Moryakov`,
коммит `d7bf2f05` от 2026-07-20.

Слияние семантику сохранило и корректно расширило: до слияния было одно
присваивание `embd_is_generated = true` (строка 893), в `dev` их два
(1214 и 1244), потому что upstream добавил второй `embd.push_back()` на
спекулятивном пути.

**Открытый вопрос к Step0:** он разделяет фазы PP и TG, а инструмент наблюдает
только TG. Если вопросы Step0 касаются маршрутизации на префилле, этого он не
даёт. Решение - за владельцем: принять как есть либо заводить отдельную задачу.

## 6. Границы

**Установлено исполнением:** прогон завершился с кодом 0; трасса разобрана
парсером, все счётчики сошлись; распределение экспертов посчитано по всем
11 904 выборам.

**Установлено чтением:** происхождение гейта `embd_is_generated` - сравнением
`dev` с `1e190293` и `git log -S`.

**НЕ является результатом производительности.** Времена этого прогона
(`prompt eval 18.33 t/s`, `eval 27.90 t/s`) не подлежат использованию как
показатели: `--moe-trace` сам объявлен «measurement only; adds synchronization
overhead», и машина была занята - `llama-server` держал 38.1 ГБ из 95.1.
Никаких утверждений о скорости настоящий документ не содержит.

**Не проверялось:** поведение трассы на swap-bound модели; поведение при
многотокенных батчах (здесь все батчи были однотокенными).
