# Evidence 9 — Step0 §1a и §1b: диагностические прогоны

Дата: 2026-09-09
Продолжение evidence-7 и evidence-8. Та же машина, сборка `D:\build-zen4`,
артефакт `D:\MiniMax-M2.5-VariantA.gguf`. Данные в `F:\step0-2026-09-09`.

Оба прогона помечены рунбуком как диагностические и не авторитетные.

## 1. §1a. Token-timing: НЕ ПРОЙДЕН, причина установлена

```
WARNING: Token timing evidence is invalid:
         Token timing footer counts do not match the CLI reported eval runs.
status token_timing_invalid | gen 2.92 t/s | peak 86254 MB | 260.8 s
```

Сайдкар при этом внутренне непротиворечив. Файл содержит 513 строк: заголовок,
511 интервалов и футер.

```json
{"type":"end","complete":true,"generated_tokens":512,"intervals":511,
 "n_eval":511,"llama_reported_n_eval":511}
```

Четыре из пяти проверок в `Read-TokenTiming` (`step0-bench.ps1:364-368`) проходят.
Падают две последние, обе сравнивают с `$ReportedEvalRuns`, а он равен 512.

### Причина

`$ReportedEvalRuns` разбирается из лога регулярным выражением на строке 303:

```
'(^|\s)eval time\s*=\s*[\d.]+\s*ms\s*/\s*(\d+)\s*(?:runs|tokens).*?([\d.]+)\s*tokens per second'
```

Оно принимает и `runs`, и `tokens`, поэтому ловит первую подходящую строку лога.
Раньше подходила только строка `llama_print_timings`, печатающая `ctx->n_eval`
со словом `runs`. Теперь первой идёт строка `main.cpp`, печатающая `n_decoded`
со словом `tokens`.

Числа различаются по устройству: первый выданный токен выходит из батча
обработки промпта, увеличивающего `n_p_eval`, а не `n_eval`. Поэтому
`n_eval = n_decoded - 1` всегда.

### Откуда взялась строка

Внесена upstream, коммит `0a415bde` от 2026-07-06, автор Samuel Oliveira Alves,
«Feat: Llama-cli Spec (#2081)». Проверено: в `1e190293` (снимок до слияния)
такой строки в `main.cpp` нет, в `dev` и в `ik-upstream/main` есть.

Тот же коммит сделал вызов `llama_print_timings` условным:

```c
if (n_decoded > 0) {
    LOG_TEE("main: eval time = ... / %5d tokens ...", n_decoded);
    ...
} else {
    llama_print_timings(ctx);
}
```

При любой нормальной генерации `n_decoded > 0`, поэтому строка со словом `runs`
в логе отсутствует вовсе. Проверено: в логе прогона 0 вхождений
`llama_print_timings`.

### Что это значит

Слияние не сломало ни инструментацию, ни модель. Оно сломало договор между
выводом программы и разбором этого вывода в обвесе. Ни сборка, ни `ctest`, ни
внутренние проверки сайдкара такого не показывают: данные на диске корректны,
футер записан с `complete:true`. Отказ пришёл от единственной проверки, которая
смотрела на обе стороны сразу.

Отсюда следствие для процедуры: после слияния с upstream надо прогонять не
только сборку и тесты, но и измерительный конвейер целиком, включая режимы,
не задействованные в обычной репетиции. Наша репетиция на Qwen шла без
`-TokenTiming` и эту ветку не проверила.

### Решение не принято

Правка на две строки в `step0-bench.ps1`: различать источник по слову, при
`tokens` вычитать единицу. Последствие, которое надо учесть: `$evalRuns`
используется и в расчёте установившегося окна, поэтому производные метрики
базовой линии сдвинутся примерно на 0.2%. Владелец решения не выносил.

Квантили p50/p95/p99, требуемые пунктом 2 списка §4, поэтому не собраны.

## 2. §1b. ETW: пройден со второй попытки

### Первая попытка: отказ по месту на диске

`wpr -start` отработал, `wpr -stop` вернул `0xc5583000` «There are no trace
profiles running». Причина не в локализации и не в правах: `wpr -status`
распознан («WPR is not recording»), права администратора есть.

WPR писал промежуточные коллекторы в `%TEMP%`, а он указывает на
`F:\flutter-build\tmp`. За 114 секунд они выросли до 6.5 ГБ и заполнили `F:`
до нуля, после чего запись остановилась сама.

Осиротевшие коллекторы удалены после проверки по времени создания (22:03:21,
совпадает с началом прогона) и состоянию WPR. Освобождено 6.5 ГБ.

### Вторая попытка

После освобождения места на `F:` (владелец убрал `Games`, плюс перенос
`F:\Фильмы` на `D:` и очистка корзины) прогон прошёл.

```
SCRIPT_EXIT=0
ETL: 11 028 922 368 байт (10.27 ГиБ)
status provisional_reconstructed | gen 2.56 t/s | steady 221 590 742 B/tok
                                 | peak 86 019 MB | 276.3 s
```

Цена наблюдения видна прямо: 2.56 т/с против 3.02 в базовой линии и 221.6 МБ
на токен против 163.6. Наблюдение изменило наблюдаемое примерно на треть по
обоим показателям. Доли и адресатов трафика из этого прогона брать можно,
абсолютные величины нельзя.

### Атрибуция

Рунбук предписывает открыть ETL в WPA вручную. Вместо этого использован
`xperf` из того же Windows Performance Toolkit: это то же извлечение из того же
ETL, без графического окна. Запрет рунбука касается подстановки чисел вручную,
а не штатного инструмента.

```
xperf -i <etl> -o etw-hardfault.csv -a hardfault
```

Отчёт `diskio` вышел пустым, и это ожидаемо: модель читается через mmap,
обращения идут отказами страниц, а не обычными дисковыми запросами.

Итог по жёстким отказам, всего 6 565 408 событий на 183.5 ГиБ:

```
183.25 ГиБ  99.86%  6 551 032 отказа  llama-cli.exe (40464)
  0.03 ГиБ   0.02%      1 458          MiniMax Code.exe
  0.02 ГиБ   0.01%        597          MiniMax Code.exe
  0.01 ГиБ   0.01%        852          backgroundTaskHost.exe
```

Из них на файл модели `D:\MiniMax-M2.5-VariantA.gguf` приходится 183.2 ГиБ,
то есть **99.86% всего объёма жёстких отказов**. Остальные файлы у `llama-cli`
пренебрежимы: `ggml.dll` 2.9 МБ, `llama.dll` 2.3 МБ.

Средний размер отказа по модели 29.3 КиБ, то есть 7.3 страницы по 4 КиБ:
Windows подтягивает соседние страницы упреждающе.

## 3. Что это подтверждает и что закрывает

**Классификация из evidence-8 подтверждена независимым каналом.** Давление на
диск принадлежит файлу модели, читаемому через отказы страниц процессом
`llama-cli`. Посторонний трафик составляет 0.14%.

**Закрыто отклонение про pagefile.** В evidence-7 оно записано как рассуждение
на основании прежнего пика 609 МБ, с явной пометкой «EXPECTED to be negligible,
not verified». Теперь измерено: обращений к `C:\pagefile.sys` за весь прогон
13.0 МиБ у powershell и 5.1 МиБ у MemCompression, около 18 МиБ против 183 ГиБ
у модели. Одна сотая процента. Конкуренции нет.

**Уточнение к симулятору.** Он работает с гранулой замещения 256 страниц (1 МиБ)
и сам помечает это как приближение (`replacement_granularity_approximation: True`).
Фактическая гранула вчетверо мельче, 29.3 КиБ. Это одна из вероятных причин,
почему он завышал промахи вдвое против измеренной базовой линии.
