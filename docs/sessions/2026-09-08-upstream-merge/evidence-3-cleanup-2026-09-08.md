## 1. Модель ветвления записана и сразу применена

`FORK_WORKFLOW.md` переписан из карты веток в модель: три постоянные ветки

## 2. Ветки: 742 → 6

Критерий удаления — доказательство, а не суждение: ветка, у которой **имя и
SHA совпадают** с веткой upstream, не может содержать коммита, которого у
upstream нет.

```
identical-to-upstream   728   ← удалены
FORK-ONLY                13
DIVERGED                  1   ← main
```

Порядок: манифест всех 742 ссылок закоммичен
(`docs/branch-manifest-2026-09-08.tsv`) → классификация пересчитана на свежем
снимке непосредственно перед удалением → удаление партиями по 50 с проверкой,
что в партию не попало имя из списка сохраняемых → сверка уцелевших со
списком построчно (`EXACT MATCH`).

**Обратимость проверена, а не заявлена.** `ik/mla` восстановлена из манифеста
(`git push origin <sha>:refs/heads/ik/mla`), сверена по SHA и удалена снова.
Работает потому, что форки GitHub делят хранилище объектов с родителем.

Затем 8 собственных веток заархивированы аннотированными тегами
(`archive/<ветка>-<дата>`, в сообщении — причина и команда восстановления) и
удалены. Теги создавались **до** удаления, и удаление шло только после
проверки, что тег на GitHub указывает ровно на тип ветки.

Две ветки едва не попали под правило «удалить всё чужое»: `fcp/crash` и
`fcp/recurrent_checkpoint` выглядят как ветки контрибьютора, но upstream их
удалил — форк остался единственным местом. Проверка по содержанию показала,
что обе вошли в upstream через PR (`common_sampler_review` теперь сам
проверяет `adapt_p_ctx != nullptr`; checkpoint — `3fac78c4 (#1310)`), после
чего они заархивированы.

## 3. Второй цикл `upstream-sync` — выигрыш короткого интервала

```
                     синхронизация №1      №2 (в тот же день)
upstream             fe215a8c              1a2a8604
коммитов              415                   2
конфликтов            13 файлов / 15 блоков 0
межфайловых поломок   1 (сигнатура колбэка) 0
время                 часы                  минуты
```

Порядок по `FORK_WORKFLOW.md`: fetch → подтянуть `dev` в полосу →
`git merge-tree --write-tree` (карта без побочных эффектов, вернула чистое
дерево) → merge → гейты → обратно в `dev` → перемотка `main`.

Гейты после №2: сборка 10/10 целей, 0 ошибок; `ctest` 27/31 — **те же четыре**
известных отказа, совпадающих с `docs/rtr-handoff/upstream-four-tests.log`.

Разница между №1 и №2 — не в удаче, а в интервале: неделя upstream-времени
против четырёх месяцев. Конфликтуют не строки, а параллельно развивавшиеся
решения.

## 4. PR #1 закрыт: направление, а не содержание

Открытый в форке PR `exp/raptor-runtime → main` показывал `CONFLICTING`.
Измерения:

```
merge-base                     9f1deefa (май)
добавил бы                     134 коммита
в main есть, а в ветке нет     478 коммитов
диф                            481 файл, +111 796 / −18
```

`+111 796` — не объём работы ветки, а её отставание: `exp/raptor-runtime` не
содержит ни `fe215a8c`, ни `1a2a8604`. Ветка, отстающая сильнее, чем
опережающая, просится в синхронизацию, а не в слияние.

Плюс два запрета из модели: `exp/*` не идёт в `main` до гейтов, а `main`
меняется только перемоткой из `dev`. PR закрыт с комментарием; ветка
сохранена.

## 5. Два фикса из `exp/raptor-runtime` оказались устаревшими

Обнаружено при попытке перенести из ветки что-нибудь полезное:

| Фикс форка | Когда | Что вместо него в upstream |
|---|---|---|
| MSVC AVX-VNNI VEX/EVEX (`bfff3fb7`) | 2026-05-20 | именованные обёртки `ggml_mm256_dpbusd_epi32` в `iqk_config.h` |
| muge+rtr crash (`3e92b6b3`) | 2026-02-23 | `54bcafee` «Allow using -rtr and -muge together» (#1444), 2026-03-16 — ассерт стал терпим к несовпадению типов |

Второй случай — методическая ошибка, стоит записи. `git grep` по добавленным
строкам не нашёл их в `dev`, и это было прочитано как «фикса нет». Два
независимых исправления одного дефекта не имеют общих строк, поэтому поиск по
строке даёт уверенный ложноотрицательный результат. Дискриминатор — датировка:
`git log -S` показал, что послабления не было в родителе форкового коммита,
то есть фикс писали **вместо** него, а не поверх.

Спрашивать надо, достижим ли ещё сбой, а не присутствует ли код.
