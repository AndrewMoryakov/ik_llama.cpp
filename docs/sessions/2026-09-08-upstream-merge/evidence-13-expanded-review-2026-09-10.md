## Результаты расширенного ревью

### B1. P1: dashboard позволяет выбрать произвольный исполняемый файл

`dashboard/dashboard_server.py:1013-1039` принимает `args[0]` из POST
`/api/launch`, добавляет расширение и вызывает `os.path.join(BUILD_BIN, ...)`.
Проверяется только наличие файла, затем `ProcessManager.launch` передаёт его
в `subprocess.Popen` (`:259-268`). Абсолютный путь отменяет ограничение
`BUILD_BIN`; относительный путь с `..` также выходит из каталога.
Клиент может передать путь к системному интерпретатору и его аргументы.

`_cors` и `do_OPTIONS` (`:852-855,873-876`) разрешают POST/JSON с произвольного
Origin; проверки токена или Origin в этом пути нет. Это расширяет поверхность
вызова до сторонних страниц в браузерах, допускающих доступ к localhost.
Успешная эксплуатация из браузера не проверялась и зависит от его сетевых
ограничений. Сам API не ограничивает выбор исполняемого файла.

Windows terminal mode дополнительно сериализует args через `list2cmdline`
и env в `.bat` (`:213-220`), хотя quoting для argv не экранирует язык cmd.
Это требует отдельного отказа от shell-сериализации пользовательского ввода.

Рекомендация: разрешать точные имена поддерживаемых бинарников, проверять
разрешённый путь и Origin/токен, передавать аргументы без сборки shell-кода.
Атрибуция: dashboard добавлен в наш diff относительно `1a2a8604`.
Read-only проверка пути обработчика; отдельно Python `ntpath.join` с
абсолютным именем вернул `C:\Windows\System32\cmd.exe` вне заданного BUILD_BIN.
HTTP-запросы и запуск процесса не выполнялись.

### B2. P2: FQC-03 засчитывает нестрогий JSON как соблюдение формата

`eval/llm_eval_suite_v2/run_fast_qc.py:155-159` начисляет баллы за строгий JSON
через `strict_json_loads`, но `eval_common.py:149-173` после неудачи полного
разбора извлекает объект из окружающего текста. Задание FQC-03 требует
"STRICT JSON only. No extra text". Поэтому неверное соблюдение формата
не отражается в оценке критического теста.

Воспроизведено на Python целевой машины: из исходников HEAD через AST
извлечены именно `strict_json_loads` и `score_fqc_03`; им передан ожидаемый
объект TechVision с префиксом `Extra text before` и суффиксом `Extra text after`.
Получен score 14/15 и `parse_error=None`; прямой `json.loads` того же ответа
дал `JSONDecodeError`. Недостающий балл связан с полем market в синтетическом
объекте, не с посторонним текстом. Это проверка scorer, не замер качества модели.
Рекомендация: для строгого формата разбирать весь ответ и не применять fallback.
Атрибуция: eval-suite включён в наш diff относительно `1a2a8604`.

### B3. P1: RTR auto и загрузчик по-разному размещают CPU MoE-слои

`src/llama.cpp:5435-5445` при одной GPU оценивает `-ncmoe N` как первые N
слоёв (`il < min(ncmoe, n_layer)`). Но `src/llama-load-tensors.cpp:274-286`
при `model.devices.size() < 2` идёт с конца и выбирает последние N слоёв,
в которых реально есть expert-тензоры. Защита AUTO_UNKNOWN для нескольких
GPU этот случай не покрывает.

Триггер: одна GPU, offload включён, `0 < ncmoe < n_layer`, RTR auto;
особенно модель с плотными начальными слоями или неодинаковым размером MoE.
Policy может недооценить CPU-резидентные данные и разрешить repack при
недостаточной памяти. Реальная OOM/подкачка не воспроизводилась.

Рекомендация: использовать единую схему размещения с загрузчиком либо
возвращать неизвестное решение, пока точный placement не доступен.
Атрибуция по agent blame: first-N правило из `d4032bc12`, loader из upstream;
само расхождение перепроверено основным агентом через `git show` обоих файлов.
Оценка read-only, без GPU-прогона.

### B4. P2: SQL-сравнение теряет новый контекст RTR

`scripts/compare-llama-bench.py:125-129,312-320` объединяет `test` и `test_v2`,
но в проекцию и ключ сопоставления не включает `repack_auto`,
`repack_effective`, `repack_status`. `llama-bench` уже пишет эти поля.
Если в БД есть одинаковые по остальным параметрам запуски с разными режимами
RTR, сравнение усреднит их и скроет отличие политики. Нужна явная политика
сопоставления старых записей без этих полей и новых записей с ними.

Атрибуция: отсутствие старого `repack` в ключе унаследовано. Новая поддержка
`test_v2` сохранила ограничение и отбрасывает добавленные нами status-поля.
Это пробел интеграции, не утверждение о полностью новой ошибке усреднения.
Read-only: просмотр diff и SQL; реальная БД бенчмарков не запускалась.
