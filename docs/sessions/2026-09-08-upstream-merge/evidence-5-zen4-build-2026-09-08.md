# Evidence 5 — сборка под Zen4 (Ryzen 9 7950X)

Дата: 2026-09-08
Машина: DESKTOP-HENS8K7, AMD Ryzen 9 7950X, 16 ядер, 95.1 ГБ, Windows
Ветка: `dev` = `b597ece`

## 1. Что проверялось

Утверждение к проверке: «7950X проработан, и мы сможем собрать под него».
Проверялось исполнением, а не чтением конфигураций.

## 2. Найденная проблема

Рабочая сборка `Z:\...\ik_llama_my-fork\build-ui` (бинарники от 2026-09-08
05:52, те самые, на которых предполагалось мерить Step0) собрана **без
Zen4-ядер IQK**.

Условие в `dev:ggml/src/iqk/iqk_config.h:45`:

```c
#if defined(__AVX512F__) && defined(__AVX512VNNI__) && defined(__AVX512VL__) \
 && defined(__AVX512BW__) && defined(__AVX512DQ__)
    #define HAVE_FANCY_SIMD
#endif
```

`__AVX512VNNI__` обязателен. Для MSVC этот макрос ставит только CMake по
`GGML_AVX512_VNNI=ON` (`ggml/src/CMakeLists.txt`); сам MSVC по `/arch:AVX512`
определяет F/BW/DQ/VL, но не VNNI, VBMI и BF16.

В `build-ui` было `GGML_NATIVE=ON` и все четыре `GGML_AVX512*` в `OFF`.
Отсюда `/arch:AVX512` в флагах — и ни одного из нужных макросов.

Существенно: **сборка не давала никакого сигнала.** Конфигурирование без
ошибок, компиляция без предупреждений на этот счёт, бинарники работают.
Отсутствие `#define` — это молча выбранная другая ветка `#if`. В замерах это
выглядело бы как «процессор медленнее ожидаемого».

## 3. Проверка: собирается ли под Zen4

Конфигурирование во `D:\build-zen4`, генератор Ninja, флаги как в
`scripts/build-zen.bat` (`GGML_AVX512`, `_VBMI`, `_VNNI`, `_BF16`):

| Шаг | Результат |
|---|---|
| конфигурирование | `CONFIG_EXIT=0`, 12.8 с, `HAS_AVX512_1 - Success` |
| макросы в `build.ninja` | `__AVX512VNNI__`, `__AVX512VBMI__`, `__AVX512BF16__` — по 27 вхождений |
| те же в `build-ui\build.ninja` | **0** каждого |
| компиляция целей `llama-bench`, `llama-cli` | **154/154, 0 ошибок**, 706 предупреждений (обычный фон) |

`DEFINES` новой сборки содержит `-DGGML_EXPERT_CHUNKING`, `-DGGML_USE_IQK_MULMAT`,
`-DGGML_IQK_FLASH_ATTENTION`, `-DGGML_IQK_FA_ALL_QUANTS` — быстрый путь MoE из
`dev` собирается вместе с Zen4-ядрами.

## 4. Подтверждение исполнением

Запуск обоих бинарников (`llama-cli` на vocab-only модели, без весов):

```
===== NEW BUILD (D:\build-zen4) =====
======================================= HAVE_FANCY_SIMD is defined
===== OLD BUILD (build-ui) =====
======================================= HAVE_FANCY_SIMD is NOT defined
```

Баннер печатает сам бинарник при старте. Это наблюдение, а не вывод из чтения
условий.

## 5. Ответ на исходный вопрос

**Проработан:** инструментарий сборки под Zen4 существует в `dev` и корректен -
`scripts/build-zen.bat` и `scripts/build-zen.sh` включают ровно нужный набор.

**Собирается:** проверено полным циклом - конфигурирование, компиляция, запуск.

**Но применялся не он:** сборка, лежавшая на диске, сделана иначе.

## 6. Следствие для Step0

Базовая линия, снятая на `build-ui`, описывала бы не 7950X, а обобщённый
AVX-512. Мерить следует на `D:\build-zen4`.

Побочно получена готовая пара для A/B, различающаяся ровно одним свойством:
`build-ui` без `HAVE_FANCY_SIMD` против `D:\build-zen4` с ним. Разница между
ними - цена вопроса в числах. Замер требует тихой машины, как и сам Step0.

## 7. Границы

**Установлено исполнением:** конфигурирование, компиляция 154/154, запуск обоих
бинарников с печатью состояния `HAVE_FANCY_SIMD`.

**Не измерено:** производительность. Разница между двумя сборками в t/s не
снималась - на машине занято `llama-server` (pid 30960), и замер был бы
недостоверен. Утверждений о величине выигрыша настоящий документ не содержит.

**Не проверялось:** собираются ли остальные цели (собраны только `llama-bench`
и `llama-cli`), и проходит ли `ctest` на новой сборке.
