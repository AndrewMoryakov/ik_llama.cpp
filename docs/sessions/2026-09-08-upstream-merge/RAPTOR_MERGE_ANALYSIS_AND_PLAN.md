## 1. Метод

```
git merge-tree --write-tree dev 123d398a
```

Вычисляет слияние целиком в объектной базе. Рабочее дерево, индекс и HEAD не
затрагиваются, откатывать нечего. Код возврата `1` = конфликты есть.

## 3. Что слилось чисто

Без единого конфликта:

- `ggml/include/ggml.h` — весь публичный API инструментария MoE
- `ggml/src/ggml-backend.cpp` (+80)
- `src/llama-context.h` — поля `pg_trace_*`
- `examples/server/server.cpp`
- `ggml/src/iqk/iqk_mul_mat.cpp`
- `ggml/CMakeLists.txt`

**Важная оговорка.** «Слилось чисто» означает только то, что git смог свести
текст. Семантика не проверена. В этой же сессии автослияние `main.cpp` прошло
без конфликта и дало ошибку сборки `C2440`, потому что upstream сменил тип
callback'а с `bool` на `int`. Чистое слияние - не гейт, а лишь отсутствие
одного из препятствий.

## 5. Четыре конфликта, созданных нами самими

`AGENTS.md`, `build_raptor_lake.bat`, `dashboard.bat` конфликтуют как **add/add**,
`.gitignore` - по содержимому. Причина: эти файлы уже перенесены в `dev`
порциями 1-2. Они конфликтуют **именно потому, что мы их уже взяли**.

Вместе - 9 блоков и 87 строк, то есть пятая часть всех блоков, не несущая
никакой новой информации. Само по себе это подтверждает выбор «перенос вперёд,
а не слияние»: слияние здесь воевало бы с нашей же предыдущей работой.

## 6. Главный вывод

Стоимость слияния сосредоточена ровно в том, что мы уже решили не брать.

- 9 блоков `llama.cpp` = rtr-auto (L6). Решение «оставить реализацию `dev`» - и их нет.
- 8 блоков `llama.cpp` + `llama-bench.cpp` (9 блоков) = дрейф upstream. При
  переносе вперёд его **не существует**: мы пишем по актуальному коду, а не
  сводим старый с новым.
- 9 блоков = следствие уже сделанного переноса.
- `iqk_config.h` (1 блок) = L2, перекрыт, пропускается.

Остаётся содержательного: `ggml.c` 1 блок, `common/common.cpp` 3,
`common/common.h` 1, `include/llama.h` 1, `src/llama-model.h` 2.

## 7. Поправка к предыдущей оценке

В стратегии от того же числа L1 оценён как «средний риск, куски не наложатся
механически, `ggml.c` за полгода сильно изменился». **Анализ это опровергает.**
`ggml/include/ggml.h` и `ggml/src/ggml-backend.cpp` сливаются без конфликта,
в `ggml.c` один блок, в `llama.cpp` инструментария нет вовсе.

L1 дешевле, чем я оценил. Требование A/B-замера стоимости счётчиков в горячем
цикле при этом сохраняется: оно про производительность, а не про конфликты, и
анализ слияния его никак не снимает.

## 8. План

### Шаг 1. L0 - рецепт Tapered-RAM

Ветка `feature/tapered-ram-recipe` от `dev`.
`git checkout 123d398a -- scripts/quant_minimax_m25/` - 10 файлов, все новые,
конфликт невозможен. Гейт: `bash -n` для `.sh`, разбор парсером для `.ps1`.
PR в `dev`.

Зачем: этим рецептом получен артефакт Step0. Файл есть, рецепта нет.

### Шаг 2. L1 - инструментарий MoE

Ветка `feature/moe-expert-instrumentation` от `dev`.

1. `ggml/include/ggml.h`, `ggml/src/ggml-backend.cpp` - взять как есть, слияние чистое;
2. `ggml/src/ggml.c` - разобрать один блок `GGML_EXPERT_CHUNKING` руками;
3. `include/llama.h` (1 блок) и часть `src/llama.cpp` - API и выгрузка CSV;
4. гейты: сборка всех целей + `ctest`;
5. **A/B-замер**: счётчики выключены против сборки без них. Расхождение в
   пределах шума - слой принят. Иначе - переделка врезок, а не приёмка.

### Шаг 3. Step0

Требует действий владельца: остановить `llama-server` pid 30960 (держит 58.4 ГБ
из 95.1) и перезагрузить машину. Перезагрузка применит новую конфигурацию
pagefile: освободится ~82 ГБ на `C:` (98 -> 16) и ~150 ГБ на `D:`.

Step0 стоит **между** слоями, а не после всех: L0 и L1 делают его доказуемее,
а L4 и L5 должны решаться по его данным.

### Шаг 4. По данным Step0

- **L4 prompt-packed-QKV** - брать, только если PP окажется узким местом.
  Измерено: `pp512` +2.60%, в `pg512,128` - `pp512` +3.45%, `tg128` +0.08%,
  и всё это на `gpt-oss-120b`, не на MiniMax.
- **L5 бюджет hot-expert** - как дефолт не брать: длинный прогон автора
  гипотезу не подтвердил. Ручку - только если захочется перепроверить с L1.
- **L3 CLI `--experimental`** - переносить только вместе с L4 или L5;
  сам по себе это транспорт без груза.

### Шаг 5. L6 - решение владельца

Рекомендация: оставить реализацию `dev` (`llama_rtr_status`, `-rtra` проверен
вживую), из raptor не брать ничего. Это решение снимает 9 из 17 блоков
`llama.cpp` - самую дорогую часть всего расхождения.

### Шаг 6. Закрытие

После Step0 удалить `feature/minimax-step0-readiness`.
`exp/raptor-runtime` не двигать и не удалять до конца переноса; тег
`archive/exp/raptor-runtime-2026-09-08` уже страхует объекты.

## 9. Границы анализа

**Установлено командами:** число и размер конфликтных блоков по дереву
`f15cc1fb`; список чисто слившихся файлов; принадлежность каждого из 17 блоков
`src/llama.cpp` к rtr-auto либо к дрейфу upstream (по первым строкам блоков);
перекрытость `iqk_config.h` в `dev`; отсутствие L0 и L1 в коде `dev`.

**Не установлено:** компилируемость и корректность чисто слившихся файлов;
построчное содержание тел функций; трудоёмкость шага 2.2 - разбор блока
`GGML_EXPERT_CHUNKING` может оказаться дороже оценки, это выяснится при заходе.

**Не проверялось:** влияние L1 на производительность. Это и есть предмет
A/B-замера в шаге 2.5, а не вывод настоящего анализа.
