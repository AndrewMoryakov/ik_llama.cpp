Зачем: этим рецептом получен артефакт Step0. Файл есть, рецепта нет.

### Шаг 2. L1 - инструментарий MoE

Ветка `feature/moe-expert-instrumentation` от `dev`.

1. `ggml/include/ggml.h`, `ggml/src/ggml-backend.cpp` - взять как есть, слияние чистое;
2. `ggml/src/ggml.c` - разобрать один блок `GGML_EXPERT_CHUNKING` руками;
3. `include/llama.h` (1 блок) и часть `src/llama.cpp` - API и выгрузка CSV;
4. гейты: сборка всех целей + `ctest`;
5. **A/B-замер**: счётчики выключены против сборки без них. Расхождение в
   пределах шума - слой принят. Иначе - переделка врезок, а не приёмка.

### Шаг 3. Step0

Требует действий владельца: остановить `llama-server` pid 30960 (держит 58.4 ГБ
из 95.1) и перезагрузить машину. Перезагрузка применит новую конфигурацию
pagefile: освободится ~82 ГБ на `C:` (98 -> 16) и ~150 ГБ на `D:`.

Step0 стоит **между** слоями, а не после всех: L0 и L1 делают его доказуемее,
а L4 и L5 должны решаться по его данным.

### Шаг 4. По данным Step0

- **L4 prompt-packed-QKV** - брать, только если PP окажется узким местом.
  Измерено: `pp512` +2.60%, в `pg512,128` - `pp512` +3.45%, `tg128` +0.08%,
  и всё это на `gpt-oss-120b`, не на MiniMax.
- **L5 бюджет hot-expert** - как дефолт не брать: длинный прогон автора
  гипотезу не подтвердил. Ручку - только если захочется перепроверить с L1.
- **L3 CLI `--experimental`** - переносить только вместе с L4 или L5;
  сам по себе это транспорт без груза.

### Шаг 5. L6 - решение владельца

Рекомендация: оставить реализацию `dev` (`llama_rtr_status`, `-rtra` проверен
вживую), из raptor не брать ничего. Это решение снимает 9 из 17 блоков
`llama.cpp` - самую дорогую часть всего расхождения.

### Шаг 6. Закрытие

После Step0 удалить `feature/minimax-step0-readiness`.
`exp/raptor-runtime` не двигать и не удалять до конца переноса; тег

## 10. Проверка режима `-rtr 2` и вопроса L6 (2026-09-08, после основного анализа)

### Режим `2` - синоним `auto`, содержания не несёт

`123d398a:common/common.cpp`: значения `0|off` и `1|on` разобраны явно, всё
остальное - включая `2` и `auto` - попадает в общую ветку `else`:
`repack_tensors = true; repack_tensors_auto = true;`.

`123d398a:examples/llama-bench/llama-bench.cpp:804`: там это записано ещё
прямее - `if (v == "2" || v == "auto")`, одно условие на оба.

Отдельной ветки кода под режим `2` нет: `repack_mode` в коде отсутствует,
сравнений `rtr == 2` нет. **При выборе реализации `dev` не теряется ничего.**

### `rtr-auto-v2` - это не режим `2`

Отдельная политика за env-переменной `IK_LLAMA_RTR_AUTO_V2`
(`--experimental rtr-auto-v2`): `llama_rtr_auto_v2_enabled()` в
`123d398a:src/llama.cpp:4183`, применение на 4925. Даёт решение из четырёх
исходов - `DISABLE / UNKNOWN / NOT_APPLICABLE / KEEP` - вместо булева ответа v1,
и трактует неопределённость как «безопасно», а не «разрешено».

Комментарий автора над блоком, дословно: этот блок «намеренно самодостаточен,
чтобы его можно было перенести в upstream PR, убрав диспетчеризацию по
переменной окружения и сделав v2 единственной реализацией».

### Реализация `dev` - это и есть v2, уже продвинутая

`dev:include/llama.h`:

```
enum llama_rtr_status {
    LLAMA_RTR_STATUS_DISABLED     = 0,
    LLAMA_RTR_STATUS_ENABLED      = 1,
    LLAMA_RTR_STATUS_AUTO_KEEP    = 2,
    LLAMA_RTR_STATUS_AUTO_DISABLE = 3,
    LLAMA_RTR_STATUS_AUTO_UNKNOWN = 4,

```

`dev:src/llama.cpp:5518` - `llama_rtr_auto_should_disable()` возвращает
`llama_rtr_auto_decision`, а не `bool`; исходы проставляются на 5710
(`AUTO_DISABLE`), 5719 (`AUTO_UNKNOWN`), 5729 (`AUTO_KEEP`).

То есть в `dev` сделано ровно то, что автор raptor описал как план: v2 без
env-гейта, единственной реализацией. Сверх того `dev` выставляет результат в
публичный API (`llama_model_rtr_status`, `dev:src/llama.cpp:10095`) -
наблюдаемости такого рода в raptor нет.

### Вывод: L6 перестал быть решением владельца

Ранее в этом же документе L6 значился как выбор, требующий суждения владельца.
**Это утверждение снимается.** Реализация `dev` содержит функциональность
raptor'овского v2 плюс наблюдаемость, режим `2` эквивалентен `auto`, а
env-гейт и путь v1 в raptor помечены самим автором как временные.

Переносить из raptor по части rtr-auto нечего. Соответствующие 9 блоков
`src/llama.cpp`, 2 блока `common/common.cpp`, 9 блоков `llama-bench.cpp`,
1 блок `common/common.h`, 1 блок `src/llama-model.h` и часть блока
`include/llama.h` разбираются как «взять `dev`».

**Не проверялось:** поведение обеих политик на реальной загрузке модели.
Сравнение проведено по исходному коду и по комментарию автора, а не прогоном.

### Сравнение самой логики решения (дополнение)

Первоначально вывод §10 опирался на сравнение **контракта** решения (четыре
исхода) и наличия env-гейта. Ниже - сравнение самих реализаций, основание
более прочное.

**Вся политика v2** (`123d398a:src/llama.cpp:4406`) - одна эвристика:

```
const uint64_t threshold = avail_ram - avail_ram / 10;  // 90% доступной
if (model_bytes <= threshold) return KEEP;
// иначе DISABLE
```

Сравнивается размер файла целиком. Перед этим - гейт `is_moe || is_minimax_m2`,
иначе `NOT_APPLICABLE`.

**Политика `dev`** (`dev:src/llama.cpp:5518`) моделирует фактическое размещение:

- проход по `probe.weights` с определением, окажется ли тензор на CPU
  (`llama_rtr_auto_tensor_is_cpu`), с учётом `tensor_buft_overrides`;
- раздельный подсчёт `cpu_total_bytes`, `cpu_repackable_bytes` и
  `max_repack_temp_bytes` через `iqk_repack_workspace_size` - то есть учитывается
  пиковая стоимость самой перепаковки, которой у v2 нет вовсе;
- обработка связанного `output.weight`, отсутствующего в GGUF, но создаваемого
  загрузчиком;
- проверки переполнения на каждом сложении;
- пять ранних выходов в `UNKNOWN`, которых у v2 нет ни одного: `--fit`,
  `merge_qkv`/`merge_up_gate_exps`, `--defer-experts`, split-mode `ATTN`/`GRAPH`,
  откат Kompute;
- отдельный исход `DISABLE` при `cpu_repackable_bytes == 0`: `repack=true` тогда
  не даёт ничего, но всё равно тянет отключение mmap;
- лог с четырьмя числами: репакуемое, всего на CPU, пиковая оценка, доступно.

Существо различия: **v2 меряет файл, `dev` меряет то, что попадёт в RAM и будет
перепаковано.** Для MiniMax на 123.6 ГБ это разные числа - часть тензоров может
уйти на GPU, часть неперепаковываема, а пик включает временный буфер
перепаковки. Эта же разница делает реализацию `dev` пригодной для Step0, где
вопрос стоит именно так: влезет ли и какой ценой.

**Что есть у v2 и отсутствует в `dev`** - ровно два пункта, оба не являются
переносимой функциональностью:

1. Исход `NOT_APPLICABLE` и пропуск dense-моделей. `dev` применяет политику ко
   всем моделям, решая по замеру, а не по архитектуре. Это разница в границах
   области действия, а не потерянная функция.
2. Особый случай `is_minimax_m2`. У v2 он нужен был лишь чтобы протащить MiniMax
   сквозь гейт `is_moe`; гейта в `dev` нет - надобность отпала. В остальном это
   метка в тексте сообщения (`"MiniMax M2 model"` против `"MoE model"`).

**Граница по-прежнему та же:** обе реализации сравнены по исходному коду.
Прогоном на реальной загрузке они не сравнивались и не могут быть, пока машина
занята. Доказательство поведением - отдельная задача после освобождения памяти:
одна загрузка MiniMax с `-rtr auto` на `dev` с логом решения.

## 11. L1 отложен (2026-09-08)

Решение владельца: работа с raptor откладывается. Ниже - где именно остановились
и что выяснено, чтобы следующий заход не переоткрывал то же самое.

### Почему это ничего не стоит

Адаптация под Ryzen 9 7950X (Zen4) не зависит от raptor:

- оптимизации Zen4 - это upstream-PR'ы самого ik_llama.cpp (Zen4 Flash Attention,
  Faster R4 quants on Zen4, Zen4: Faster PP for IQ2_KS/IQ4_KS/IQ5_KS и другие),
  а `dev` содержит upstream `1a2a8604` целиком;
- рабочая сборка `build-ui` собрана MSVC 14.41 с `/arch:AVX512` (подставлен через
  `GGML_NATIVE=ON`), то есть Zen4-ядра `HAVE_FANCY_SIMD` активны;
- raptor - лента Intel-ноутбука (Raptor Lake). Его фикс AVX-VNNI существует для
  Alder/Raptor Lake, где AVX-VNNI есть, а AVX-512 нет. **На Zen4 этот путь кода
  не берётся вовсе.**

Ценное из raptor, не зависящее от железа, уже перенесено: активы и документы
(порции 1-2), рецепт квантования Tapered-RAM (L0, PR #2).

### Что сделано в заходе на L1 и не закоммичено

Ветка `feature/moe-expert-instrumentation` заведена от `dev` и удалена.
В ней были взяты из дерева слияния два файла, оба аддитивно
(+102 строки, 0 удалений):

- `ggml/include/ggml.h` (+22) - публичный API инструментария;
- `ggml/src/ggml-backend.cpp` (+80).

Не закоммичено намеренно: без реализации в `ggml.c` это объявления без тел.

### Две находки, ради которых стоит читать этот раздел

**1. Инструмент искажает измеряемое.** Весь подсчёт статистики в raptor стоит
под флагом `ggml_moe_vm_prefetch` (`123d398a:ggml/src/ggml.c:17485`):

```
// Hot expert tracking (PR04)
if (ggml_moe_vm_prefetch) {
    atomic_fetch_add(&ggml_moe_expert_hits[a], ...);
```

Тот же флаг включает `PrefetchVirtualMemory`/`madvise` и перестройку порядка
обхода экспертов. Получить статистику, не изменив поведение ввода-вывода,
в этой реализации нельзя. Для Step0 это дисквалифицирующее свойство: его
методология требует наблюдения без вмешательства.

Следствие: перенос обязан **развязать** наблюдение и оптимизацию - завести
отдельный флаг под счётчики. Это код, которого нет ни в одной ветке.

**2. «Один конфликтный блок» в `ggml.c` обманчив.** Конфликт - в заголовке цикла
диспатча, а тело цикла git слил автоматически в пользу raptor: оно уже использует
`_d` и `ggml_moe_dispatch_order`. Разрешение «оставить `dev`» не соберётся.
Стороны перестраивают один цикл по-разному: у `dev` быстрый путь
`GGML_EXPERT_CHUNKING` через `iqk_mul_mat_moe`, у raptor - обход в порядке
резидентности.

Поправка §7 («L1 дешевле, чем оценивалось») верна для `ggml.h` и
`ggml-backend.cpp` и **неверна для `ggml.c`**.

### Если возвращаться

Порядок: взять только наблюдаемость (счётчики, послойную статистику, выгрузку
CSV) под собственным флагом; VM-префетч, сортировку резидентности и перестройку
цикла не брать. Открытый вопрос, не проверенный: откуда берётся `layer_id`
в счётчике raptor и есть ли он в соответствующей функции `dev`.
