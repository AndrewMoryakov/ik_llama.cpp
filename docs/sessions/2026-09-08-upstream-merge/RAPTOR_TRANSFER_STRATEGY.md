## 2. Главный принцип: перенос вперёд, а не слияние

**Запрещено:** `git merge exp/raptor-runtime` в любую сторону.

Обоснование измеримое: ветка отстала на 491 коммит, включая весь upstream-мерж
(415 коммитов). Слияние заставит разрешать полугодовые изменения upstream против
майского кода в 13 файлах, из них 17 конфликтных блоков в одном `src/llama.cpp`.
Такое число блоков в одном файле — признак не расхождения версий, а двух
независимых реализаций одной функции; построчное разрешение здесь не имеет смысла.

**Вместо этого:** содержимое берётся послойно из дерева `123d398a` и
накладывается на *текущий* `dev`. Для новых путей — `git checkout 123d398a -- <path>`.
Для файлов, существующих в обоих, диff служит **справкой**, а правка пишется
руками по текущему коду.

## 3. Слои, по возрастанию риска

### L0. Tapered-RAM — рецепт квантования. РИСК: НЕТ

10 файлов в `scripts/quant_minimax_m25/`, в `dev` отсутствуют полностью.
C++-кода не содержит вообще: это оффлайн-скрипты квантования плюс документы.

Ценность: этим рецептом получен артефакт `D:\MiniMax-M2.5-VariantA.gguf`,
на котором будет считаться Step0. Сейчас у нас есть файл, но нет
воспроизводимого рецепта — это реальный пробел в доказуемости Step0.

Метод: `git checkout 123d398a -- scripts/quant_minimax_m25/`
Гейт: файлы на месте; `.sh` проходят `bash -n`, `.ps1` — разбор парсером.

### L1. Инструментарий MoE. РИСК: СРЕДНИЙ. ГЛАВНАЯ ЦЕННОСТЬ

Файлы: `ggml/include/ggml.h` (+22), `ggml/src/ggml.c` (+499),
`ggml/src/ggml-backend.cpp` (+80), `include/llama.h` (3 функции), часть `src/llama.cpp`.

Добавляет:
- счётчики попаданий по экспертам, с разбивкой по слоям — `ggml_moe_get_layer_expert_hits`
- статистику locked/unlocked диспатчей — `ggml_moe_get_locked_stats`
- сортировку резидентности: считать сначала экспертов в RAM, перекрывая своп-I/O — `ggml_moe_set_expert_locked`
- VM-префетч для swap-bound моделей — `ggml_set_moe_vm_prefetch`
- выгрузку статистики в CSV — `llama_export_expert_stats_to_file`

Проверено: в коде `dev` этого нет (упоминания только в документах и в JSON
старых прогонов). Не дублирует наш `--moe-trace`: тот на уровне `examples/main`,
этот внутри диспатча ggml. Слои разные.

Почему риск средний, а не низкий: API аддитивное (новые функции, существующие
сигнатуры не меняются), но счётчики стоят **в горячем цикле диспатча**, а
`ggml.c` за полгода upstream сильно изменился — куски не наложатся механически.

Гейт: сборка всех целей + `ctest`, **плюс A/B-замер**, показывающий, что при
выключенных счётчиках стоимость неотличима от нуля. Без этого замера слой не
принимается.

### L2. AVX-VNNI под MSVC. ПРОПУСТИТЬ — перекрыто

`ggml/src/iqk/iqk_config.h` (+8). В `dev` уже есть именованные обёртки upstream:
`dev:ggml/src/iqk/iqk_config.h:60` — `#define ggml_mm256_dpbusd_epi32 _mm256_dpbusd_avx_epi32`.
Тот же дефект, другое решение. Переносить нечего.

### L3. CLI `--experimental key=value`. РИСК: НИЗКИЙ

`common/common.h` (+2: `experimental_cli`), часть `common/common.cpp`.
Сам по себе ничего не делает — это транспорт для ручек из L4/L5.
Переносить до них, не после.

### L4. Prompt-packed-QKV. ОТЛОЖИТЬ ДО ДАННЫХ Step0

`src/llama-model.h` (`computed_prompt_wqkv`/`bqkv`), `src/llama-context.h`
(`pg_trace_*`), часть `src/llama.cpp`.

Измеренный эффект (`GPT_OSS120B_PROMPT_PACKED_CONFIRM_2026-03-04.md`):
`pp512` +2.60%; в смешанном `pg512,128` — `pp512` +3.45%, `tg128` **+0.08%**.
То есть выигрыш только на препроцессинге промпта, и померян на `gpt-oss-120b`,
не на MiniMax.

Решение переносить принимать **по результатам Step0**: если PP-фаза не окажется
узким местом, 3% на чужой модели не окупают правку `src/llama.cpp`.

### L5. Бюджет hot-expert. НЕ ПЕРЕНОСИТЬ как дефолт

`MINIMAX_HOT_EXPERT_LONGRUN_2026-03-01.md`, вывод дословный: длинный
контролируемый прогон **не подтвердил** подъём бюджета выше legacy `16`.
Экспериментальный дефолт `~24` был откатан обратно.

Гипотеза закрыта собственными данными автора. Ручку имеет смысл вернуть только
после L1 — чтобы перепроверить с нормальным инструментарием, а не наугад.

### L6. rtr-auto. ТРЕБУЕТ РЕШЕНИЯ ВЛАДЕЛЬЦА

Столкновение двух реализаций одной фичи:
- `dev`: `llama_rtr_status` (`include/llama.h`, `src/llama-model.h`, `src/llama.cpp`), работает, `-rtra` проверен вживую
- raptor: `llama_get_total_ram_bytes`, `effective_repack_tensors` (`src/llama-model.h`, `src/llama.cpp`), поколение мая

Рекомендация: **оставить реализацию `dev`, из raptor не переносить ничего**.
Основание: реализация `dev` новее и проверена; upstream не возьмёт ни ту, ни
другую (PR #1738 закрыт), значит второй экземпляр не нужен никому.

## 4. Страховка, обязательная для всех слоёв

1. **До начала** — тег `archive/exp/raptor-runtime-2026-09-08` на `123d398a`.
   После этого объекты переживут любое удаление ветки.
2. **Один слой = одна ветка от `dev` = один PR.** Два слоя в одной ветке
   запрещены: иначе откат одного тянет за собой другой.
3. Каждый слой проходит те же гейты, что проходил `dev`: сборка всех целей + `ctest`.
4. L1 дополнительно — A/B-замер стоимости счётчиков.
5. Ветка `exp/raptor-runtime` **не удаляется и не двигается** до конца переноса.

## 5. Порядок

```
L0 (рецепт) -> L1 (инструментарий) -> [ Step0 ] -> решение по L4 и L5
                                          L2 пропущен, L3 перед L4/L5,
                                          L6 - решение владельца
```

Step0 стоит **между** слоями, а не после всех. L0 и L1 делают Step0 доказуемее:
L0 даёт воспроизводимый артефакт, L1 — наблюдаемость маршрутизации внутри
диспатча. А L4 и L5 наоборот должны решаться **по данным** Step0, а не до них.

## 6. Границы этой проверки

Установлено командами: объёмы расхождения, список файлов, добавленный
публичный API, отсутствие L0/L1 в `dev`, перекрытость L2, выводы замеров
из документов самой ветки.

Не проверено: построчный дифф тел функций в `src/llama.cpp` (+1822) и
`ggml/src/ggml.c` (+499). Оценки трудоёмкости L1 и L4 - предположительные;
их надо уточнять при заходе в слой, а не сейчас.
