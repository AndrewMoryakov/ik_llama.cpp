# Evidence 11 — фазы генерации и обработки промпта суть разные режимы

Дата: 2026-09-10
Продолжает evidence-10, где цена сборки без Zen4-ядер измерена на модели,
помещающейся в память. Здесь тот же вопрос задан целевой модели, и отдельно
разобрано, почему две фазы работают с разной скоростью.

## 1. Гипотеза и её проверка

Step0 (evidence-7) мерил генерацию и показал загрузку процессора 7.97%, то есть
упор в чтение. Обработка промпта это другая фаза: веса читаются один раз на
батч, а не один раз на токен, и работы над ними в разы больше. Гипотеза была,
что эта фаза может оказаться вычислительной, и тогда правильная сборка ускорит
целевую модель без всякого квантования.

Проверка прямая: если Zen4-ядра дают прирост, фаза вычислительная; если нет,
она тоже упирается в диск.

`llama-bench -m MiniMax-M2.5-VariantA.gguf -t 16 -fa 1 -p 2048 -n 0 -r 3 -ngl 0`,
генерация выключена, чтобы фазы не смешивались.

```
OLD build-ui     pp2048  10.25 ± 0.35
NEW build-zen4   pp2048  10.39 ± 0.03
```

**Гипотеза не подтверждена.** Разница 1.4% при разбросе старой сборки ±0.35
лежит внутри шума. Обработка промпта на MiniMax упирается в чтение.

## 2. Картина по четырём режимам

Сведение evidence-7, evidence-10 и настоящего замера:

```
модель в памяти,   промпт      +19.9%   измерено (evidence-10)
модель в памяти,   генерация     0%     измерено (evidence-10)
модель больше RAM, промпт       +1.4%   измерено, внутри шума
модель больше RAM, генерация    ~0%     выведено из CPU 7.97%, не измерено
```

Вывод точнее прежнего: **Zen4-ядра значимы только когда модель помещается в
память и фаза вычислительная.** Для MiniMax они не значимы ни в одной фазе.

Это уточняет формулировку evidence-10, где сказано «значима для нагрузок с
длинными промптами на моделях, помещающихся в память». Условие про длинные
промпты верно, но недостаточно: помещение в память обязательно.

## 3. Почему промпт всё же втрое быстрее генерации

При том же упоре в диск обработка промпта идёт на 10.25 т/с против 3.02 т/с на
генерации. Причина не в вычислениях, а в объёме чтения на токен.

При генерации маршрутизатор выбирает 8 экспертов из 256 в каждом из 62 слоёв,
их веса поднимаются, считается один вектор. Измерено: логический диапазон
3.76 ГиБ на токен, из них 163.6 МБ реально с диска.

При батче в 2048 токенов каждый токен выбирает своих экспертов, но объединение
по батчу охватывает почти весь набор. Из отчёта локальности (evidence-8):

```
окно   8 токенов   2 333 уникальных эксперта
окно  32 токена    5 448
окно 128 токенов   9 593  из 15 872 существующих
```

На 2048 токенах читается по сути вся модель, около 120 ГиБ, но один раз на весь
батч. Это порядка 63 МБ на токен против измеренных 163.6 МБ при генерации,
отношение 2.6. Наблюдаемое отношение скоростей 10.25 к 3.02 составляет 3.4.
Величины одного порядка, то есть объём чтения на токен объясняет разницу.

**Оговорка:** дисковый трафик отдельно для фазы промпта не измерялся. 63 МБ на
токен это расчёт по объёму модели и размеру батча, а не показание счётчика.
Согласованность с наблюдаемым отношением скоростей есть, доказательства нет.

Почему выигрыш всего втрое, а не в тысячу раз при батче в 2048: объединение
экспертов растёт вместе с батчем. Маршрутизация почти равномерная,
нормализованная энтропия 0.919 (evidence-8), поэтому при большом батче читать
приходится всё. Нельзя прочитать меньше, чем вся модель.

## 4. Что это меняет в выводах evidence-8

Ветка работ там выбрана по измерениям фазы генерации. Оставался вопрос, не
относится ли вывод «узкое место это объём чтения» только к декодированию.

Настоящий замер отвечает: **не относится, обе фазы в одном режиме.** Вывод
evidence-8 распространяется на обработку промпта без изменений, и выбор ветки
(сокращение байт на токен) от этого только прочнее.

Побочно закрывается и вопрос о вычислительных оптимизациях на целевой модели:
они не помогают ни в одной фазе.

## 5. Границы

**Измерено:** обе сборки на MiniMax, промпт 2048, три повтора, генерация
выключена.

**Слабое место замера:** каждый запуск `llama-bench` загружает модель заново,
три повтора внутри запуска идут по одному и тому же неполному прогретому
состоянию, поэтому разброс занижен. Чередующегося прогона, как для Qwen в
evidence-10, здесь не делалось: разница и так лежит внутри разброса старой
сборки, и чередование её не выявит.

**Не измерено:** дисковый трафик фазы промпта (см. оговорку в §3) и прямое
сравнение сборок на генерации MiniMax.
