## 1. Raptor Lake handoff ведёт на устаревшую ветку и опцию сборки

`project_docs/hardware/AGENT_BRIEF.md`, `LAPTOP_BENCH_PROTOCOL.md` и
`QUICKSTART_RAPTOR_LAKE.md` продолжают называть ветку
`feature/raptor-lake-laptop` и CMake-опцию `GGML_AVX_VNNI`.

Текущая карта в `FORK_WORKFLOW.md` переименовывает эту линию в
`exp/raptor-runtime`, а `build_raptor_lake.bat` использует upstream-опцию
`GGML_AVXVNNI` без подчёркивания. Следование старому brief может привести к
бенчмарку на неверной ветке или сборке без предполагаемого AVX-VNNI пути.

Нужна отдельная правка: добавить к трём старым входным документам заметку
`STOP`, направить к `FORK_WORKFLOW.md` и заменить инструкцию по опции.

**Основание:** прочитаны указанные файлы, `FORK_WORKFLOW.md:248,255` и
`build_raptor_lake.bat:39,48`. Это вывод из исходников, не проверенный сборкой.

## 2. Индекс смешивает измеренную скорость и реконструированную метрику I/O

`00-INDEX.md` называет строку «Авторитетная базовая линия: 3.02 т/с,
163.6 МБ на токен». Но `evidence-7` прямо разделяет их качество:
`3.02 т/с` измерено, тогда как `phys_gen_bytes_per_tok` получен методом
`reconstructed_estimate_from_end_and_reported_tps`.

`evidence-9` фиксирует, что после изменения upstream разбор лога выбрал число
`tokens` вместо `runs`; двухстрочная коррекция сдвинет производные метрики
базовой линии примерно на 0.2%. Пока parser не исправлен и сводка не
пересчитана, индекс должен помечать `163.6 МБ/токен` как оценку, а не как
равноценную авторитетную величину.

**Основание:** `00-INDEX.md:27`, `evidence-7` §6 и `evidence-9` §1. Это
проверка документов и кода parser, не повторный замер.

## 3. Фактическое продвижение `main` не соответствует правилу fast-forward

`FORK_WORKFLOW.md` задаёт инвариант: `main` меняется только fast-forward из
`dev`, чтобы он был проверенным состоянием `dev`. Однако GitHub PR #4 был
обычным merge: base `main@9fb6f5b9`, head `dev@48444a64`, merge commit
`ca0c4472`. На 2026-09-10 GitHub API сообщает для `main...dev` статус
`diverged`, `ahead_by=6`, `behind_by=1`.

Это не повод переписывать историю немедленно. Сначала нужно выбрать и записать
единую модель: продвигать `main` только fast-forward, либо изменить workflow
так, чтобы PR-merge был разрешён и проверяемая граница была определена иначе.

**Основание:** `FORK_WORKFLOW.md:23,38`, GitHub API PR #4 и compare
`main...dev`, прочитанные 2026-09-10. Не выполнялись merge, rebase или push.

## 4. `--moe-trace` разрушает существующий файл доказательств

В `examples/main/moe-trace.cpp:257` обычный выходной файл открывается с
`std::ios::trunc`. Перед этим есть защита от совпадения с входными и
защищёнными путями, но нет отказа для уже существующего самостоятельного
output. Повторный запуск с тем же NDJSON путём сотрёт предыдущую трассу до
того, как новый прогон завершится; последующая ошибка оставит только неполный
артефакт.

В `examples/main/token-timing.cpp:212-213` аналогичный путь уже отказывает,
если файл существует. Для trace нужен тот же контракт либо временный файл с
публикацией без замены.

**Основание:** просмотр `moe-trace.cpp:244-257` и
`token-timing.cpp:212-213`. Поведение не воспроизводилось запуском.
