## The fix review forced before the merge could be trusted

Upstream's `ae7e9b5e0` made `llama-bench` forward unknown options into a new
`extra_args` column instead of exiting 1. That turned `-rtra` from an error into
a **silent no-op**: the run benchmarked without repacking while the table looked
ordinary. Fixed in `f5ab876a6` (9 lines: a parser branch and a `--help` entry).

The same run is the first end-to-end exercise of the merge's `src/llama.cpp`
resolution — until then it had been chosen by reading, not by running:

| mode | `repack` | `repack_auto` | `repack_effective` | `repack_status` |
|---|---|---|---|---|
| `-rtr 1` | true | false | **true** | enabled |
| `-rtr auto` | true | true | false | auto_unknown |
| `-rtr 0` | false | false | false | disabled |
| `-rtra` | true | true | false | auto_unknown |

`repack_effective=true` under `-rtr 1` can only come from the
`model.n_repacked` write that was kept inside upstream's widened guard, so both
`src/llama.cpp` regions are exercised, not merely read. `auto_unknown` is the
documented Windows Job Object branch: launched over ssh, available memory cannot
be queried, and the policy refuses rather than guesses.

## Where this record is weaker than it reads

- **Gate 8b is inconclusive.** A control build of the same tree with only
  `GGML_NATIVE=ON` also printed `HAVE_FANCY_SIMD is defined` — which settles an
  open contradiction (FORK_WORKFLOW's gate text says MSVC does not define the
  extension macros by itself; on this tree and compiler it does) — but it also
  benched *faster*: pp2048 698.99 ± 16.26 against 665.01 ± 5.27, tg128 49.90 ±
  1.01 against 48.31 ± 0.56. Runs were short (`-p 2048 -n 128 -r 3`), sequential
  rather than interleaved, and `evidence-10` warns that exactly this regime
  swallows real differences in noise. So: both builds reach the fancy kernels;
  the 5% gap is unexplained and must not be quoted as a performance result. The
  control build's own log was not kept.
- **Gate 8a's error bars are the wrong yardstick.** ±1.11 is the per-run
  uncertainty. Paired per-chunk, the two runs differ by a mean of −0.00075 nats
  with a paired standard error of 0.00063 and a worst chunk of 0.015 — a much
  tighter statement than "inside the interval", and the one to cite.
- **Two gate-5 passes are hollow.** `test-model-load-cancel` and
  `test-autorelease` print "No model file provided. Skipping this test" and count
  as Passed. `test-chat-template` stops at its first mismatch, so the templates
  after granite are never exercised.
- **One model, one quant.** Gates 3, 7, 8a and 8b all ran on
  `DeepSeek-R1-Distill-Qwen-1.5B-Q4_K_M.gguf`
  (sha256 `C3DB87E9A0985C61896A03734ECCE62B…`, 1117320512 bytes) because the
  models the September gate run used, `Qwen2.5-1.5B-Instruct-Q4_K_M` and
  `Qwen3-30B-A3B-Instruct-2507-Q4_K_M`, went with the lost `D:` volume. The
  perplexity corpus is the first 204800 bytes of the rescued
  `E:\llama_cpp\corpora\wikitext-2-raw\wiki.test.raw`
  (sha256 `B434B900C963DD9487558747D40F8397…`). Consequences: the documented
  reference `PPL = 1.0126` is not reproducible and was replaced by the
  differential above; `--moe-trace` was never run end to end, because the model
  is dense.
- **Not covered at all.** With `GGML_CUDA=OFF` and no RPC, Metal, SYCL or Vulkan,
  none of `ggml-cuda/*` (~100 files), `ggml-rpc.cpp` (+1282 and the new
  `ggml-rpc-transport.*`), Metal, SYCL, Vulkan, `examples/mtmd/clip.cpp` (+564)
  or the server webui was compiled. That is the largest share of this diff, and
  a green sheet here says nothing about it.
- **The fork's own purpose is untested by this run.** `llama-load-tensors.cpp`
  (+773), `llama-model-loader.cpp` (+357), `llama-mmap.cpp` (+78) and the new
  `llama-moe-cache.cpp` (+459) all land on the swap-bound out-of-RAM MoE path
  this fork exists for. Every gate here loaded a model that fits in RAM.
