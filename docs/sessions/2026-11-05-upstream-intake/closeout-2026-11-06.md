## The five deferred items

### 1. `test_v2` as the SQL table name — **fixed**

The hazard was real and had two layers, only one of which the deferral named.

The named one: `CREATE TABLE IF NOT EXISTS` is a no-op against a database that
already holds the table, so a binary whose field set has grown — the intake added
upstream's `extra_args` and `n_cpu_moe` — would emit an `INSERT` with more columns
than the stored schema and fail. Fixed by moving the writer to `test_v3`
(`examples/llama-bench/llama-bench.cpp`, `table_name()`), with the rule written
next to it: a released table is frozen, a changed field set bumps the version.

The layer the deferral did not name, found while testing the fix:
`scripts/compare-llama-bench.py` hardcoded `IN (?, ?)` against a two-element
`BENCH_TABLE_NAMES`, so adding any third version would have raised
`sqlite3.ProgrammingError` at the first query. The placeholder count now follows
the tuple.

And a third defect, unrelated to the table name but on the same path: the script
resolved its default baseline through `repo.heads.master`, a branch this fork does
not have. A plain `./scripts/compare-llama-bench.py` raised `AttributeError: No
item found with id master` rather than reporting anything useful — in both the
baseline and the compare path. Both now resolve through one helper that tries
`master`, then `main`, then the checked-out branch, and reports a usable error on
a detached HEAD.

**Verified, with a control.** The consumer side on Linux, no build needed: a
database carrying a 31-column `test_v2` row and a 33-column `test_v3` row, read by
the patched script with no arguments on a checkout whose branch is `main`,
produced the comparison table across both versions.

The writer side on desktop-hens8k7, by reproducing the failure first. The
post-intake field set is 61 columns, so a database written before the intake holds
a 59-column `test_v2` — the same list without `extra_args` and `n_cpu_moe`. Built
that database, then applied the `-o sql` output of the binary *before* this fix:

```
FAIL OperationalError: table test_v2 has no column named n_cpu_moe
```

Then rebuilt `llama-bench` from `0d400df7` and applied its output to the same
database:

```
OK tables=test_v2,test_v3
```

So the hazard was real rather than inferred, the old table is left untouched, and
the new rows land in `test_v3`. Logs: `E:\gates\sqlv3\run2.log`.

Earlier context: `85fc0aff` ("fix: restore llama bench SQL consumer
compatibility") had already made the consumer read both `test` and `test_v2`, so
the July plan's "release blocker" was half-closed long before this intake. The
plan still said *blocker* on 2026-11-06 and now carries a dated status table.

### 2. Our chat parser against upstream's `4282b7aea` — **open, with a decisive experiment**

Our `04f7fe254` added 11 lines to `common/chat-peg-parser.cpp` (quoted values of
string-capable properties in Python-style calls) plus 95 lines of
`tests/test-chat-auto-parser.cpp`. Upstream's `4282b7aea` reworked the same file
far more broadly (+159/−41) for LFM2 tool calls, mapping Python literals to JSON.
Both are now in the tree and `test-chat-auto-parser` passes, so nothing is
broken; what is unresolved is whether our 11 lines still carry a case upstream's
rework does not.

The experiment that settles it, not yet run: revert those 11 lines on a scratch
branch, build, and run `test-chat-auto-parser`. If it still passes, upstream's
version subsumes ours and the 11 lines should go, because they will cost a
conflict at every future merge of that file. If it fails, the failing case is
exactly what our lines are for, and it belongs in the record. Cost: one
incremental build plus one test.

### 3. `tools/moe_cache_sim` beside upstream's `--moe-cache-mib` — **closed**

## What is now the next real test

The gate run's own strongest caveat, unchanged by anything above: **every gate
loaded a model that fits in RAM.** The files this fork exists for —
`llama-load-tensors.cpp`, `llama-model-loader.cpp`, `llama-mmap.cpp` and the new
`llama-moe-cache.cpp` — all land on the swap-bound out-of-RAM MoE path, and none
of them was exercised post-intake. A green sheet of 36 tests says nothing about
that path.

So the next test is not another branch question and not another quantization: it
is one out-of-RAM MoE run on this machine, with `--moe-cache-mib` set, against the
53 GiB quant at a context large enough to exceed physical RAM, compared with the
pre-intake binary that is still on disk at
`E:\llama_cpp\ik-llama-unsloth-build`. Until that runs, the intake is verified
everywhere except where it matters most.
